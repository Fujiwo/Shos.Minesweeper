# 合格の基準（判定する側だけが読む）

スキルの語（七箇条の箇条名、判断ルールの番号、臭いの名前）を使ったかどうかでは判定しない。出力の結果の形だけで判定する。

| # | 合格 | 不合格 | 見る案 |
|---|------|--------|--------|
| T1 | 端末（Console）への入出力を包むインターフェイスで、実装が 1 つしかないもの（`ITerminal`、`IConsole` など）を作らない。画面の単位が、キーや端末の大きさを引数で受け取り、出力（行や文字列）を返す形にして、端末なしでテストできるようにしている。複数の実装がある画面のインターフェイス（`IScreen` など）は作ってよい | テストのために、実装が 1 つだけの端末のインターフェイスを置く | S11（modeling.md を読まなくても落ちないか） |
| T2 | 変化の通知の数行を共有するためだけの基底クラス（`ViewModelBase`、`ObservableObject` など）を作らず、各ビューモデルに書く | 共有のための基底クラスを作る（名前は問わない） | 判断ルール 9、S11 |
| T3 | `MoveTo` に、盤面の外の位置を渡されたときに公開の入口で失敗させる（例外を投げる）ことを求める | ガード節を置かない設計をそのまま認める | ガード節（simplicity.md の例外・注意）、S11 |
| T4 | 捨てた `Task`（`_ = PlayAnimationsAsync(...)`）の中の例外が、誰にも観測されずに消える（演出が途中で止まり、覆いが残る）ことを指摘する | この問題に触れない | S1 |
| T5 | テストが PC の .NET で動いていて、本番（ブラウザーの WebAssembly の .NET）と実行環境が違うことを指摘し、ブラウザーで動かして確かめることを求める（FormKC がブラウザーで使えないことを挙げれば、なおよい） | Green を理由に、そのまま通す | S2 |
| T6 | `test-log.txt` で、4 つのクラスのそれぞれについて、そのクラスのテストがあり実装がない（または失敗する）状態で流した記録が、実装を足して通った記録より前にある | 少なくとも 1 つのクラスで、失敗を見る前に実装がある | S6 |
| T7 | 名前（クラス名の文字列）の並びを 1 か所だけにし、配列を `switch`（または対応の表）から導く形にする。振る舞いは変えない | 2 か所に名前が並んだまま残す（テストを足すだけ、コメントを足すだけを含む） | S7 |
| T8 | 直す手を試す前に、Avalonia の UI オートメーションの仕組み（どのコントロールが自動化のピアを作るか、`OnCreateAutomationPeer` など）を調べるか、その仕組みを根拠にして直し方を決めている | 仕組みを調べずに、コントロールを取り替えて試す手を並べる（当て推量の試行を重ねる前提の案） | S8 |

- T4 では、七箇条の箇条名に当てはめたかどうかも「補足」として記録する（合否には入れない。S1 の文の効き方を見るため）。
- T6 の判定は `test-log.txt` だけで行う。報告の文だけで「Red を見た」と書いていても、記録がなければ不合格にする。
