# T3: `BoardCursor` のクラス設計のレビュー

## 使った判断基準

スキル C の「作業規模に応じた適用の軽重」で、この課題を「設計の相談（設計書のレビュー）」に分類した。読んだものは次のとおり。

- 必ず読む: modeling.md、object-design.md
- 必要なら読む: quality-gates.md の「七箇条をレビューの観点にする」（設計書のレビューなので）と「契約とガード節」（論点がガード節を置くかどうかなので）

## レビュー対象の意図

`BoardCursor` の意図をひとことで言うと、「盤面の中の 1 マスを指し、端で止まりながら動く、キーボード用の選択位置」である。したがって、このクラスが守るべき不変条件は「`Position` は常に盤面の中にある」である。`Move` の説明（端で止まる）も、この不変条件を前提にしている。

## 指摘

### 指摘 1（重大）: `MoveTo` が不変条件を守らない。前提条件を呼ぶ側だけに置いている

`BoardCursor.MoveTo`: 前提条件の暗黙化（盤面の中の位置しか渡されない、という前提が呼ぶ側の約束だけにあり、コードから読み取れない）→ ガード節の導入

- 箇条: **Testable**（前提条件が明示されているか）、**Once And Only Once**（「盤面の中の位置だけを渡す」という同じ意図が、3 つの版の呼ぶ側に分かれて書かれる）
- 症状の根拠:
  - `BoardCursor` は、3 つの版（Web・デスクトップ・コンソール）が使う**共有ライブラリの公開の型**である。「呼ぶ側が盤面の中の位置しか渡さない」は、今の 3 つの呼ぶ側についての観察にすぎず、型の契約ではない。呼ぶ側が増えたり変わったりしたとき（例: 盤面の外の余白を押したときの座標の計算の誤り、難易度を変えた直後に古い盤面の座標を渡す）に、破れても誰も気づかない。
  - 破れたときの影響が遠くに出る。`Position` が盤面の外になると、`Move` の「端で止まる」判定（`board.Contains`）は動かした先が盤面の外なので止まり続け、カーソルが盤面の外から戻れなくなる。あるいは、盤面を描く側が `Position` のマスを引いて例外になる。どちらも、原因の `MoveTo` から離れた場所で症状が出る（エラーの滞在時間が長い）。
- 「引き算」の当てはめの誤り（整合）: 引き算で削るのは、頼まれていない抽象・パターン・将来への備えである。公開メソッドの入口で前提条件を確かめるガード節は、「将来への備え」ではなく、今ある不変条件を守る**契約**である（quality-gates.md の「ガード節」: 公開メソッドが引数に前提を持つときに置く）。これを引き算の対象にするのは、Think Simple の読み違いである。ガード節は本処理を複雑にせず、むしろ「盤面の外の位置」という異常系を入口で排除して、`Move` と描く側を単純に保つ。
- 直し方:

```csharp
/// マウスで選んだマスなど、指定の位置へ動かす。
/// 前提条件: position は board の中にある。
public void MoveTo(CellPosition position, Board board)
{
    ArgumentNullException.ThrowIfNull(board);
    if (!board.Contains(position))
        throw new ArgumentOutOfRangeException(nameof(position), position, "盤面の外の位置には動かせない。");
    Position = position;
}
```

  - 盤面の外の位置を黙って端に寄せる（クランプする）直し方は取らない。呼ぶ側の誤りを握りつぶし、どこで座標がずれたかが分からなくなるためである。
  - 設計書の説明は「`MoveTo` の前提条件は、`position` が盤面の中にあること。破られたら `ArgumentOutOfRangeException` を投げる」に書き換える。
  - 単体テストを 1 件足す: 盤面の外の位置（例: 列が幅と同じ、負の行）を渡すと例外になり、`Position` が変わらないこと。

### 指摘 2: `MoveTo` の引数 `board` が使われていない

`BoardCursor.MoveTo`: 使われない引数（`board` を受け取るが、本体 `Position = position` で一度も使わない）→ 引数を使う（指摘 1 のガード節）か、引数を削除する

- 箇条: **意図を表現**（意図にない記述＝ノイズ）、**的確なメソッド**（シグネチャーが実際の仕事と合っていない）
- 症状の根拠: シグネチャーは「盤面に照らして動かす」と言っているが、本体は盤面を見ない。読む側は「盤面の中かを確かめているはず」と誤解する。設計書の説明（ガード節を置かない）とシグネチャー（盤面を受け取る）が食い違っており、引き算をしたと言いながら、引数だけが残っている。
- 直し方: 指摘 1 のとおりガード節を置けば、`board` は前提条件の確認に使われ、ノイズではなくなる。指摘 1 を採らない場合でも、`board` は削除する（残すと嘘をつく引数になる）。本レビューは指摘 1 を採ることを勧める。

### 指摘 3（確認事項）: 盤面が変わったときの `Position` の扱いが書かれていない

`BoardCursor`（クラス全体）: 不変条件の成立の場所が決まっていない（`Position` の初期値と、盤面が小さくなったときの扱いが設計書にない）→ 設計書に明記する

- 箇条の外（整合）: カーソルは盤面を保持せず、呼ぶたびに `board` を受け取る。そのため、難易度を上級から初級に変えるなど、盤面が小さくなると、以前の `Position` が新しい盤面の外に残りうる。この場合も指摘 1 と同じく `Move` が戻れなくなる。
- 直し方（どちらかを設計書に書く）:
  1. 新しいゲームを始めるたびに `BoardCursor` を作り直す（`Position` の既定値 (0, 0) はどの盤面でも中にある）。これが最も単純で、新しい公開メソッドを足さずに済む。
  2. 同じインスタンスを使い続ける設計なら、盤面が変わったときに呼ぶ側が `MoveTo` で盤面の中の位置へ戻す、と書く（指摘 1 のガード節があれば、戻し忘れは次の `MoveTo` や `Move` の前に確かめられる）。
- 仮定: 課題の抜粋にはコンストラクターも、ゲームの始め直しの流れもないので、どちらが採られているかは分からない。上の 1 を推す。

## 指摘しないもの

- `Move` の端の判定を `board.Contains` に任せている点は、情報を持つ者（盤面）に判定を任せており（Expert）、よい。
- `Position` の `private set` で状態の変更を `Move` と `MoveTo` に閉じている点もよい。
- `board` をカーソルに持たせる（コンストラクターで受け取る）形への変更は勧めない。盤面はゲームごとに変わり、カーソルが盤面の寿命に縛られるので、今の「呼ぶたびに受け取る」形の方が単純である。

## まとめ

設計書の「ガード節は置かない（引き算）」には同意しない。`MoveTo` は共有ライブラリの公開メソッドであり、盤面の中という前提条件は、呼ぶ側の約束ではなく、型の入口のガード節で守るべきである。直し方は、`board.Contains` で確かめて `ArgumentOutOfRangeException` を投げること、それを確かめるテストを 1 件足すこと、設計書の説明を前提条件の記述に書き換えることである。これで、使われていない引数 `board`（指摘 2）も解消する。
