# T5 変更のレビュー: `InputText.Normalize`

## 使った判断の基準
スキル D の「作業規模に応じた適用の軽重」でこの作業は「レビュー（依頼されたとき）」に当たる。必ず読むものとして quality-gates.md の「七箇条をレビューの観点にする」、refactoring.md の「コードの臭い」「臭い → 技法の対応表」を読んだ。テストを含む変更なので、必要なら読むものの testing.md も読んだ。指摘は refactoring.md の書式（`<場所>: <臭いの名前>(<症状の根拠>)→ <技法>`）で書き、七箇条の箇条名を付ける。七箇条に当たらないものは「七箇条の外」とし、その性質の名前（正しさ／実行環境の差など）を付ける。

## 変更の意図（一言で）
利用者が入力した数値の文字列の前後の空白を除き、全角の数字を半角にして、「３０」のような入力を解釈できるようにする。

## 置いた仮定
- 呼び出し側は、`Normalize` の結果を `int.TryParse` などで解釈する（呼び出し側のコードは差分に入っていない）。
- Web 版は、Blazor WebAssembly の既定の設定（ブラウザーの上の .NET ランタイム。グローバリゼーションはブラウザー向けの限られた機能）で動く。
- 私はこの環境でブラウザーの上で動かせなかった。下の指摘 1 は、ブラウザーの .NET の既知の制約から判断したものなので、取り込む前に本物の実行環境で確かめる必要がある。

---

## 指摘

### 1.【重大・七箇条の外: 正しさ（実行環境の差）】ブラウザーの .NET では `Normalize(NormalizationForm.FormKC)` が動かないおそれが高い
- 場所: `InputText.Normalize`（Web 版からの呼び出し）
- 問題: ブラウザー（WebAssembly）の上の .NET は、Unicode の正規化（FormC/FormD/FormKC/FormKD）を完全には備えていない。ASCII 以外の文字を含む文字列を正規化しようとすると `PlatformNotSupportedException` が投げられる（インバリアント グローバリゼーションのモードでも、ASCII 以外の文字は同じく正規化できない）。そのため、全角の「３０」を受け付けるという目的の入力でこそ、Web 版は例外で落ちる。
  - テストは PC の .NET 10（ICU や OS の正規化が使える環境）で動くので、Green でもこの差を保証しない。作者の「全テストが Green」は、デスクトップ版の正しさの証拠にはなるが、Web 版の正しさの証拠にはならない。
  - この変更の動機は「全角の３０を受け付けること」なので、ASCII だけの入力（" 16 "）で動いても、Web 版では目的を果たしていない。
- 取り込む前にすべきこと:
  1. Web 版を実際にブラウザーで動かし（`dotnet run` または `dotnet publish` した発行物）、カスタムの入力に「３０」「 16 」「１６」を入れて、例外にならず 30・16・16 として解釈されるかを確かめる。Release の発行物（トリミング、グローバリゼーションの設定）でも確かめる。
  2. 例外になったら、次のどちらかにする（ユーザーの判断が要る点。下の指摘 2 と合わせて決める）。
     - 案 A（引き算。推奨）: 目的が全角の数字だけなら、NFKC を使わない。全角の数字（U+FF10〜U+FF19）を半角に写すだけの変換（`c - '０' + '0'`）を `Trim` と組み合わせて `InputText` に書く。どのランタイムでも同じに動くので、実装が 1 か所で済み、Web 版もデスクトップ版も同じテストで守れる。
     - 案 B: NFKC を保つ。Web 版だけは同じ変換をブラウザーの JavaScript の `trim().normalize("NFKC")` で行い、C# の `InputText.Normalize` は Web 版では呼ばない。この場合、同じ意図の変換が C# と JS の 2 か所になる（Once And Only Once の例外）ので、その Why をコメントと設計書に残し、両者の変換結果が揃っていることを確かめるテスト（またはブラウザーでの確認の手順）を用意する。
  3. 例外が起きうる経路には、入力を解釈できないときと同じ扱い（エラー表示）になっているかを確かめる。少なくとも、未処理の例外でアプリ全体が止まる（Blazor のエラー表示の帯が出る）状態を取り込まない。

### 2.【中・七箇条の外: 整合（要求との食い違い）／引き算】NFKC は要求より広い変換をする
- 場所: `InputText.Normalize`: 疑わしき一般化（要求は「全角の数字を受け付ける」だが、NFKC は互換文字すべてを写す）→ YAGNI・引き算で、変換を要求の範囲に絞るかを判断する
- 問題: NFKC は全角の数字だけでなく、「①」→「1」、「²」→「2」、「½」→「1⁄2」、「㉚」→「30」、全角のマイナス「－」→「-」なども写す。その結果、「①６」が 16 として受け付けられるなど、仕様に書かれていない入力が通る。これが望ましいかどうかは仕様から決まらない。また、指摘 1 の制約を持ち込む原因がこの広さである。
- 取り込む前にすべきこと: 受け付ける入力の範囲をユーザー（仕様）と合意する。全角の数字と前後の空白だけでよければ、指摘 1 の案 A にする。NFKC の範囲を受け付けると決めるなら、その決定と理由（Why）を記録し、上の例（丸数字など）をテストの表に入れる。

### 3.【小・Testable】テストの表が目的の境界とエッジケースを押さえていない
- 場所: `InputTextTests`
- 問題: 代表値（「３０」「１６」）と空白（" 16 "）しかない。次の行がない。
  - 全角の空白（U+3000）で囲まれた入力「　３０　」（日本語の IME で入れやすい。`Trim` が除くことを確かめる番人）
  - 全角と半角の混在「3０」
  - 空文字列・空白だけ（" "、"　"）→ 空文字列
  - 数字以外の全角文字（例:「ａ」）をどう扱うか（指摘 2 の合意の結果で期待値が決まる）
  - 変換の対象でない文字列がそのまま返ること（例:「abc」→「abc」）
- 取り込む前にすべきこと: 上の行を表に足す。指摘 2 で範囲を決めてから期待値を確定する。案 A にする場合は、全角の「０」と「９」（範囲の両端）を境界値として入れる。

### 4.【小・Testable（一テスト一関心）／的確な名前】一つのテストに二つの関心が混ざっている
- 場所: `NormalizesFullWidthDigitsAndTrims`: 名前が「And」で二つの仕様をつないでいる（全角の数字の変換と、空白の除去）
- 問題: " 16 " の行は全角の変換を検証せず、「３０」の行は空白の除去を検証しない。失敗したときに、どちらの仕様が破れたのかをテスト名で語れない。
- 取り込む前にすべきこと: `ConvertsFullWidthDigitsToHalfWidth` と `TrimsSurroundingWhitespace` のように、仕様の文ごとにテストを分ける。

### 5.【小・Testable】「Red を見た」の中身が確かめられない
- 場所: 作者の説明
- 問題: `InputText` がまだない時点のコンパイルエラーも Red だが、それはテストの配線を確かめただけで、変換の仕様が検証されていることは示さない。また、指摘 1 のとおり、PC の Green はブラウザーでの動作を示さない。
- 取り込む前にすべきこと: `Normalize` をわざと `text.Trim()` だけに壊したとき、全角の行が失敗することを確かめる（壊した変更は戻す）。報告には「どの環境で、何を確かめたか」（PC の dotnet test、ブラウザーでの手動の確認）を分けて書いてもらう。

### 6.【小・七箇条の外: 正しさ】`Trim` を `Normalize` の前にしているので、正規化で生まれた空白が残りうる
- 場所: `text.Trim().Normalize(...)` の順序
- 問題: NFKC は一部の文字を空白を含む並びに写す。先に `Trim` するので、正規化の後に先頭や末尾に空白が出ても残る。よく入力される全角の空白（U+3000）やノーブレークスペースは `Trim` で先に消えるので、実害は小さい。
- 取り込む前にすべきこと: NFKC を保つ（案 B）なら、順序を `Normalize(...).Trim()` にすると考えなくてよくなる。案 A なら、この指摘は消える。

## 良い点
- 変換を `Presentation` の 1 か所に置き、Web 版とデスクトップ版が同じ変換を使う形にしている（Once And Only Once）。
- 依存のない純粋な静的関数なので、テストがしやすい（Testable）。

## 結論
このままでは取り込まない。指摘 1（Web 版での実行環境の差）は、変更の目的そのものを Web 版で果たせないおそれがあるので、ブラウザーで確かめてから取り込むべきである。私の推奨は、受け付ける範囲を「前後の空白と全角の数字」に絞ること（指摘 2）、NFKC の代わりに全角の数字だけを写す変換にすること（指摘 1 の案 A）、テストを仕様の文ごとに分けて境界の行を足すこと（指摘 3、4）である。

## ユーザーの判断が要る点
- 受け付ける入力の範囲（全角の数字だけか、NFKC の互換文字すべてか。丸数字などを受け付けるか）。
- NFKC を保つ場合に、Web 版だけ JavaScript で変換する二重の実装を受け入れるか。

## 検証できなかったこと
- ブラウザー（WebAssembly）の上で `Normalize(FormKC)` が実際に投げるかは、この環境で実行していない。既知の制約からの判断である。取り込む前の確認の手順は指摘 1 に書いた。
