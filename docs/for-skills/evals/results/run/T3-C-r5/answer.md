# T3: `BoardCursor` のクラス設計のレビュー

## 読んだ判断基準

課題は「設計書のレビュー」なので、スキル C の表の「設計の相談」に当たる。必ず読むものとして modeling.md と object-design.md を読んだ。必要なら読むものとして、設計書のレビューなので quality-gates.md の「七箇条をレビューの観点にする」を読んだ。指摘の中心がガード節の有無なので、同じファイルの「契約とガード節」も読んだ。

## 意図

`BoardCursor` の意図は「キーボードで選んでいるマスを、盤面の中に保つ」である。`Move` の説明（「盤面の端では止まる」）から、このクラスには「`Position` は常に盤面の中にある」という不変条件がある、と読める。

## 置いた仮定

- `CellPosition` は行と列を持つ値型で、既定値（0, 0）はどの盤面でも中にある。
- `Board.Contains(CellPosition)` は、位置が盤面の中なら true を返す。
- `Nullable` が有効で、`board` の null はコンパイラーの警告で防げる（そのため null のガード節は指摘しない）。
- 3 つの版は、難易度を変えたときやカスタムの盤面にしたときに、大きさの違う `Board` を同じ `BoardCursor` に渡すことがありうる。

## 指摘

### 指摘 1（必須）: `MoveTo` に前提条件のガード節がない

`BoardCursor.MoveTo`: 前提条件が明示されていない（盤面の中の位置しか渡されないことを、呼ぶ側の約束だけに頼っていて、コードからは読み取れない）→ ガード節を置く

- 観点: 七箇条の「Testable」（前提条件が明示されているか）と、七箇条の外の「正しさ」（例外の境界）。
- 根拠:
  - `BoardCursor` は、3 つのアプリが共有するライブラリの公開の型である。呼ぶ側は 3 つあり、どの版も盤面の中の位置しか渡さないということは、このクラスの中からは保証できない。設計書の「呼ぶ側が盤面の中の位置しか渡さない」は、呼ぶ側への期待（前提条件）であって、確かめた事実ではない。
  - 破られたときの影響は大きい。盤面の外の位置が入ると、不変条件「`Position` は盤面の中」が黙って崩れる。その後は `Move` の端の判定（`board.Contains`）が意味をなさなくなり、カーソルが盤面の外に居続けるか、画面に何も選ばれていないように見える。しかも例外にならないので、原因の場所（`MoveTo` を呼んだ側）から離れた所で症状が出る。
  - ありうる経路: 難易度を上級から初級に変えた直後に、前の盤面の大きさで計算した位置を渡す（画面の再配置が遅れたとき）。デスクトップ版でウィンドウの大きさを変えている途中に、押された座標をマスの位置に直す計算の端数で、端から 1 つ外の位置になる。
- 「引き算」の当てはめについて: 引き算で削るのは、頼まれていない抽象・パターン・将来への備え（問題文にない制約）である。公開のメソッドが持つ前提条件を入口で確かめることは、将来への備えではない。いまある契約を、コードに書き出すことである。ガード節は 1 行で、本処理は一本道のままである。そのため、この見送りに引き算の理由は当たらない。
- 直し方: 言語標準の例外で、入口で打ち切る。

```csharp
/// マウスで選んだマスなど、指定の位置へ動かす。
/// 前提条件: position は board の中にある。
public void MoveTo(CellPosition position, Board board)
{
    if (!board.Contains(position))
        throw new ArgumentOutOfRangeException(nameof(position), position, "盤面の外の位置には動かせません。");
    Position = position;
}
```

- 単体テストで確かめること: 盤面の中の位置に動くこと、盤面の外の位置（負の行・列、行数・列数と同じ値）で `ArgumentOutOfRangeException` になり、`Position` が変わらないこと。
- 捨てた案: 盤面の外の位置を端に寄せる（クランプする）、または黙って無視する。どちらも呼ぶ側の不具合（押された座標の変換の誤り）を隠す。エラーを黙って捨てないという方針に反するので、例外にする。

### 指摘 2: `MoveTo` の引数 `board` が使われていない

`BoardCursor.MoveTo`: 使われない引数（シグネチャーに `board` があるのに、本体は `Position = position` だけで参照しない）→ 指摘 1 のガード節で使う

- 観点: 七箇条の「意図を表現」（意図以外の記述であるノイズ）。
- 根拠: 使わない引数は、読む人に「盤面に合わせて何かしているはずだ」と誤解させる。今の設計では、`board` は盤面の中かを確かめるために渡されているとしか読めないのに、確かめていない。宣言と実装が食い違っている。
- 直し方: 指摘 1 を入れれば、`board` はガード節で使われ、この指摘も解消する。仮に指摘 1 を入れないなら、引数を消すのが筋である。ただし、その場合は前提条件がシグネチャーからも消えるので、指摘 1 を入れる方を勧める。

### 指摘 3（確認）: 盤面が替わったときの `Position` の扱いが設計書に書かれていない

`BoardCursor`: 不変条件の持ち主が曖昧（カーソルは盤面を持たず、呼ぶたびに渡される。そのため、小さい盤面に替わると、それまでの `Position` が盤面の外に残りうる）→ 盤面が替わったときの手順を契約として書く

- 観点: 七箇条の外の「整合」（難易度の変更という仕様と、不変条件が両立するか）。
- 根拠: 上級（30 × 16）の右下にカーソルがある状態で初級（9 × 9）に替えると、`MoveTo` を経ずに `Position` が盤面の外になる。指摘 1 のガード節は、この経路を防げない。
- 直し方（どちらかを設計書に書く）:
  - 案 A: 新しいゲーム（盤面）ごとに `BoardCursor` を作り直す、と決めて設計書に書く。クラスを変えずに済むので、まずはこちらを勧める。
  - 案 B: 盤面をコンストラクター `BoardCursor(Board board)` で受け取って持ち、`Move` と `MoveTo` から `board` の引数を除く。不変条件をコンストラクターで成り立たせられるので、契約はいちばん明確になる。ただし、3 つの版の呼び方が変わる公開の型の変更なので、版ごとの使い方を確かめてから決める。
- この点は、3 つの版が盤面を替えるときに `BoardCursor` をどう扱っているかによる。設計書にそれが書かれていないので、確認事項とした。

## まとめ

設計書の「呼ぶ側が盤面の中の位置しか渡さないので、ガード節は置かない（引き算）」という判断には同意しない。共有ライブラリの公開のメソッドで、3 つの呼ぶ側が同じ前提を守ることに頼っている。そのうえ、破られたときは不変条件が黙って崩れる。引き算で削るのは頼まれていない備えであり、いまある前提条件を確かめる 1 行のガード節はそれに当たらない。`board.Contains` で確かめて `ArgumentOutOfRangeException` を投げ、使われていない引数 `board` もそれで生かす。あわせて、盤面が替わったときに `Position` をどうするか（作り直すのか、盤面を持たせるのか）を設計書に書く。
