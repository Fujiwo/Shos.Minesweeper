# T3 クラス設計のレビュー: `BoardCursor.MoveTo`

## 結論
指摘あり（3 件）。中心は、指摘 1 の「公開の型の引数に、ガード節を置かない」ことである。設計書にある引き算の理由は、この型には当てはまらない。

## 仮定
- `Board.Contains(CellPosition)` は、位置が盤面の中なら true を返す（`Move` の説明にあるもの）。
- `Position` は、呼ぶ側がそのまま盤面の添字に使う（マスを開く、旗を立てる、描画でハイライトする）。
- 盤面の外の位置を渡すのは、呼ぶ側の誤り（プログラムの不具合）であり、利用者の操作で起きる正常な場合ではない。

---

## 指摘 1（正しさ・契約）: 公開の型の `MoveTo` にガード節がない

**問題**
- 「呼ぶ側が盤面の中の位置しか渡さない」は、呼ぶ側の実装への期待にすぎず、型で保証されていない。`BoardCursor` は 3 つのアプリが使う共有ライブラリの公開の型なので、呼ぶ側は 1 つではない。Web 版（押されたマス）、デスクトップ版（クリック、ウィンドウの大きさの変化）、コンソール版（端末の座標からの変換）と、位置の出どころがそれぞれ違い、座標の換算の誤り（1 始まり/0 始まり、行と列の取り違え、枠の分のずれ）が起きやすい。
- 盤面の外の位置を受け入れると、不正な状態（`Position` が盤面の外）がカーソルに残る。失敗が表に出るのは、その後に `Position` でマスを開く・描く時点（添字の範囲外の例外や、何も光らない表示）で、原因の `MoveTo` の呼び出しから離れる。原因を追いにくい。
- 同じクラスの `Move` は「盤面の端では止まる」で、カーソルは常に盤面の中という不変条件を守っている。`MoveTo` だけがその不変条件を破れるので、クラスの中で契約が食い違う。
- 引き算（要らないものを置かない）は、内部の、呼ぶ側を 1 か所に限れるコードでは妥当だが、公開の境界の引数の検査は「要らないもの」ではない。確かめるのは `board.Contains` の 1 行で、省いて得るものがほとんどない。

**直し方**
公開の境界でガード節を置き、盤面の外なら例外で知らせる（呼ぶ側の誤りなので、黙って丸めない）。

```csharp
/// マウスで選んだマスなど、指定の位置へ動かす。
/// position が盤面の外なら ArgumentOutOfRangeException。
public void MoveTo(CellPosition position, Board board)
{
    ArgumentNullException.ThrowIfNull(board);
    if (!board.Contains(position))
        throw new ArgumentOutOfRangeException(nameof(position), position, "盤面の外の位置です。");
    Position = position;
}
```

- 単体テストを足す: 盤面の中なら動く／盤面の外（負の値、幅・高さちょうど）なら例外になり、`Position` が変わらない。
- 設計書の説明を「盤面の外の位置は呼ぶ側の誤りとして例外にする。カーソルは常に盤面の中にある（不変条件）」に書き換える。
- 別案として「盤面の外なら何もしない（無視）」もあるが、不具合を隠すので採らない。利用者の操作で盤面の外が正常に起こりうる場合（例: 盤面の余白のクリック）は、呼ぶ側がマスへの換算の段階で弾くか、`bool TryMoveTo(...)` を別に設ける。

## 指摘 2（引き算・整合）: 使わない引数 `board`

**問題**
今の `MoveTo` は `board` を受け取るのに使っていない。読み手は「盤面で何か確かめている」と誤解するか、「なぜ要るのか」で迷う。設計書の説明（ガード節を置かない）とシグネチャが食い違っている。

**直し方**
指摘 1 のとおりガード節で `board` を使えば、引数の意味が生まれて解消する。仮にガード節を置かない判断を続けるなら、`board` を引数から外す（ただし指摘 1 の理由から、ガード節を置く方を勧める）。

## 指摘 3（正しさ）: 盤面が替わったときに、カーソルが盤面の外に残りうる

**問題**
`Board` を呼び出しごとに渡す形なので、カーソルは今の盤面の大きさを知らない。難易度を上級（30×16）から初級（9×9）に替えたり、カスタムで小さくしたりすると、前の `Position`（例: (20, 10)）が新しい盤面の外に残る。この状態で `Move` を呼ぶと、`board.Contains` による「端で止まる」判定が、外にいる前提を扱えず、カーソルが盤面に戻れない（どの方向も「外」になって止まる）か、外をさまよう。`MoveTo` のガード節だけでは防げない。

**直し方**（どちらか）
- 新しいゲーム・盤面の替わり目で呼ぶ `Reset()`（`Position` を (0, 0) など、決めた初期位置に戻す）を足し、`GameSession` の新しいゲームの開始で必ず呼ぶ。
- あるいは、カーソルを盤面ごとに作り直す（`new BoardCursor(board)` とし、コンストラクターで `Board` か寸法を受け取って保持する。こうすると `Move`/`MoveTo` の `board` 引数も要らなくなり、指摘 2 も形の上で消える）。

3 つの版で使い方をそろえやすく、呼び忘れが起きないので、後者（盤面ごとに作り直す）を勧める。その場合も、`MoveTo` の範囲の検査（指摘 1）は、保持した盤面で行う。
