# T3: `BoardCursor` のクラス設計のレビュー

## 使った判断の基準
スキル B の SKILL.md の「作業規模に応じた適用の軽重」で、この課題は「レビュー（ユーザーから依頼されたとき）」の行に当たる。必ず読むものとして、quality-gates.md の「七箇条をレビューの観点にする」と refactoring.md の「コードの臭い」「臭い → 技法の対応表」を読んだ。さらに、指摘が前提条件とガード節に関わるので、quality-gates.md の「契約とガード節」も読んだ。インターフェイスなどを新しく作る設計ではないので、simplicity.md は読んでいない。

## レビューの対象の意図（一言で）
`BoardCursor` は「キーボードで選んでいるマスを、盤面の中に保つ」ための型で、3 つの版が共有する公開の型である。

## 置いた仮定
- `Board.Contains(CellPosition)` は、その位置が盤面の中なら true を返す（設計書のコメントから読み取った）。
- `CellPosition` は値の型で、`BoardCursor` の `Position` の初期値は `(0, 0)` である。
- 難易度（カスタムを含む）を変えると、盤面の大きさが変わる。

## 指摘

### 指摘 1（重要）: `MoveTo` の前提条件がコードに書かれていない。この場合の引き算は当たらない
`BoardCursor.MoveTo`: 臭いの表の名前には当てはまらない（症状: 公開の型の公開メソッドの前提条件「位置は盤面の中」が、呼ぶ側の約束としてしか書かれておらず、コードには表れていない）→ 入口にガード節を置いて前提条件を明示する（quality-gates.md の「ガード節」）

- **箇条**: Testable（前提条件が明示されているか）、意図を表現。
- **根拠**:
  - ガード節は、スキルの「公開メソッド・コンストラクタが引数や状態に前提を持つとき」に当たる。`BoardCursor` は、3 つのアプリが使う共有ライブラリの公開の型である。「呼ぶ側が盤面の中しか渡さない」は、今の呼び出し元（画面で押されたマス）についての観察にすぎない。契約ではない。呼び出し元は 3 つの版に分かれていて、これからも増える（例: コンソール版で数字の座標を入力して動かす、盤面の外にある余白のクリック、テスト）。
  - 引き算（Think Simple）で削る対象は、頼まれていない抽象、パターン、将来への備えである。前提条件の検査はそのどれでもなく、契約をコードに書くこと、つまり説明責任の実行である。1 行の検査を省いても、読むものは減らない。約束がコードから消えるだけである。したがって、引き算の理由にはならない。
  - 起こりうる誤り: 呼び出し元の誤りで盤面の外の `Position` が入ると、その後の `Move` は `board.Contains` による端の判定を前提にしているので、どう振る舞うかが決まらない（外から中へ戻れるか、外に留まるか）。そのうえ、描画・読み上げ・開く操作で盤面の外の添字を使ったところで初めて落ちる。誤りが見つかるまでの時間が長くなり、原因の場所からも遠くなる。
- **Once And Only Once / ルールの統一の面から**: 同じクラスの `Move` は `board.Contains` で盤面の中に保つのに、`MoveTo` は保たない。そのため、「カーソルは盤面の中にある」という約束を守る場所が、クラスの中と呼び出し元の 3 つの版とに散らばっている。
- **意図を表現の面から**: `MoveTo(CellPosition position, Board board)` は `board` を受け取るのに使っていない。この使われない引数はノイズで、読む人に「盤面で何か確かめているはずだ」という誤った期待を持たせる。ガード節を置けば、`board` に意味ができる。

**直し方**（言語標準の検証の API を使い、独自の仕組みは作らない）:

```csharp
/// マウスで選んだマスなど、指定の位置へ動かす。
/// 前提条件: position は board の中にあること（外なら ArgumentOutOfRangeException）。
public void MoveTo(CellPosition position, Board board)
{
    ArgumentNullException.ThrowIfNull(board);
    if (!board.Contains(position))
        throw new ArgumentOutOfRangeException(nameof(position), position, "盤面の外の位置には動かせない。");
    Position = position;
}
```

- 盤面の外のときに、黙って無視したり、端に寄せたりはしない。`Move` の「端で止まる」は仕様の振る舞いだが、`MoveTo` に外の位置が来るのは呼び出し元の誤りだからである。黙って直すと、誤りを握りつぶすことになる。
- 設計書の説明は、次のように書き換える。「`MoveTo` の前提条件は、位置が盤面の中にあることである。入口のガード節で確かめ、破れていたら `ArgumentOutOfRangeException` を投げる。通常の呼び出し元（画面で押されたマス）はこの前提を満たすので、例外になるのは呼び出し元の誤りのときだけである。」
- `Move` にも、`ArgumentNullException.ThrowIfNull(board)` を置く。
- テストケース（xUnit）:
  - 盤面の中の位置を渡すと、`Position` がその位置になる。
  - 四隅（`(0,0)` と `(幅-1, 高さ-1)` など）を渡すと動く（境界の中）。
  - `x = -1`、`x = 幅`、`y = -1`、`y = 高さ` のそれぞれで `ArgumentOutOfRangeException` になり、`Position` は変わらない（境界の外）。
  - `board` が null なら `ArgumentNullException` になる。

### 指摘 2（中）: 「カーソルは盤面の中にある」は不変条件なのに、盤面が呼ぶたびに引数で渡されるので、クラスが保てない
`BoardCursor`（`Position` と、メソッドの引数の `Board`）: 臭いの表の名前には当てはまらない（症状: `Position` はどの盤面の中かに依存する状態なのに、盤面は呼ぶたびに引数で渡される。盤面が差し替わったとき（難易度の変更、カスタムの小さな盤面）に、前の盤面での `Position` が新しい盤面の外に残りうる。ガード節が確かめられるのはメソッドの入口だけで、盤面の差し替えの後に `Position` が外に残るのは防げない）→ 不変条件をコンストラクタで成り立たせる（quality-gates.md の「契約とガード節」の不変条件）

- **箇条**: Testable（不変条件が明示されているか）、単一責務（盤面の中に保つ仕事が、カーソルと呼び出し元に漏れている）。
- **起こりうる誤り**: 上級（30×16）で `(29, 15)` にいた後に初級（9×9）へ変えると、`Position` が `(29, 15)` のまま残る。次の描画や「開く」の操作で、盤面の外を指す。
- **直し方（案。ユーザーの判断が要る）**:
  - 案 A（推奨）: カーソルを、盤面（または盤面の大きさ）と一緒に作る。`new BoardCursor(board)` の形にして、不変条件をコンストラクタで成り立たせる。新しいゲームや難易度の変更ではカーソルを作り直すので、古い位置は残らない。`Move(Direction)` と `MoveTo(CellPosition)` から `Board` の引数がなくなり、引数も減る。カーソルが要るのは大きさ（`Contains`）だけなので、`Board` 全体ではなく、盤面の寸法の型に依存させるほうが結合は弱い。
  - 案 B（変更が小さい）: 今の形のまま、`Reset()`（`Position = (0,0)`）を足して、新しいゲームのたびに呼ぶことを契約として設計書に書く。ただし、呼び忘れを型では防げないので、案 A より弱い。
- どちらの案もシグネチャを変えるので、公開の API の変更になる。3 つの版の呼び出し元に影響するため、採るかどうかはユーザーが決める。指摘 1 のガード節は、どちらの案とも両立する（案 A なら `MoveTo` の中で自分の盤面を使って確かめる）。

### 指摘 3（軽）: `Move` の `direction` の前提条件
`BoardCursor.Move`: 臭いの表の名前には当てはまらない（症状: `Direction` が C# の enum なら、定義にない値（`(Direction)99`）も渡せる。その場合の振る舞いが書かれていない）→ switch の既定の枝で `ArgumentOutOfRangeException`（または `UnreachableException`）を投げ、設計書に一言添える。
- **箇条**: Testable。大きな問題ではないので、実装のときに扱えばよい。

## 指摘がない点
- `Position { get; private set; }` の書き込みを型の中に閉じているのは良い。
- `Move` の「端で止まる」を `board.Contains` で判定するのは、端の判定を盤面に任せていて（Expert）、良い。
- 名前（`BoardCursor`、`Move`、`MoveTo`、`Position`）は仕事を過不足なく表している。

## ユーザーの判断が要る点
1. 指摘 1: 盤面の外の位置を例外で拒むこと（黙って無視しないこと）。推奨は例外で拒むことである。
2. 指摘 2: 公開の API を変えるかどうか（案 A: 盤面と一緒に作る、案 B: `Reset` を足す、または今の形のまま）。
