# T3 のレビュー: `BoardCursor`

作業の種類は「設計の相談（設計書のレビュー）」として扱った。読んだもの: SKILL.md、modeling.md、object-design.md、quality-gates.md の「七箇条をレビューの観点にする」。この設計書の論点はガード節を省くかどうかなので、quality-gates.md の「契約とガード節」も読んだ。refactoring.md の書式と臭いの一覧も確かめた。

## 対象の意図（一言で）

`BoardCursor` は、キーボードで選んでいるマスを、盤面の中に保ったまま動かす。

意図の中に「盤面の中に保つ」が入っている。これはこのクラスの不変条件である。`Move` のコメント（「盤面の端では止まる」）も、そう読むことを前提にしている。

## 結論

指摘は 3 件ある。このうち 1 件目は、設計書の説明の判断（「ガード節は置かない（引き算）」）を改めるよう求めるものである。

---

## 指摘 1（必ず直す）: `MoveTo` に前提条件がなく、不変条件を守れない

- **書式**: `BoardCursor.MoveTo`: 前提条件が明示されていない（公開の型の公開メソッドなのに、`position` が盤面の中であることを型でも検査でも表していない。そのため `Position` が盤面の外になりうる）→ 入口にガード節を置く
- **箇条**: Testable（前提条件が明示されているか）。七箇条の外では「正しさ」の問題でもある（不変条件が崩れる）。
- **根拠**:
  1. 「呼ぶ側が盤面の中の位置しか渡さない」は、今の呼び出し元がそう振る舞っているというだけである。`BoardCursor` の契約として保証されているわけではない。`Presentation` は 3 つのアプリ（Web、デスクトップ、コンソール）が共有する公開のライブラリで、呼び出し元は少なくとも 3 つとテストである。ある版の座標の変換に誤りがあれば（端のマス、余白、拡大率の違い、1 つずれた変換など）、盤面の外の位置がそのまま入る。
  2. 盤面の外に出た後の症状は、原因から遠くで起こる。`Move` は「次の位置が `board.Contains` なら動く」ので、外にいるカーソルは向きによって動いたり止まったりする。`Position` を添字に使う描画や開く操作では、範囲外の例外や別のマスへの操作として表れる。エラーの滞在時間が長くなり、どこで壊れたかを追えない。ガード節の効能 2（バグの早期検知）が失われる。
  3. 引き算（Think Simple）の対象は、頼まれていない抽象、パターン、将来への備えである。公開メソッドの入口で前提条件を確かめるのは、それには当たらない。クラスの意図（「盤面の中に保つ」）の一部であり、足さないと、ピュアなモデルの条件の「意図が書き尽くされていること」を満たさない。1 行のガード節で読む量はほとんど増えない。一方で、契約が型の宣言から読み取れるようになる。
- **直し方**:

```csharp
/// マウスで選んだマスなど、指定の位置へ動かす。
/// 前提条件: position は board の中である。
public void MoveTo(CellPosition position, Board board)
{
    ArgumentNullException.ThrowIfNull(board);
    if (!board.Contains(position))
        throw new ArgumentOutOfRangeException(nameof(position), position, "盤面の外の位置には動かせない。");
    Position = position;
}
```

  - 盤面の外の位置を渡すのは呼び出し元のバグである。そのため、例外で打ち切る。黙って端に寄せる（clamp）ことや、無視することはしない。寄せると、呼び出し元の座標の変換の誤りが隠れてしまう。
  - 検査には、言語の標準の API（`ArgumentNullException.ThrowIfNull`、`ArgumentOutOfRangeException`）と、既にある `board.Contains` を使う。独自の検証の仕組みは作らない。`Move` と同じ `Contains` で判定するので、「盤面の中」の定義が 1 か所にまとまる（Once And Only Once）。
  - 単体テストを 2 件足す: 盤面の外の位置を渡すと `ArgumentOutOfRangeException` になり、`Position` は変わらない。端のマス（四隅）には動ける。
  - 設計書の説明は、「呼ぶ側は盤面の中の位置を渡す。それを前提条件としてガード節で確かめる」に書き換える。

## 指摘 2: `MoveTo` の引数 `board` を使っていない

- **書式**: `BoardCursor.MoveTo(CellPosition, Board)`: 使われない引数（シグネチャは盤面に依存すると言っているのに、本体は `board` を使わない。読み手は何に使うのかを探すことになる）→ 指摘 1 のガード節で使う
- **箇条**: 意図を表現（シグネチャと本体が同じ意図を表していない）。
- **根拠**: 引数に `board` があるのは、確かめる前提があったからだと読める。今の設計では、宣言と実装が食い違っている。
- **直し方**: 指摘 1 を入れると解消する。逆に `board` を消す案もあるが、盤面の中かを確かめる手段がなくなり、指摘 1 が直せなくなる。そのため採らない。

## 指摘 3（確認事項）: 盤面が替わったときに不変条件を保つ役割が決まっていない

- **書式**: `BoardCursor` と盤面の関係: 七箇条の外、「正しさ」（カーソルは盤面を持たず、呼び出しのたびに受け取る。そのため、新しいゲームで盤面が小さくなると、`Position` が新しい盤面の外に残りうる。例: 上級 30×16 で (29, 15) にいた後に初級 9×9 に替える）→ 盤面が替わるときの扱いを設計書に書く
- **根拠**: 指摘 1 のガード節は `MoveTo` の入口を守る。しかし、盤面が替わったことで `Position` が外に残る場合は防げない。その後の `Move` の振る舞いは、指摘 1 の根拠 2 と同じく定まらない。この部分だけでは、新しいゲームを始めるときにカーソルを作り直すのか、位置を戻すのかが読み取れない。
- **直し方（どちらか。仮定によって選ぶ）**:
  - (a) 新しいゲームごとに `BoardCursor` を作り直すと設計書に書く（初期値の `Position` は (0, 0) で、どの難易度でも盤面の中になる）。新しい型もメソッドも足さずに済むので、こちらを勧める。
  - (b) 1 つのカーソルを使い続けるなら、呼び出し元が新しいゲームで `MoveTo(原点, 新しい盤面)` を呼ぶと決める。さらに、`Move` の入口でも `board.Contains(Position)` を確かめ、外なら `InvalidOperationException` にする。
  - どちらにしても、「`Position` はいつも最後に渡された盤面の中にある」ことを、クラスの不変条件として設計書に書く。

---

## 指摘しなかった点（引き算）

- 盤面を `BoardCursor` のフィールドに持たせる形（コンストラクタで受け取る）には変えない。今の「呼び出しのたびに渡す」形で不変条件は守れる（指摘 1、3）。変えるほどの具体的な理由は、この部分からは見えない。
- 盤面の外の位置を表す専用の型（「盤面の中の位置」型など）は足さない。使われるのはここと `Move` だけで、ガード節の 1 行で足りる。

## 置いた仮定

- `CellPosition` は値型（構造体）で、既定値は (0, 0) である。
- `Board.Contains(CellPosition)` は、位置が盤面の中なら true を返す。
- 盤面の大きさは、どの難易度でも 1×1 以上である。
- `Position` は、盤面の添字として描画や操作に使われる。
- 新しいゲームを始めるときにカーソルをどう扱うかは、与えられた部分には書かれていない（指摘 3 はこのため確認事項とした）。
