# T3 クラス設計のレビュー: `BoardCursor`

## 適用したスキルの範囲

作業の種類は「設計の相談（設計書のレビュー）」とした。SKILL.md の表に従い、object-design.md（必ず読む）と、quality-gates.md の「七箇条をレビューの観点にする」（設計書のレビューなので）を読んだ。指摘の中心が前提条件なので、quality-gates.md の「契約とガード節」も読み、指摘の書式のために refactoring.md の「コードの臭い」「臭い → 技法の対応表」を読んだ。

## 対象の意図（ひとこと）

`BoardCursor` は「キーボードで選んでいるマスを、盤面の中に保つ」型である。3 つの版が共有する公開の型なので、その約束（常に盤面の中を指す）は、この型が自分で守るべき不変条件になる。

## 結論

指摘がある。設計書の「呼ぶ側が盤面の中の位置しか渡さないので、ガード節は置かない（引き算）」は、引き算の誤用である。

## 指摘

### 指摘 1（主）: `MoveTo` に前提条件のガード節がない

- `BoardCursor.MoveTo`: 前提条件が明示されていない（盤面の中の位置しか来ないという前提を、呼ぶ側の 3 つのアプリの振る舞いに頼っている。公開の型なのに、コードからは前提が読み取れず、破られても黙って盤面の外を指すカーソルができる）→ 入口にガード節を置き、`board.Contains` で検証して `ArgumentOutOfRangeException` を投げる
- 箇条: **Testable**（「前提条件が明示されているか」）。あわせて七箇条の外の **正しさ**（例外の境界）
- 理由:
  - 引き算（Think Simple）で削るのは、頼まれていない抽象・パターン・将来への備えである。公開メソッドの前提条件の検証は「備え」ではなく契約の宣言であり、削る対象ではない（quality-gates.md の「ガード節」: 公開メソッドが引数に前提を持つときに置く）。
  - 「呼ぶ側が中の位置しか渡さない」は、今の 3 つの呼び出し元についての観察で、`BoardCursor` の契約ではない。共有ライブラリの公開の型では、呼び出し元は版ごとに別の人・別の時期に書かれる（例: デスクトップ版で座標からマスを求める計算のずれ、コンソール版のマウス対応を足したとき、難易度を変えた直後に古い盤面の位置が届くとき）。そのとき破れは `MoveTo` では検知されず、後で `Move` や描画・開放の側で別の症状として現れる。ガード節は、この滞在時間をゼロにする。
  - `Move` は `board.Contains` で盤面の中を保つのに、`MoveTo` は保たない。同じ不変条件（カーソルは盤面の中）を、片方の入口だけが守っている。
- 直し方:

```csharp
/// マウスで選んだマスなど、指定の位置へ動かす。
/// 前提条件: position は board の中にある。
public void MoveTo(CellPosition position, Board board)
{
    ArgumentNullException.ThrowIfNull(board);
    if (!board.Contains(position))
        throw new ArgumentOutOfRangeException(nameof(position), position, "盤面の外の位置です。");
    Position = position;
}
```

- 捨てた案:
  - 盤面の中に丸める（clamp）: 呼び出し元の誤りを黙って別のマスに置き換え、バグを隠す。前提の破れは例外で知らせる方がよい。
  - 各アプリの呼び出し元で確かめる: 同じ検証が 3 か所に散る（Once And Only Once に反し、変更の分散の芽になる）。検証は、盤面の中を保つ責務を持つ `BoardCursor` に 1 か所だけ置く。
- 設計書の説明は、「`MoveTo` の前提条件は、position が盤面の中にあること。破られたら `ArgumentOutOfRangeException` を投げる」に書き換える。
- テスト（クラス設計書のテストの節に足す）: 盤面の中の位置で `Position` が変わる、盤面の外の位置（負の座標、幅・高さちょうどの座標）で例外になり `Position` が変わらない、`board` が null で `ArgumentNullException`。

### 指摘 2: `MoveTo` が引数 `board` を使っていない

- `BoardCursor.MoveTo(CellPosition position, Board board)`: 使われない引数（シグネチャが「盤面に照らして動かす」と読めるのに、本体 `=> Position = position` は `board` を無視する。名前と引数が仕事を正しく表していない）→ 指摘 1 のガード節で `board` を使う形にする
- 箇条: **意図を表現**（ノイズ）、**的確な名前**（シグネチャが仕事を過不足なく表していない）
- 補足: `board` を消してシグネチャを合わせる案もあるが、それでは指摘 1 の検証ができず、`Move` とも引数の形が揃わなくなる（クラスのインタフェース不一致の芽）。`board` を残して使う方を選ぶ。

### 指摘 3（確認事項）: 盤面が変わったときに、今の `Position` が盤面の外に残りうる

- `BoardCursor.Position`: 不変条件が成り立たない経路がある（`board` を呼び出しごとに受け取り、保持しないので、難易度を上級から初級に変えるなど盤面が小さくなると、`Position` が新しい盤面の外に残る。その状態で `Move` を呼ぶと、「端で止まる」判定の前提（今の位置が中にある）が崩れる）
- 性質: 七箇条の外の **正しさ**（例外の境界）
- 直し方の案: 新しいゲームを始めるときにカーソルを戻す操作（例: `Reset()` で左上へ。または `MoveTo` で盤面の中の位置を明示して渡す）を設計書に書き、呼び出す場所（共有の `GameSession` の新しいゲームの開始など、1 か所）を決める。あわせて `Move` の先頭にも、今の位置が `board` の中にあることを前提条件として明示するか、`Debug.Assert` で表す。
- 仮定: 設計書の抜粋には、新しいゲームの開始時のカーソルの扱いが書かれていない。別の箇所で決まっていれば、この指摘は不要である（ユーザーの判断が要る点）。

## 指摘しなかったこと

- `Position` の `private set` と `sealed` は、状態を自分だけで変える形で良い。
- `Move` の端の判定に `board.Contains` を使う（情報を持つ `Board` に判定を任せる。Expert）のは良い。
- カーソルに `Board` を保持させる（コンストラクタで受け取る）作り替えは提案しない。盤面は新しいゲームのたびに作り直されるので、保持すると古い盤面を指す別の問題が出る。引数で受け取る今の形を保ち、指摘 3 は開始時の戻し方で扱う。

## 置いた仮定

- `Board.Contains(CellPosition)` は、位置が盤面の中なら true を返す。
- `CellPosition` は値の型（record struct など）で、null にならない。
- リポジトリの規約は、例外によるガード節を禁じていない。
