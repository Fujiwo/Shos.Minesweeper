# T3: `BoardCursor` のクラス設計のレビュー

## 読んだもの
課題が設計書のレビューなので、スキル C の表の「設計の相談（設計書のレビューを含む）」に当たる。
- 必ず読む: modeling.md、object-design.md
- 必要なら読む: quality-gates.md の「七箇条をレビューの観点にする」（設計書のレビューなので）と、「契約とガード節」（論点がガード節の有無なので）

## 対象の意図
`BoardCursor` は、3 つの版が共有する公開の型で、「キーボードで選んでいるマスを、盤面の中に保つ」ためのもの。`Move` は端で止めて、盤面の中にとどめている（`board.Contains`）。そのため、このクラスの不変条件は「`Position` はいつも盤面の中にある」と読める。

## 結論
指摘は 3 件ある。設計書の「ガード節を置かない（引き算）」という判断は取り消し、`MoveTo` の入口に前提条件のガード節を置くべきである。

---

## 指摘 1（重要）: `MoveTo` の前提条件がコードに書かれず、不変条件が破れる

- **書式**: `BoardCursor.MoveTo`: 前提条件の欠落（`Move` は `board.Contains` で `Position` を盤面の中に保つのに、`MoveTo` は何も確かめずに代入する。守られるかどうかは、3 つのアプリの呼ぶ側のコード次第になる）→ ガード節の導入（前提条件を入口で確かめる）
- **箇条**: Testable（前提条件が明示されているか）。七箇条の外の性質としては、正しさ（契約と不変条件）にも当たる。
- **根拠**:
  - 「呼ぶ側が盤面の中の位置しか渡さない」は、いまの呼ぶ側についての観察にすぎず、契約ではない。`BoardCursor` は 3 つのアプリ（Web、デスクトップ、コンソール）が共有する公開の型なので、呼ぶ側は 3 か所あり、UI の技術もそれぞれ違う。この前提が正しいかを確かめるには 3 か所をすべて読む必要があり、どこかで破れても `BoardCursor` の側では気づけない。
  - 破れたときの症状は遠くに出る。盤面の外の `Position` が表示や操作に使われて、例外になるか、何も起きない。ガード節があれば、誤りはその場で見つかる（エラーの滞在時間を縮める）。
  - 同じクラスで、`Move` は盤面の中を保ち、`MoveTo` は保たない。不変条件を守るメソッドと守らないメソッドが混ざっている。
- **「引き算」の使い方について**: 引き算で削るのは、頼まれていない抽象・パターン・将来への備えである。公開メソッドの前提条件を書くガード節はそのどれでもなく、スキルでは「公開メソッドが引数に前提を持つとき」に置くものとされている。1 行で書けて読む対象もほとんど増えないので、削る理由にならない。
- **直し方**:

```csharp
/// マウスで選んだマスなど、指定の位置へ動かす。
/// 前提条件: position は board の中にある。
public void MoveTo(CellPosition position, Board board)
{
    if (!board.Contains(position))
        throw new ArgumentOutOfRangeException(nameof(position), position, "盤面の外の位置です。");
    Position = position;
}
```

  - 盤面の外の値を黙って端に丸める（クランプする）ことはしない。呼ぶ側の誤りを隠して、症状を握りつぶすことになるからである。前提条件が破れたのは呼ぶ側の不具合なので、例外で知らせる。
  - `board` が null になりうる場合の `ArgumentNullException.ThrowIfNull(board)` は、`Nullable` が有効で引数が null を許さない型なら要らない（仮定。`Move` もそろえる）。
  - 設計書の説明は「`MoveTo` の前提条件は、`position` が `board` の中にあること。破れたら `ArgumentOutOfRangeException` を投げる。こうして `Position` がいつも盤面の中にあるという不変条件を保つ」に書き換える。
- **テスト**（Presentation.Tests に足す）: 盤面の外（負の座標、幅や高さと同じ座標）を渡すと `ArgumentOutOfRangeException` になり、`Position` は変わらない。盤面の中の位置を渡すと、そこへ動く。

## 指摘 2: `MoveTo` の引数 `board` が使われていない

- **書式**: `BoardCursor.MoveTo(CellPosition position, Board board)`: 使われない引数（本体が `Position = position` だけで、`board` を読んでいない）→ 引数の削除か、引数を使う形への変更
- **箇条**: 意図を表現（意図にない記述はノイズになる）。
- **根拠**: 引数に `board` があると、読む人は「盤面で確かめている」と受け取るが、実際は確かめていない。シグネチャと振る舞いが食い違っている。
- **直し方**: 指摘 1 のガード節で `board` を使えば、この指摘も解消する。逆に、設計書のとおりガード節を置かないのなら、`board` は削るべきである（そのときも指摘 1 は残る）。本レビューが勧めるのは、ガード節を置いて `board` を残すほうである。`Move` と引数の形がそろい、第六箇条（ルールの統一）にも合う。

## 指摘 3（確認が要る）: 盤面が替わったときに `Position` が盤面の外に残りうる

- **種類**: 七箇条の外の正しさ（不変条件の境界）。
- **根拠**: `BoardCursor` は盤面を持たず、呼ぶたびに `board` を受け取る。そのため、難易度を上級（30×16）から初級（9×9）に替えたとき、`Position`（たとえば列 20、行 10）が新しい盤面の外に残りうる。その後の `Move` は、移動先が `board.Contains` を満たさないので、どの向きにも止まる。カーソルがどこにも動かなくなる。
- **仮定**: 示された部分には、新しいゲームや難易度の変更で `BoardCursor` を作り直すか、元に戻すかが書かれていない。ほかの箇所（たとえば `GameSession`）で作り直しているのなら、この指摘は当たらない。
- **直し方（最小のもの）**: 盤面を替えるときに、呼ぶ側が `BoardCursor` を新しく作ることを設計書に書く。たとえば「新しいゲームを始めるたびに `new BoardCursor()` にする（位置は左上の (0, 0)）」。そのうえで、テストを 1 件足す（難易度を替えた後にカーソルが盤面の中にある）。`BoardCursor` に盤面の大きさを持たせる作り替えは、この問題のためには大きすぎるので勧めない。

---

## 作らなかったもの・置いた仮定
- `Board.Contains(CellPosition)` があり、盤面の中かを正しく判定すると仮定した（設計書の `Move` の注記による）。
- `CellPosition` は値の型で、負の座標も表せると仮定した（だからガード節が要る）。
- 盤面の外を渡されたときに、例外ではなく無視する（何もしない）ことが仕様で決まっているのなら、指摘 1 の直し方は「`Contains` でなければ何もしない」に替わる。ただし、そうすると誤りに気づけなくなるので、勧めない。
- 盤面を持つ `BoardCursor` や、座標の型で盤面の中を表すといった、新しい型や抽象は提案していない。1 行のガード節で足りるからである。

## ユーザーの判断が要る点
- 盤面の外が渡されたときに、例外にするか（勧める）、無視するか。
- 指摘 3 の、盤面を替えたときにカーソルを作り直すか戻すかは、どこの責務か（`GameSession` か各アプリか）。
