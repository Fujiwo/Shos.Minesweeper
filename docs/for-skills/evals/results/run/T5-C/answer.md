# T5 のレビュー: `InputText.Normalize` の追加

## 適用したスキルの手順

- 作業の種類は「レビュー（ユーザーから依頼されたとき）」なので、判断を伴う作業として扱った。
- 読んだもの: quality-gates.md の「七箇条をレビューの観点にする」、refactoring.md の「コードの臭い」と「臭い → 技法の対応表」、テストを含む変更なので testing.md（全体）。
- 変更の意図をひとことで言うと、「利用者が入力した数の文字列を、解釈する前に整えて、全角の数字（例:『３０』）も受け付けるようにする」。

## 結論

**このままでは取り込まない。** いちばん重い指摘（指摘 1）は、この変更が本番の実行環境であるブラウザーの中で動かない疑いが強いことである。「全テストが Green」は PC の .NET で出た結果なので、この疑いは解消されない。

## 指摘

### 指摘 1（重大）: 七箇条の外、正しさ（実行環境の差）。Green が本番の環境を保証していない

- 場所: `InputText.Normalize` の `Normalize(NormalizationForm.FormKC)`。
- 問題: テストは PC の .NET 10（`dotnet test`）で動いているが、この部品を使う本番は Blazor WebAssembly、つまりブラウザーの中の .NET である。ブラウザーの .NET はグローバリゼーションのデータを減らして動き、`string.Normalize` の FormKC・FormKD に対応していない（`PlatformNotSupportedException` を投げる）と見込まれる。そうなると、全角の数字を受け付けるという目的が果たせないうえに、カスタムの盤面の入力で例外が出て、画面が壊れるおそれがある。デスクトップ版（Windows の .NET）では動くので、共有のクラスライブラリに置いたことで、版によって振る舞いが違う部品になる。
- テストとの関係: testing.md の「フィードバックの種類」の「本番の実行環境での実行」に当たる。テストの環境と本番の環境が違うので、Green はこの差を保証しない。作者の「全テストが Green」は、Web 版で正しく動くことの根拠にならない。
- 取り込む前にすべきこと:
  1. 発行した Release 版（`dotnet publish -c Release` の出力。発行の設定でグローバリゼーションの扱いが変わりうるので、Debug 実行だけで判断しない）をブラウザーで動かし、カスタムの幅に「３０」「 16 」「１６」を入れて確かめる。Chrome と Safari（iOS）で確かめるのが望ましい。
  2. 例外が出るなら、どちらかの方法で直す（どちらを選ぶかはユーザーの判断が要る）。
     - 案 A（Think Simple）: 目的は「全角の数字を受け付ける」だけなので、NFKC を使わず、全角の数字（U+FF10〜U+FF19）を半角に置き換える処理と `Trim` を C# で書く。どの実行環境でも同じに動き、Presentation の 1 か所で済む。捨てるもの: 全角の負号など、数字以外の全角の文字の変換。
     - 案 B: NFKC の変換を保ちたいなら、Web 版だけブラウザーの JavaScript（`text.trim().normalize("NFKC")`）で行い、デスクトップ版は C# の `InputText.Normalize` を使う。捨てるもの: 変換が 2 か所になる（Once And Only Once が崩れるので、2 か所の対応をテストか設計書で押さえる必要がある）。
  3. 選んだ方法で、Web 版の部品のテスト（bUnit など）か、少なくともブラウザーでの確認の結果を、この変更の説明に書く。

### 指摘 2: 七箇条の外、整合（要求と変換の範囲の食い違い）。NFKC は目的より広い

- 場所: `Normalize(NormalizationForm.FormKC)`。
- 問題: 目的は「全角の『３０』を受け付ける」だが、NFKC は全角の数字のほかに、丸数字「①」→「1」、上付き「²」→「2」、分数「½」→「1⁄2」、全角の負号「－」→「-」なども変える。つまり、「①⑥」を 16 として受け付けるなど、仕様で決めていない入力まで受け付けることになる。問題文にない振る舞いを足している（引き算: 問題を複雑にしていないか）。
- 取り込む前にすべきこと: どの入力を受け付けるかを、入力と期待値の表にしてユーザーと合意する（testing.md の「何を検証すべきかはユーザーと合意する」）。少なくとも「全角の数字」「全角の空白（U+3000）」「丸数字」「全角の負号」の 4 行を決める。表で NFKC の範囲が要らなければ、指摘 1 の案 A を選ぶ根拠にもなる。

### 指摘 3: テストの設計（境界値・エッジケースの欠け）。いちばん起きやすい入力が確かめられていない

- 場所: `InputTextTests` の `[InlineData]`。
- 問題: 日本語の IME で打つと、空白は全角の空白（U+3000）になりやすいのに、その行がない。半角の空白の前後の除去（`" 16 "`）だけでは、全角の空白を除けるかは確かめられていない。ほかにも、次の行が欠けている。
  - 全角の空白と全角の数字の組み合わせ（`"　１６　"` → `"16"`）
  - 空文字列と空白だけ（`""`、`"　"` → `""`）。この後の解釈で「入力なし」を正しく扱えるかの境界になる
  - 変える必要のない入力（`"30"` → `"30"`）。変換が既存の入力を壊さない番人になる
  - 指摘 2 で合意した表の行（丸数字などを受け付けるか、受け付けないか）
- 取り込む前にすべきこと: 上の行をテストに足す。後から足した行で最初から Green になるものは、実装をわざと壊して失敗することを確かめ、壊した変更は戻す。

### 指摘 4: テスト名（一テスト一関心の崩れ）。`NormalizesFullWidthDigitsAndTrims` → 関心ごとにテストを分けて名前を変える

- 場所: `InputTextTests.NormalizesFullWidthDigitsAndTrims`。
- 箇条: 的確な名前、Testable。
- 問題: 一つのテストに「全角の数字を半角にする」と「前後の空白を除く」の二つの関心が入っている（名前の `And` がその印）。`" 16 "` の行が失敗しても、テストの名前からはどちらの仕様が破れたか読みにくい。
- 取り込む前にすべきこと: `ConvertsFullWidthDigitsToHalfWidth`（`"３０"`、`"１６"`）と `TrimsLeadingAndTrailingSpaces`（`" 16 "`、`"　16　"`）に分ける。

### 指摘 5: 七箇条の外、正しさ（入力の境界）。null の扱いが決まっていない

- 場所: `Normalize(string text)`。
- 問題: `text` が null だと `NullReferenceException` になる。`Nullable` が有効なら、引数が `string`（null 非許容）なのでコンパイラーの警告で防げるが、Razor の入力の束縛で null が来る経路（入力欄が空のときの値など）がないかは、この差分からは分からない。
- 取り込む前にすべきこと: 呼び出し側で null が来ないことを確かめる。来るなら、契約を決める（null を空文字列として扱う、または入り口のガード節で `ArgumentNullException` を投げる）。どちらにしてもテストを 1 件足す。

### 指摘 6: 七箇条の外、整合（呼び出し側の変更とつなぎの確認がない）

- 問題: 差分には `InputText.Normalize` の定義だけがあり、カスタムの幅・高さ・地雷数を解釈する側でこれを呼ぶ変更が見えない。呼んでいなければ、目的（全角の「３０」を受け付ける）は果たせていない。単体テストは `Normalize` だけを確かめており、「全角で入力したカスタムの盤面が始められる」ことは確かめていない。
- 取り込む前にすべきこと: 解釈する側の変更を差分に含め、カスタムの入力に「３０」を入れると幅 30 の盤面が始まることを、画面の部品のテスト（bUnit）か、指摘 1 のブラウザーでの確認で押さえる。

### 指摘 7（軽微）: 七箇条の外、正しさ（変換の順序）

- 場所: `text.Trim().Normalize(...)`。
- 問題: 先に `Trim` し、後で NFKC をかけているので、NFKC で空白を含む形に変わる文字（例: 全角の濁点「゛」（U+309B）は、空白と結合文字に変わる）が端にあると、変換の後に空白が残りうる。数の入力では起きにくいので軽微である。
- 取り込む前にすべきこと: 指摘 1 で NFKC を残すなら、`Normalize` の後に `Trim` する順序にするか、この順序を選んだ理由を書く。案 A を選べば、この指摘は消える。

## よい点

- 変換を Presentation の 1 か所（`InputText.Normalize`）に置き、Web 版とデスクトップ版で共有している。入力を整える責務の所在が一つに決まっている（Once And Only Once、単一責務）。
- 純粋な静的メソッドなので、依存を差し替えずにテストできる（Testable）。
- テストを先に書いて Red を見たと説明している。

## 作者に確かめたいこと・置いた仮定

- 仮定: Web 版の発行の設定は既定で、ブラウザーの .NET は FormKC に対応していない。この仮定が正しいかは、指摘 1 の 1. のブラウザーでの確認で決まる。そこで例外が出なければ指摘 1 は取り下げるが、その場合も確認の結果を変更の説明に残してほしい。
- 仮定: 入力の対象は、カスタムの盤面の幅・高さ・地雷数の整数だけである。
- ユーザーの判断が要る点: 受け付ける入力の範囲（指摘 2 の表）と、それに応じた方法（指摘 1 の案 A か案 B）。

## 取り込む前にすべきことのまとめ

1. 発行した版をブラウザーで動かし、全角の入力で例外が出ないかを確かめる（指摘 1）。
2. 受け付ける入力の表をユーザーと合意し、案 A（全角の数字だけを置き換える）か案 B（Web 版は JavaScript の NFKC）を選ぶ（指摘 1、2）。
3. テストに全角の空白・空文字列・変えなくてよい入力・合意した表の行を足し、関心ごとにテストを分ける（指摘 3、4）。
4. null の契約を決める（指摘 5）。
5. 解釈する側の変更と、全角で入力して盤面が始まることの確認を差分に含める（指摘 6）。
