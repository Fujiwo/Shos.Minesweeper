- 必ず読む: object-design.md
- 必要なら読む: quality-gates.md の「七箇条をレビューの観点にする」（設計書のレビューなので）。論点がガード節の要否なので、同じファイルの「契約とガード節」も読んだ。書式の確認のため refactoring.md の「精神論ではなく臭いと技法の名前で語る」を読み、引き算の是非を判断するため simplicity.md の「引き算の設計」の注意書きも確かめた

## レビュー対象の意図（ひとことで）

`BoardCursor` は、キーボードで選んでいるマスを持ち、盤面の中で動かす。3 つの版が共有する公開の型である。

## 結論

指摘がある。「呼ぶ側が盤面の中しか渡さないのでガード節を置かない（引き算）」は、引き算の対象を取り違えている。公開の型の入口で前提条件を確かめるガード節は、契約を明示するものである。「要求にない入力を処理する分岐」ではないので、引き算で削ってはいけない。

## 指摘

### 指摘 1（重大）: `MoveTo` が前提条件を確かめず、不変条件が守られていない

- 書式: `BoardCursor.MoveTo`: 前提条件が明示されていない（公開メソッドが、盤面の外の位置を受け取っても黙って `Position` にする）→ ガード節を置く
- 観点: 七箇条の Testable（前提条件が明示されているか）と、七箇条の外の「正しさ（例外の境界）」
- 根拠:
  1. **公開の境界である。** `BoardCursor` は 3 つのアプリが共有するライブラリの公開の型である。「呼ぶ側が盤面の中しか渡さない」は、今の呼ぶ側のコードについての観察にすぎない。型の契約にはなっていない。呼ぶ側は 3 つあり（Web のクリック、デスクトップのマウス、そして今後の変更）、その全部が守る保証を、この型は持っていない。
  2. **不変条件「`Position` は盤面の中」が崩れる。** `Move` は `board.Contains` で端を判定するので、`Position` が盤面の中にあることを前提にしている。`MoveTo` だけがこの前提を破れる。いったん外に出ると、`Move` の結果が決まらない。たとえば、隣のマスも盤面の外なので止まったまま動けなくなるか、判定の仕方によっては外のまま動き続ける。さらに、その `Position` で盤面のマスを引く描画や開く操作が、離れた場所で範囲外の例外を投げる。原因（`MoveTo` の呼び出し）と症状が離れるので、エラーが気づかれずに残る時間が長くなる。
  3. **盤面が変わる場面がある。** 難易度の変更やカスタムの寸法で、盤面の大きさは変わる。前の盤面での位置が新しい盤面では外、ということが、呼ぶ側に悪意がなくても起こりうる（仮定: 盤面が替わっても同じ `BoardCursor` を使い続ける作りもありうる）。
  4. **`board` 引数が使われていない。** `MoveTo(CellPosition position, Board board) => Position = position;` は `board` を受け取るのに使っていない。受け取った意図（盤面に合わせる）が本体に表れていない。これはノイズで、「確かめるつもりで引数を足したが、確かめていない」と読める。
- 引き算との関係: スキルの simplicity.md は、公開の境界での前提条件のガード節を「契約の明示で、削る対象ではない」としている。削るのは「要求にない入力や状況をわざわざ処理する分岐」である。たとえば、盤面の外が来たら端に丸める、黙って無視する、といった処理がそれに当たる。ガード節は、異常な入力を入口で断るために置く。本処理を一本道に保つためのもので、複雑さを増やすものではない。

#### 直し方

```csharp
/// マウスで選んだマスなど、指定の位置へ動かす。
/// 前提条件: position は board の中にある。外なら ArgumentOutOfRangeException。
public void MoveTo(CellPosition position, Board board)
{
    ArgumentNullException.ThrowIfNull(board);
    if (!board.Contains(position))
        throw new ArgumentOutOfRangeException(nameof(position), position, "盤面の外の位置には動かせない。");
    Position = position;
}
```

- `Move` にも `ArgumentNullException.ThrowIfNull(board)` を置く（`Nullable` が有効でも、公開の型の入口なので）。
- テストを足す: 盤面の中の位置なら `Position` がその位置になる。盤面の外（負の座標、幅・高さちょうどの座標）なら `ArgumentOutOfRangeException` を投げ、`Position` は変わらない。
- 採らなかった案: 盤面の外を端に丸める（clamp）、または黙って無視する。どちらも呼ぶ側の不具合を隠し、要求にない入力を処理する分岐を足すことになる。これこそ引き算で削るべきものなので採らない。

### 指摘 2（軽微）: 不変条件と前提条件が設計書に書かれていない

- 書式: `BoardCursor` の説明: 契約の不足（`Position` がいつも盤面の中にあること、初期位置、`Move` と `MoveTo` の前提が書かれていない）→ 不変条件と前提条件を設計書と doc コメントに書く
- 観点: 七箇条の「意図を表現」と Testable
- 直し方: 設計書に次の 3 行を足す。「不変条件: `Position` は、最後に渡された盤面の中にある。」「初期値: 左上 (0, 0)。盤面は 1 マス以上ある（仮定）。」「`MoveTo` の前提条件: 位置は盤面の中。外なら例外（指摘 1）。」設計書の「ガード節は置かない（引き算）」という説明は削る。

### 参考（ユーザーの判断が要る点。指摘ではない）

`Board` を呼び出しのたびに受け取る形だと、カーソルが「どの盤面の中にいるか」は呼ぶ側まかせになる。盤面をコンストラクタで受け取って持つ形にすれば、不変条件をコンストラクタで成り立たせられる。盤面が替わったら新しいカーソルを作ればよく、指摘 1 の 3 の場面も型の側で閉じる。ただし、この形にすると、盤面が替わるたびに呼ぶ側がカーソルを作り直す必要がある。3 つの版の呼ぶ側の作りが分からないので、ここでは提案にとどめる。指摘 1 のガード節は、どちらの形でも要る。

## 置いた仮定

- `Board.Contains(CellPosition)` は、位置が盤面の中なら true を返す（設計書の `Move` の説明から）。
- 盤面は 1 マス以上ある。
- 呼ぶ側は、盤面が替わっても同じ `BoardCursor` を使い続けることがある。
