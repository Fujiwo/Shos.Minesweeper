# T3 BoardCursor のクラス設計のレビュー

## 適用したスキルと読んだ範囲

- 作業の種類は「設計の相談（設計書のレビュー）」なので、SKILL.md の表に従い、object-design.md を全部読み、quality-gates.md の「七箇条をレビューの観点にする」を読んだ（設計書をレビューするため）。
- 指摘の中心が引数の検証（ガード節）なので、quality-gates.md の「契約とガード節」も読んだ（表の「引数の検証・前提条件を書くとき」の条件に当たる）。

## レビュー対象の意図（ひとこと）

`BoardCursor` は「キーボードで選んでいるマスの位置を、盤面の中に保ったまま動かす」部品で、3 つの版が共有する公開の型である。

## 結論

指摘がある。設計書の「呼ぶ側が盤面の中しか渡さないのでガード節を置かない（引き算）」という判断は採らず、`MoveTo` にガード節を置くべきである。

## 指摘

### 指摘 1（重大度: 高）: `MoveTo` の前提条件が契約になっていない

`BoardCursor.MoveTo`: 前提条件の欠落（「盤面の中の位置」という前提が呼ぶ側の善意にしかなく、コードにない。`Move` は `board.Contains` で盤面の中を保つのに、`MoveTo` は何でも `Position` に入れる）→ ガード節の導入

- 箇条: **Testable**（前提条件が明示されているか）。あわせて七箇条の外の**正しさ**（不変条件の破れ）。
- 根拠:
  1. **公開の型で、呼ぶ側が一つではない。** 「呼ぶ側が盤面の中しか渡さない」は、いま想定している呼び出し（Web 版のマウスのクリック）についての観察であって、型の契約ではない。Presentation は Web・デスクトップ・コンソールの 3 つのアプリが使う共有のライブラリなので、呼ぶ側はこれから増え、書く人も変わる。前提を呼ぶ側に預けると、「盤面の中の位置を渡すこと」を 3 か所以上で個別に守らせることになる（前提の知識が呼ぶ側に散る）。
  2. **クラスの不変条件が崩れる。** `Move` は「盤面の端で止まる」、つまり「`Position` は常に盤面の中」という不変条件を守っている。`MoveTo` だけがそれを破れる入口になっている。破れた後は、表示（カーソルの枠を描く位置）や、`Position` を使ったマスの開放で、範囲外の添え字の例外や何も起きない不具合として、原因から離れた場所で表に出る。ガード節の効能の 2（契約違反をその場で検知し、エラーの滞在時間を縮める）が失われる。
  3. **これは引き算の対象ではない。** Think Simple の引き算が削るのは「頼まれていない抽象・パターン・将来への備え」である。前提条件の検証は、公開のメソッドが持つ契約を書き表すもの（説明責任の実行形）で、1 行で済み、読む対象を増やさない。削ると、クラスが単純になるのではなく、クラスの外（呼ぶ側すべて）に前提の確認が漏れ出して、全体としては複雑になる。
  4. **引数 `board` が使われておらず、シグネチャが意図と食い違う。** 現在の `MoveTo(CellPosition position, Board board) => Position = position;` は `board` を受け取りながら使っていない。読む人は「盤面に照らして何かしている」と読むが、実際は何もしない（意図を表現・的確な名前の問題。名前と引数が嘘をついている）。ガード節を置けば、`board` が引数にある理由がそのまま説明になる。

- 直し方:

```csharp
/// マウスで選んだマスなど、指定の位置へ動かす。
/// 前提条件: position が board の中にあること。
public void MoveTo(CellPosition position, Board board)
{
    ArgumentNullException.ThrowIfNull(board);   // Board が参照型のとき（Nullable が有効でも公開 API の入口では確かめる）
    if (!board.Contains(position))
        throw new ArgumentOutOfRangeException(nameof(position), position, "盤面の外の位置には動かせない。");
    Position = position;
}
```

- 例外を投げる方を選び、盤面の中に丸める（クランプする）方は採らない。範囲外の位置が来るのは呼ぶ側の不具合なので、黙って直すと不具合を隠すことになる。`Move` の「端で止まる」は利用者の操作（矢印キーを押し続ける）として正常な入力への仕様であり、`MoveTo` の範囲外は契約違反なので、扱いが違ってよい。
- テスト（先に足して Red を確かめる）:
  - `MoveTo` に盤面の中の位置を渡すと、`Position` がその位置になる。
  - `MoveTo` に盤面の外の位置（列が幅と同じ、行が負など、境界のすぐ外）を渡すと `ArgumentOutOfRangeException` になり、`Position` は変わらない。
- 設計書の説明も、「呼ぶ側が盤面の中しか渡さないのでガード節は置かない」から、「前提条件は盤面の中の位置。破られたら `ArgumentOutOfRangeException`」に書き換える。

### 指摘 2（重大度: 中。確認事項を含む）: 盤面を持たないので、盤面が替わったときに不変条件が保てない

`BoardCursor` 全体: 不変条件の置き場所の不足（`Position` が盤面の中かどうかは、毎回引数で受け取る `board` に依存するのに、盤面が替わったときにカーソルを合わせる操作がない）→ 盤面が替わるときの操作を契約として決める

- 箇条: 七箇条の外の**正しさ**（状態の境界）。
- 根拠: 難易度を上級（30×16）から初級（9×9）に替えると、カーソルが (20, 10) のままなら新しい盤面の外に残る。この後の `Move` が盤面の外の位置を起点にどう振る舞うか（`board.Contains(次の位置)` が偽になって永久に動けない、など）が、設計書から読み取れない。指摘 1 のガード節は `MoveTo` の入口しか守らないので、この経路は残る。
- 直し方（どちらか。仮定: 新しいゲームを始めたときにカーソルを左上に戻す、または作り直すのが仕様として許される）:
  - 盤面が替わったら `BoardCursor` を作り直す（新しいゲームごとに新しいカーソル）と、設計書に書く。クラスに操作を足さずに済むので、こちらを第一案とする（引き算）。
  - 作り直せない事情があるなら、`Reset()`（左上に戻す）を 1 つだけ足す。
- `Board` をコンストラクターで受け取って保持する形（`Move(direction)`、`MoveTo(position)` から `board` を消す）も考えられるが、盤面の置き場所や版ごとの寿命の事情が設計書からは分からないので、ここでは提案にとどめる。

## 指摘にしなかった点

- `sealed`、`Position` の `private set` は、状態を外から書き換えさせない形で適切である。
- `Move` の「端では止まる」判定を `board.Contains` に任せているのは、盤面の中かの判定を情報を持つ `Board` に置いている（Expert）ので適切である。`MoveTo` のガード節も同じ `board.Contains` を使えば、「盤面の中か」の判定が 1 か所に保たれる（Once And Only Once）。

## 置いた仮定

- `CellPosition` は値型（record struct など）で、`Board.Contains(CellPosition)` がすでにある（`Move` の説明から）。
- `Board` は参照型で、プロジェクトは Nullable が有効。`board` の null 検査は公開 API の入口としての防御で、Nullable の警告だけで足りるとチームが決めていれば省いてよい。
- 盤面が替わるとき（難易度の変更、新しいゲーム）のカーソルの扱いは、提示された設計書の範囲には書かれていないので、指摘 2 は確認事項として挙げた。
