# T3 `BoardCursor` のクラス設計のレビュー

## 適用したスキルの範囲

作業の種類は「設計の相談（設計書のレビュー）」で、ユーザーから頼まれたレビューでもある。そのため、次を読んで判断した。

- object-design.md（必ず読む）
- quality-gates.md の「七箇条をレビューの観点にする」（設計書のレビューなので）と「契約とガード節」（論点がガード節を置くかどうかなので）
- refactoring.md の「コードの臭い」「臭い → 技法の対応表」「精神論ではなく臭いと技法の名前で語る」（指摘の書式のため）

## 対象の意図（ひとことで）

`BoardCursor` は「キーボードで選んでいるマスを、盤面の中に保つ」型である。`Move` は端で止まる、つまり「`Position` は盤面の中にある」ことを保つ。これが、この型が 3 つの版に約束している不変条件だと読める。

## 結論

指摘がある。設計書にある「呼ぶ側が盤面の中の位置しか渡さないので、ガード節は置かない（引き算）」という判断は誤っている。直すべきである。

---

## 指摘 1（重要）: `MoveTo` の前提条件がコードに書かれていない。不変条件を外から壊せる

- **書式**: `BoardCursor.MoveTo`: 臭いの一覧には当てはまらない。症状は次のとおり。公開の型の公開メソッドなのに、前提条件（`position` は `board` の中にある）がコードになく、設計書の説明文にしかない。そのため、`Move` が保っている不変条件「`Position` は盤面の中にある」を、`MoveTo` からは壊せてしまう。→ ガード節で前提条件を入口で確かめる
- **箇条**: Testable（前提条件が明示されているか）。性質としては「正しさ（契約の境界）」でもある
- **根拠**
  1. **引き算の対象を取り違えている。** 引き算で削るのは、頼まれていない抽象・パターン・将来への備えである。公開メソッドが引数に前提を持つときに置くガード節は、スキルでは「いつ置くか」がはっきり決まっている要素で、先回りの備えには当たらない（quality-gates.md の「ガード節」の「いつ」: 公開メソッド・コンストラクタが引数や状態に前提を持つとき）。
  2. **「呼ぶ側が中の位置しか渡さない」は、呼ぶ側の事情であって、型の契約ではない。** `BoardCursor` は 3 つのアプリが共有するライブラリの公開の型である。呼ぶ側は Web（描いたマス）、デスクトップ（Avalonia で、ピクセルの座標からマスへの換算。枠や余白の上で押すと、範囲の外の値になりやすい）、コンソールと 3 つあり、今後も増えうる。どの呼ぶ側も正しいことを、この型の側では保証できない。前提が破れたときに気づけないと、エラーの滞在時間が延びる（ガード節の効能 2「バグの早期検知」が失われる）。
  3. **壊れた後の振る舞いが決まっていない。** `Move` は `board.Contains` で次の位置を確かめて止まる。そのため、`Position` が盤面の外にあると、隣のマスもたいてい盤面の外になり、カーソルが盤面の外に閉じ込められて戻れなくなるおそれがある。症状は `MoveTo` から離れた `Move` で出るので、原因を追いにくい。
  4. **`board` の引数が、`MoveTo` の中で使われていない。** シグネチャは「盤面に照らして動かす」ことを約束しているのに、中身は代入だけである。読む人は、確かめているものと誤解する（意図を表現: シグネチャと中身が呼応していない）。
- **直し方**: 入口で確かめて、破れていれば例外で打ち切る。言語の標準の例外を使い、独自の検証の仕組みは作らない。

```csharp
/// マウスで選んだマスなど、指定の位置へ動かす。
/// 前提条件: position は board の中にある。
public void MoveTo(CellPosition position, Board board)
{
    ArgumentNullException.ThrowIfNull(board);
    if (!board.Contains(position))
        throw new ArgumentOutOfRangeException(nameof(position), position, "盤面の外の位置です。");
    Position = position;
}
```

- **捨てた案**: 盤面の中に丸める（クランプする）、または黙って無視する案。この案では、呼ぶ側の換算の誤りを隠してしまう（エラーを黙って捨てない）。範囲の外で押したときに無視したいなら、それは呼ぶ側の UI の仕様として、呼ぶ側で判定する。
- **設計書の直し**: 「ガード節は置かない（引き算）」の説明を削り、次の 2 点を書く。「`MoveTo` の前提条件は、`position` が `board` の中にあること。破れれば `ArgumentOutOfRangeException`」と、「`BoardCursor` の不変条件は、`Position` が盤面の中にあること」。
- **テスト**: `MoveTo` に盤面の外の位置（負の座標、幅・高さちょうどの座標）を渡すと例外になり、`Position` が変わらないことを確かめる単体テストを足す。

## 指摘 2（確認）: 盤面が替わったときに、不変条件を誰が保つかが書かれていない

- **書式**: `BoardCursor`（盤面を持たずに、呼ぶたびに `Board` を受け取る形）: 臭いの一覧には当てはまらない。症状は次のとおり。難易度を変えて小さい盤面になると（例: 上級の右下から初級へ）、前の `Position` が新しい盤面の外に残りうる。指摘 1 の 3 と同じく、`Move` で戻れなくなるおそれがある。→ 設計書に、新しいゲームでのカーソルの扱いを 1 行書く
- **性質**: 正しさ（不変条件の境界）。設計書との整合
- **直し方（最小）**: 新しい機能は足さない。設計書に「ゲームを始め直すたびに、`BoardCursor` を作り直す（`Position` は既定の (0, 0)）」か「呼ぶ側が `MoveTo` で盤面の中に置き直す」のどちらかを決めて書く。指摘 1 のガード節があれば、置き直しの誤りも入口で見つかる。
- 仮定: 設計書の他の箇所に、すでにこの扱いが書かれているかは分からない。書かれていれば、この指摘は不要である。

## 指摘しなかったこと（引き算の判断）

- `BoardCursor` に `Board` を持たせて、引数から外す案は勧めない。盤面の持ち主はゲームの進め方の側であり、カーソルが持つと、盤面の差し替えを 2 か所で行うことになる（ひとつの変更 → ひとつの修正に反する）。いまの「呼ぶたびに渡す」形で足りる。
- インターフェイスの抽出や、位置の検証の仕組みの新設は要らない。`board.Contains` があるので、ガード節 1 行で済む（Expert: 盤面の中かどうかは、盤面が答える）。

## 置いた仮定

- `Board.Contains(CellPosition)` があり、盤面の中なら `true` を返す（`Move` の説明の「board.Contains を使う」から）。
- `CellPosition` は値型で、`Position` の初期値 (0, 0) はどの盤面でも中にある。
- プロジェクトの規約は、例外を投げるガード節を禁じていない。
