# T3 の回答: `BoardCursor` のクラス設計のレビュー

## 適用したスキルの範囲

作業の種類は「設計の相談（設計書のレビュー）」とした。SKILL.md の表に従い、modeling.md と object-design.md を全部読み、設計書のレビューなので quality-gates.md の「七箇条をレビューの観点にする」を読んだ。論点が引数の検証なので、同じファイルの「契約とガード節」も読んだ。

## レビュー対象の意図

`BoardCursor` の仕事を一言でいうと「キーボードで選んでいるマスを、盤面の中に保つ」。`Move` のコメントの「盤面の端では止まる」から、**カーソルはいつも盤面の中にある**という不変条件が、このクラスの意図に入っていると読める。

## 結論

指摘がある。どちらも同じ根本原因（`MoveTo` が不変条件を守っていない）から来ている。

| # | 分類 | 重さ |
|---|------|------|
| 1 | 正しさ（七箇条の外。契約・不変条件）と Testable | 高い。直すべき |
| 2 | 意図を表現（使われていない引数） | 中。指摘 1 を直せば解消する |
| 3 | 整合（盤面が変わったときの責任の所在） | 中。設計書に書き足す |

---

### 指摘 1: `MoveTo` が前提条件をコードで確かめておらず、不変条件が破れる

`BoardCursor.MoveTo`: 前提条件が書かれていない（「盤面の中の位置しか渡さない」という約束が設計書の文章にしかなく、コードに現れない）→ ガード節で前提条件を明示する。

- **分類**: 正しさ（七箇条の外。契約と不変条件）。あわせて七箇条の「Testable」（前提条件が明示されているか）。
- **根拠**:
  1. `BoardCursor` は、3 つのアプリが使う共有ライブラリの**公開の型**である。「呼ぶ側が盤面の中の位置しか渡さない」は、設計書の筆者がいま思い浮かべている呼び出し元（画面で押されたマス）についての見込みにすぎない。Web 版・デスクトップ版・コンソール版の呼び出し元がこれからも増え変わるので、その約束をすべての呼び出し元に守らせる仕組みがない。
  2. `Move` は `board.Contains` を使って盤面の中に保っている。しかし `MoveTo` は何でも代入するので、クラスの不変条件（カーソルは盤面の中にある）を、2 つある状態変更のうち 1 つしか守っていない。
  3. 破れたときの害が、原因から離れた所で出る。たとえば次のとき、`Position` が盤面の外になる。
     - マウスの座標からマスを求める計算が、盤面の縁の余白や境界の 1 ピクセルで盤面の外の位置（-1 や幅と同じ値）を出したとき
     - 難易度を上級から初級に変えた後に、前の盤面で得た位置を渡したとき（指摘 3）

     すると、後でその `Position` を使って盤面を引いたり描いたりする所で、範囲外の例外や見えないカーソルになる。`Move` もずれた位置から計算を始める。どれも、原因の `MoveTo` の呼び出しから離れた所で出るので、調べにくい。
- **「引き算」の理由について**: 引き算（Think Simple・YAGNI）で削るのは、頼まれていない抽象・パターン・将来への備えである。公開メソッドの前提条件を入口で確かめるガード節は、これに当たらない。ガード節は、契約（何を期待するか）をコードで述べるものであり、異常系を入口で落として本処理を一本道にする。つまり、複雑さを減らす側にある。「呼び出し元が守るはずだから確かめない」は、前提条件を設計書の文章に置いたままにするので、理解負債と意図負債になる。
- **直し方**: 入口に、言語標準の例外を使ったガード節を置く。独自の検証の仕組みは作らない。

```csharp
/// マウスで選んだマスなど、指定の位置へ動かす。
/// 前提条件: position は board の中にある。
public void MoveTo(CellPosition position, Board board)
{
    ArgumentNullException.ThrowIfNull(board);
    if (!board.Contains(position))
        throw new ArgumentOutOfRangeException(nameof(position), position, "盤面の外の位置です。");
    Position = position;
}
```

- 盤面の外の位置を渡すのは、呼び出し元の不具合である。だから、黙って無視したり、端に寄せたり（クランプ）はしない。この 2 つは不具合を隠す。「盤面の外を押したら何もしない」という振る舞いが要るなら、それは呼び出し元（画面側）の仕様として、呼び出し元で `board.Contains` を確かめて決める。
- 単体テストを 1 件足す。盤面の外の位置（例: `(-1, 0)`、`(Width, 0)`）を渡すと `ArgumentOutOfRangeException` になり、`Position` は変わらないことを確かめる。これで契約がテストでも表せる。

### 指摘 2: `MoveTo` の `board` 引数が使われていない

`BoardCursor.MoveTo`: 使われていない引数（`board` を受け取るが本体は `Position = position` だけ）→ 指摘 1 のガード節で使う（指摘 1 を直せば解消する）。

- **分類**: 七箇条の「意図を表現」（意図にない記述＝ノイズ）。
- **根拠**: 引数の並びだけを読むと、盤面に照らして確かめているように見えるが、実際は確かめていない。名前と引数が約束する内容と、中身が食い違っている。
- **補足**: 設計書の考えのまま（確かめない）にするのなら、`board` 引数を消すのが筋である。ただし指摘 1 のとおり、公開の型では確かめる方を勧める。

### 指摘 3: 盤面が変わったときに、`Position` を盤面の中に戻すのが誰の責任かが書かれていない

`BoardCursor`（設計書）: 不変条件を守る責任の所在が不明（盤面は呼び出しごとに引数で渡すので、盤面が小さく変わると、保持している `Position` が新しい盤面の外に残りうる）→ 設計書に責任の所在を書く。

- **分類**: 整合（七箇条の外。設計書の記述の欠け）。
- **根拠**: 上級（30×16）で `(29, 15)` にあったカーソルが、初級（9×9）に変えた後も残っていると、次の `Move` や描画は盤面の外から始まる。`Board` を持たずに引数で受け取る形は悪くない。しかしその場合、「新しいゲームのとき、カーソルはどうなるか」を決めておかないと、不変条件が守られない。
- **直し方**（どちらかを選び、設計書に書く）:
  - 案 A（勧める）: 新しいゲーム（盤面）ごとに `BoardCursor` を作り直すと決め、その責任を `GameSession` などゲームの始まりを持つ側に置くと書く。`Position` の既定値 `(0, 0)` はどの盤面にも入るので、クラスに何も足さなくてよい。
  - 案 B: 3 つの版が盤面の作り直しのときにカーソルを残すなら、`Reset()`（左上に戻す）を足し、呼ぶ場所を設計書に書く。

  どちらも、今の計画に書かれていることの範囲で済む。盤面を持たせてカーソルが盤面の変化を監視するような仕組みは、要求がないので足さない。

## 置いた仮定

- `Board.Contains(CellPosition)` は盤面の中かを返し、`CellPosition` は値型（既定値は `(0, 0)`）で、盤面の大きさは 1×1 以上であると仮定した。
- `Move` の実装は、「動かした先が `board.Contains` なら動かし、外なら止まる」と仮定した。この場合、`Move` は今の位置が盤面の中であることを前提にしている。
- 盤面の外の位置を渡すことを、呼び出し元の不具合（契約違反）とみなした。画面の仕様として「盤面の外を押したら無視する」が要るときも、その判定は呼び出し元に置くと考えた。

## 問題のない点（参考）

- 名前 `BoardCursor`、`Move`、`MoveTo`、`Position` は利用者の関心を表していて、実装を名前に出していない。
- `Position` の setter を private にし、状態を変えるのをメソッドに限っているので、不変条件を守る場所がクラスの中に閉じている。指摘 1 を直せば、その形が生きる。
- `Board` を持たずに引数で受け取るのは、カーソルと盤面の寿命を結び付けない単純な形であり、3 つの版で共有しやすい（ただし指摘 3 の決めごとが要る）。
