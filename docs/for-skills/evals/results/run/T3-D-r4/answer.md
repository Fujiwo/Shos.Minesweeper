# T3: `BoardCursor` のクラス設計のレビュー

## レビュー対象の意図(一言で)

`BoardCursor` は「盤面の中の 1 マスを指す、キーボード操作用の選択位置」であり、3 つの版が共有する公開の型である。`Move` は端で止まり、`MoveTo` は指定の位置へ移す。

## 結論

指摘がある。主な指摘は 1 件（`MoveTo` のガード節の省略）で、それに付随する指摘が 2 件ある。

---

## 指摘 1（主）: `MoveTo` に前提条件のガード節がない

**書式**: `BoardCursor.MoveTo`: 前提条件が暗黙（盤面の中の位置しか来ない、という契約がコードになく、呼ぶ側の善意に頼っている。受け取った `board` も使われていない）→ ガード節の導入（`board.Contains` で前提条件を入口で検証する）

- **七箇条**: Testable（前提条件が明示されていない）。あわせて七箇条の外の「正しさ」（公開の境界での不変条件の破れ）
- **根拠**
  - `BoardCursor` は 3 つのアプリが使う共有ライブラリの**公開の型**である。「呼ぶ側が盤面の中の位置しか渡さない」は、今の呼び出し元についての観察であって、型の契約ではない。呼び出し元は 3 つあり、今後も増えうる（デスクトップ版のマウスの座標からマスへの換算、コンソール版の入力など、Web 版の「描画したマスを押す」以外の経路で位置を作る版がある）。換算の誤り（盤面の余白を押した、難易度を変えた直後の古い位置など）があると、盤面の外の位置が黙って `Position` に入る。
  - 盤面の外に入った後の害は、`MoveTo` ではなく離れた場所で出る。`Move` は `board.Contains` で「次の位置が盤面の中か」を見て止まるので、外にいるカーソルは動けなくなるか、外を動き続ける。表示やマスを開く処理は範囲外の位置で例外になる。原因（`MoveTo` の呼び出し）と症状が離れ、エラーの滞在時間が長くなる。
  - 設計書は、ガード節を置かないことを「引き算」と説明しているが、これは引き算の対象の取り違えである。引き算で削るのは「要求にない入力や状況をわざわざ処理する分岐」であり、**公開の境界での前提条件のガード節は契約の明示（説明責任の実行形）で、削る対象ではない**。ガード節は、盤面の外の位置を「処理する」（丸める、無視する）ものではなく、「前提が破れたことをその場で知らせる」ものなので、問題を複雑にしない。
  - `MoveTo(CellPosition position, Board board)` は `board` を受け取りながら使っていない。シグネチャーは「盤面に照らして動かす」と読めるのに、中身はただの代入であり、名前・引数と振る舞いが食い違っている（使われない引数）。
- **直し方**: 前提条件を入口のガード節で検証し、本処理は一本道の代入のままにする。言語標準の例外を使い、独自の検証の仕組みは作らない。

```csharp
/// マウスで選んだマスなど、指定の位置へ動かす。
/// 前提条件: position は board の中にある。
public void MoveTo(CellPosition position, Board board)
{
    if (!board.Contains(position))
        throw new ArgumentOutOfRangeException(nameof(position), position, "盤面の外の位置には動かせない。");
    Position = position;
}
```

- 設計書の説明は、「呼ぶ側は盤面の中の位置だけを渡す。これは `MoveTo` の前提条件で、破れていれば `ArgumentOutOfRangeException` で知らせる」に書き換える。
- 盤面の外の位置を最寄りのマスに丸める（`Clamp`）直し方は取らない。要求にない入力を黙って処理する分岐になり、呼び出し元の換算の誤りを隠すからである。
- **テスト**（xUnit の単体テストで確かめる）: 盤面の中の位置で `Position` が変わること、盤面の外（負の行、列数と同じ列など、境界のすぐ外）で `ArgumentOutOfRangeException` になり `Position` が変わらないこと。

## 指摘 2（付随）: 盤面を持たないので、「カーソルは盤面の中にある」という不変条件を型が保てない

**書式**: `BoardCursor`: 不変条件が成立しない構造（`Position` は盤面の中にあるべきだが、盤面は呼び出しのたびに引数で渡されるだけで、別の（小さい）盤面で `Move` を呼ぶと、前の盤面の位置のまま始まる）→ 不変条件をどこで保つかを決める

- **七箇条の外**: 正しさ（不変条件）
- **根拠**: 難易度を上級から初級に変えたとき、`Position` が (20, 25) のまま残ると、新しい盤面では外である。指摘 1 のガード節は `MoveTo` の入口しか守らない。
- **直し方（二案。今の設計を大きく変えない案 A を推す）**
  - 案 A: `Move` の入口にも同じ前提条件（`board.Contains(Position)`）のガード節を置き、新しいゲーム（盤面の作り直し）のときにカーソルを作り直すか、左上へ戻すことを、呼ぶ側（`GameSession` など、ゲームの始まりを知る者）の責務として設計書に書く。
  - 案 B: `BoardCursor` がコンストラクタで盤面（または盤面の寸法）を受け取り、不変条件をコンストラクタで成立させる。`Move`・`MoveTo` から `board` の引数が消え、契約が型に入る。新しいゲームでは新しいカーソルを作る。ただし 3 つの版の呼び出し方が変わるので、今の設計書の範囲で決められるなら案 B、呼び出し元の設計が固まっていないなら案 A とする（判断はユーザーに委ねる）。

## 指摘 3（小）: 前提条件が文書のコメントに書かれていない

**書式**: `BoardCursor.MoveTo` の XML コメント: 意図の欠落（「マウスで選んだマスなど」は用途の例で、契約（何を期待し、何を保証するか）がない）→ 前提条件と例外をコメントに書く

- **七箇条**: 意図を表現
- **直し方**: 指摘 1 のコード例のように、`/// 前提条件: position は board の中にある。` と、`<exception cref="ArgumentOutOfRangeException">` を書く。「マウスで」は利用者固有の事情なので、要約は「指定のマスへ動かす」にしてよい。

---

## 指摘しなかったもの

- `Move` の「端で止まる」振る舞いと、その判定を `board.Contains` に任せる形は、判定に必要な情報を持つ盤面に判定を任せており（Expert）、問題はない。
- 名前（`BoardCursor`、`Move`、`MoveTo`、`Position`）は、利用者の関心を表しており、実装の事情は漏れていない。

## 置いた仮定

- `Board.Contains(CellPosition)` は「その位置が盤面の中か」を返す公開のメソッドである。
- `Nullable` が有効なので、`board` の null の検査（`ArgumentNullException.ThrowIfNull`）は型に任せ、必須の指摘にはしなかった。共有ライブラリを Nullable の無効なアプリから呼ぶ計画があれば、足す。
- `CellPosition` は行と列を持つ値型で、負の値を取りうる。
