# T5 変更のレビュー: `InputText.Normalize`

## 読んだスキルの範囲
SKILL.md の表の「レビュー(ユーザーから依頼されたとき)」に従い、quality-gates.md の「七箇条をレビューの観点にする」と、refactoring.md の「コードの臭い」「臭い → 技法の対応表」を読んだ。レビュー対象にテストが含まれるので、testing.md も読んだ。

## 変更の意図（一言で）
利用者が入力した文字列を、解釈する前に整える（前後の空白を除き、全角数字を半角にする）。これで、カスタムの盤面の幅などに「３０」と入れても受け付けられるようにする。

## 結論
このままでは取り込まない。一番大きな問題は指摘 1 である。テストが Green になったのは PC の .NET だけで、このコードが実際に動くのはブラウザーの .NET（WebAssembly）である。そのため、「全テストが Green」だけでは、Web 版で動くかどうかは分からない。

---

## 指摘

### 1.【重大・正しさ（実行環境の差）/ Testable】ブラウザーの .NET で `Normalize(FormKC)` が動くか確かめていない
- `InputText.Normalize`: 検証した環境と動く環境が違う（テストは PC の .NET 10 で動くが、Web 版はブラウザーの WebAssembly の .NET で動く。そこでは globalization が縮小されているか、invariant になっている）→ 本物の実行環境で確かめ、足りなければ変換の置き場所を実行環境ごとに分ける
- 問題: ブラウザーの .NET は、globalization のデータ（ICU）を削ったり、invariant モードで動いたりする。そのため、`string.Normalize` の FormKC/FormKD は `PlatformNotSupportedException` を投げるおそれがある。変換されないまま文字列が返るおそれもある。もしそうなら、Web 版ではカスタムの入力で例外が起き、画面が止まる（Blazor の未処理例外）。つまり、この変更の目的の「３０を受け付ける」が、肝心の Web 版で果たせない。デスクトップ版では問題なく動く見込みだが、共有のライブラリに置いたことで、「どこでも動く」と思い込みやすくなっている。
- 作者の「全テスト Green」は正しいが、この点を何も確かめていない。Red→Green を見たのも PC の上だけである。
- 取り込む前にすべきこと:
  1. Web 版をブラウザーで動かし（`dotnet run` と、`dotnet publish -c Release` で発行したものの両方。発行の設定によって globalization が変わるため）、カスタムの入力に「３０」「 16 」を入れて確かめる。PC の Chrome/Edge/Firefox と iOS の Safari で行う。
  2. 例外になる場合や、変換されない場合は、次のどれかを選ぶ（ユーザーの判断が要る）。
     - (a) Web 版だけ、ブラウザー側の JavaScript（`text.trim().normalize("NFKC")`）で整えてから C# に渡す。デスクトップ版は `InputText.Normalize` を使う。「整え方の規則」が二か所に分かれるので、どちらも同じ表でテストし、なぜ分けたかを Why のコメントか設計書に残す。
     - (b) 目的が全角数字だけなら、FormKC を使わずに、U+FF10〜U+FF19 を '0'〜'9' に写す変換を自前で書く。これならどの実行環境でも同じに動き、指摘 3 も同時に解ける。
     - (c) Web 版の globalization の設定を変えて、正規化のデータを入れる。発行物が大きくなるので、トレードオフを示して決める。
  3. 選んだ方式で、Web 版の実行環境で振る舞いを押さえる確認を足す（bUnit の結合テストだけでは WebAssembly の実行環境の差は出ないので、ブラウザーでの確認を手順に入れる）。

### 2.【正しさ（契約とガード節）/ Testable】`null` を渡したときの契約が決まっていない
- `InputText.Normalize(string text)`: 前提条件が明示されていない（`text` が `null` なら `NullReferenceException` になる）→ 契約を決めてガード節で表す
- 問題: Blazor の `@bind` は、入力の状態によって `null` を渡しうる。そこで `NullReferenceException` が出ると、原因が分かりにくい。`Nullable` を有効にしていても、実行時に `null` が来るのを止めることはできない。
- 取り込む前にすべきこと: 契約を一つに決める。「`null` は空文字列として扱う」か、「`ArgumentNullException.ThrowIfNull(text)` で拒む」かのどちらかである。決めた契約をテストに一件足す。どちらにするかは、呼び出し側（カスタムの入力）の作り次第で決める。

### 3.【整合（仕様との整合）/ 意図を表現】FormKC の変換の範囲が、目的の「全角数字」より広い
- `InputText.Normalize`: 意図と実装の範囲がずれている（目的は全角数字を受け付けることだが、NFKC は互換文字をすべて変換する）→ 受け付ける範囲を仕様として決め、テストの表に書く
- 問題: NFKC は、たとえば次のように変換する。「①」→「1」、「²」→「2」、「Ⅲ」→「III」、全角の「－」→「-」、「½」→「1⁄2」。このため、「①⑥」が 16 として受け付けられるなど、利用者の意図しない入力が数として通りうる。これを「寛容で良い」とするか、「余計」とするかは仕様の判断である。ただ、今のテストの名前は「全角数字と空白」を約束しているので、実装が約束より広いことが、コードからもテストからも読み取れない。
- 取り込む前にすべきこと: 受け付ける範囲をユーザーと決める。NFKC の範囲を丸ごと受け入れるなら、そう決めたことを Why として残す（「全角の英数・記号も含めて、見た目の同じ文字をそろえるため」など）。そのうえで、互換文字の代表を一件テストに足す（例: 「①」の期待値）。全角数字だけでよいなら、指摘 1 の (b) にする。

### 4.【正しさ（小）】`Trim` と `Normalize` の順序
- `text.Trim().Normalize(...)`: 空白を除いてから正規化している → 正規化してから空白を除く（`text.Normalize(...).Trim()`）ことを検討する
- 問題: 互換文字の中には、正規化すると空白を含む文字列になるものがある（例: 「¨」U+00A8 →「 ̈」）。これが端にあると、先に `Trim` しているので、変換の後に空白が残る。全角の空白 U+3000 や NBSP は `char.IsWhiteSpace` に入るので、今の順序でも除かれる。数の入力では影響は小さい。
- 取り込む前にすべきこと: 順序を「正規化 → Trim」に変えるか、今の順序にした理由を書く。指摘 1 で JavaScript の側に同じ変換を書く場合は、二か所の順序を必ず揃える（Once And Only Once）。

### 5.【Testable / テストケースの設計】テストの表に抜けと重なりがある
- `InputTextTests.NormalizesFullWidthDigitsAndTrims`: 一つのテストに二つの関心が入っている（全角の変換と Trim が一つの名前になっている）。さらに、代表値が重なっていて（「３０」と「１６」は同じ種類）、境界とエッジケースがない → 関心ごとにテストを分け、表を育てる
- 抜けているケース:
  - 全角の空白で囲まれた全角数字「　１６　」→「16」（日本語の IME で最も起きやすい入力で、二つの変換が重なる）
  - 空文字列「」→「」と、空白だけ「   」→「」。呼び出し側が「未入力」として扱えるかに関わる
  - `null`（指摘 2 で決めた契約）
  - 変換しない文字がそのまま残ること。例: 「abc」→「abc」、半角の「30」→「30」（何もしない場合の番人）
  - 互換文字の扱い（指摘 3 で決めた範囲）
- テスト名は、入力の状況と結果を言う文にする。例: `FullWidthDigitsBecomeHalfWidth`、`SurroundingWhitespaceIsRemoved`、`FullWidthSpaceIsRemoved`、`EmptyStaysEmpty`。
- 取り込む前にすべきこと: 上の表でテストを分けて足す。最初から通るものは、実装をわざと壊し（`Normalize` を外すなど）、失敗することを確かめてから戻す。

### 6.【整合 / Testable】呼び出し側で「３０を受け付ける」ことを確かめるテストがない
- 変更の全体: 目的を満たしたかを確かめていない（テストは部品の変換だけで、カスタムの入力が「３０」を幅 30 として受け付けるかは確かめていない）→ 呼び出し側の結合テストを足す
- 問題: 変更の目的は「全角の３０を受け付ける」ことである。この差分には、`InputText.Normalize` を呼ぶ側（カスタムの入力の解釈）が見えない。呼び忘れたり、`int.Parse` などが先に走ったりしても、今のテストは Green のままである。
- 取り込む前にすべきこと: 呼び出し側の差分をレビューに含める。カスタムの入力のコンポーネント（bUnit）かビューモデルに、「幅に『３０』を入れると 30 の盤面になる」テストを一件足す。デスクトップ版でも使うなら、デスクトップ版の呼び出し側にも同じテストを足す。

### 7.【的確な名前（軽微）】`InputText.Normalize` という名前が `string.Normalize` と重なる
- `InputText.Normalize`: 同じ名前で意味が違う（`string.Normalize` は Unicode の正規化だけを行うが、こちらは Trim も行う）→ 今のままでもよいが、違いを XML ドキュメントのコメントに一行書く
- 問題は小さい。ただ、読み手が中で `string.Normalize` を呼んでいるのを見ると、「Trim もしている」ことを見落としやすい。名前を変える（例: `InputText.Clean`、`ForParsing`）かどうかは、既存の流儀に合わせて決めればよく、必須ではない。

## 取り込む前にすべきことのまとめ（優先順）
1. Web 版を本物のブラウザー（開発のビルドと発行物の両方）で動かし、FormKC が例外にならず変換されるかを確かめる。だめなら、方式 (a)(b)(c) の中からユーザーが選ぶ。（指摘 1）
2. 受け付ける範囲（NFKC の全部か、全角数字だけか）と、`null` の契約を決める。（指摘 2、3）
3. テストの表を関心ごとに分けて足し、呼び出し側の結合テストを一件足す。（指摘 5、6）
4. 必要なら、Trim の順序を揃え、名前の違いをコメントに書く。（指摘 4、7）

## 置いた仮定
- 差分に見えない呼び出し側（カスタムの入力の解釈）は、この変更で `InputText.Normalize` を呼ぶように変わっているものとした。
- Web 版の発行の設定（`InvariantGlobalization`、`BlazorWebAssemblyLoadAllGlobalizationData` など）は分からない。そのため、指摘 1 は「例外になるおそれがあり、確かめるまで分からない」として挙げた。この環境ではブラウザーで動かしていない。

## ユーザーの判断が要る点
- 指摘 1 で動かなかったときの方式: (a) JavaScript で整える、(b) 全角数字だけを自前で変換する、(c) globalization のデータを入れる。
- 指摘 3 の、受け付ける文字の範囲。
