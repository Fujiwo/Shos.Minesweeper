# T5 変更のレビュー（InputText.Normalize）

## 結論
**このままでは取り込めない。** 最大の問題は、テストが Green なのは PC の .NET の上だけで、この変更が実際に動く場所（ブラウザーの中の .NET、WebAssembly）では動く保証がないことである。

## 仮定
- Web 版は既定の設定で発行する（グローバリゼーションは invariant モードか、ブラウザー向けの縮小した ICU を使う）。
- 盤面の幅などの入力は、Blazor の `@bind` で `string?` として受け、`int.TryParse` で解釈する。

---

## 指摘 1（正しさ・実行環境の差。重大）ブラウザーの .NET で `Normalize(FormKC)` が動かないおそれ
- **問題**: `string.Normalize` は OS か ICU の機能に頼る。Blazor WebAssembly の .NET は ICU を小さくしているか、invariant モードで動くことがあり、NFKC の正規化は `PlatformNotSupportedException` になりうる（少なくとも PC と同じ結果になる保証はない）。このコードは Web 版とデスクトップ版が共有する Presentation にあるが、テストは PC の `dotnet test` だけで動かしている。「全テストが Green」は、Web 版で動くことの根拠にならない。例外になれば、カスタムの入力を確定した瞬間に画面が壊れる（Blazor の未処理例外の表示になる）。
- **取り込む前にすべきこと**:
  1. 発行した Web 版（`dotnet publish -c Release` の結果を静的に配信したもの）をブラウザーで開き、カスタムの幅に「３０」と入れて確かめる。`dotnet run` の開発ビルドだけでなく、発行物で確かめる（発行の設定でグローバリゼーションの扱いが変わるため）。
  2. 動かなかった場合の方針を決める。案は次のどちらか。
     - (a) 正規化に頼らず、必要な変換だけを自前で行う: 全角数字 `U+FF10`〜`U+FF19` を `'0'`〜`'9'` に、全角の空白やマイナス（`U+3000`、`U+FF0D`）を半角に置き換える。どの実行環境でも同じに動き、PC のテストがそのまま根拠になる。**要求（全角の「３０」を受け付ける）にはこれで足り、最も単純である。**
     - (b) NFKC が必要なら、Web 版だけ JavaScript の `String.prototype.normalize("NFKC")` を JS interop で呼び、デスクトップ版は .NET の `Normalize` を使う。この場合、「どの環境でも同じ変換」を 1 か所に置けなくなるので、両方の実装を同じテストケースで確かめる仕組み（少なくとも手での確認の項目）が要る。
  3. ブラウザーで動くことを確かめたら、その結果（どのブラウザー、発行物か開発ビルドか）を変更の説明に書く。

## 指摘 2（正しさ）`null` を渡すと `NullReferenceException`
- **問題**: Blazor の入力欄は空のとき `null` を渡しうる。`text.Trim()` がそこで落ちる。Nullable が有効なら引数が `string` なので呼ぶ側で警告は出るが、`@bind` 経由では気づきにくい。
- **取り込む前にすべきこと**: 契約を決める。`null` を空文字として扱う（`text ?? ""`）か、ガード節で `ArgumentNullException` を投げて呼ぶ側で空を処理するかのどちらかにし、その振る舞いをテストに足す。

## 指摘 3（正しさ）Trim と正規化の順序
- **問題**: 先に `Trim` し、後で正規化している。正規化によって空白に変わる文字が端にあると、正規化の後に空白が残りうる（例: `U+00A0` は `char.IsWhiteSpace` で消えるが、NFKC で空白になる互換文字は他にもある）。全角の空白 `U+3000` は `Trim` で消えるので今回の主な場面は通るが、順序として脆い。
- **取り込む前にすべきこと**: 正規化してから `Trim` する（`text.Normalize(...).Trim()`）。指摘 1 で (a) を選ぶなら、置き換えの後に `Trim` する。

## 指摘 4（テスト）Red を見た根拠と、テストの網羅が弱い
- **問題**:
  - 「Red を見てから実装した」のは PC の上であり、ブラウザーで壊れる場合の Red はどのテストでも見えない（指摘 1）。自動テストで捕まえられない以上、手での確認を手順に入れる必要がある。
  - ケースが全角数字と半角の空白だけで、全角の空白（`"　１６　"`）、空文字・空白だけ、`null`、全角のマイナス（`"－５"`。解釈の側で弾くべき値）が無い。
  - テスト名が「全角数字と Trim」だが、NFKC は数字以外も変える（`"①"` → `"1"`、`"¹"` → `"1"`、`"½"` → `"1⁄2"`）。これらを受け付けてよいかが決まっていない。`"①６"` が `16` として通るのは、意図した仕様か確認が要る。
- **取り込む前にすべきこと**: 上のケースを足す。NFKC の副作用（丸数字・上付き数字を数字と見なす）を受け入れるか決め、受け入れないなら指摘 1 の (a) を選ぶ理由がさらに強くなる。

## 指摘 5（整合）呼ぶ側と置き場所
- **問題**: 差分に呼び出し側が無い。どの入力欄（幅・高さ・地雷数の全部か）で、解釈の前に必ず通るのかが確かめられない。また、デスクトップ版が使うと書かれているが、デスクトップ版で呼ぶ箇所も無い。
- **取り込む前にすべきこと**: 呼び出し側の変更（カスタムの入力の解釈の直前）を同じ変更に含め、「全角で入れて確定すると盤面が変わる」ことをコンポーネントのテスト（bUnit）か実機で確かめる。整える処理を 1 か所に置く方針なら、各 UI で独自に `Trim` していた箇所があれば消す。

## 取り込む前の作業のまとめ
1. 発行した Web 版をブラウザーで動かし、`Normalize(FormKC)` が例外にならないか確かめる（指摘 1）。
2. 動かなければ、全角数字などの置き換えを自前で書く方式に替える（推奨）。どちらにするにしても、選んだ理由を説明に書く。
3. `null` の契約、正規化と `Trim` の順序を直す（指摘 2、3）。
4. テストケースを足し、NFKC の副作用を受け入れるか決める（指摘 4）。
5. 呼び出し側を含め、実機で全角の「３０」が通ることを確かめる（指摘 5）。
