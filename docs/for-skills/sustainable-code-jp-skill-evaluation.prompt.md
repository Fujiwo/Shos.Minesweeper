# 依頼: スキル sustainable-code-jp の評価と改善案

## 目的

`.claude/skills/sustainable-code-jp/`（SKILL.md と references/ の 10 ファイル）が、AI 駆動のソフトウェア開発（AI エージェントが設計・実装・テスト・レビューを行い、人間が承認する形）で、どれだけ役に立っているかを評価したい。そのうえで、改善案を作りたい。
この評価の結果で、改善案のどれをスキルに入れるかを私が決める。

## 対象と時点

- 評価の対象は、今のコミットのスキルである（docs/reviews/skill-evaluation.md の 11.8 で S1〜S3、S5〜S9 を入れ、docs/reviews/skill-review.md の 6 章で指摘 1〜5 を反映した後）。始めるときに、ファイルごとの行数とバイト数を数え直して書く
- 記録（skill-log.md など）は、ほとんどが改良の前のスキルで取ったものである。改良の後のスキルは、まだ一巡も使っていない。そのため、S1〜S9 の効果は「未測定」と書き、記録から推して言えることは「推測」と書く
- 範囲は 3 つの一巡（Web 版 1.0.0、1.1.0、デスクトップ版・コンソール版）の全体である

## 前提（すでにあるもの）

- これまでの評価: docs/reviews/skill-evaluation.md（1〜11 章）、docs/reviews/skill-log.md、docs/reviews/skill-review.md
- 上の文書にある結論をやり直さない。章と節の番号で引用して使い、新しい根拠で変わる点だけを書く。記録の判定の区分（skill-log.md の「判定の区分」）も、新しい根拠なしに付け直さない
- 根拠の文書は、ほかに docs/reviews/ と docs/desktop-console/reviews/ の各レビュー、git log を使ってよい。会話の記録（`~/.claude/projects/` の jsonl）を使うときは、skill-evaluation.md の 1.1 と同じく「リポジトリに残っていない根拠」と書き分ける
- スキルのファイルは編集しない（`.claude/settings.json` の `deny` で禁じている）。Bash で書き換えることもしない。案を書くだけにする
- 英語版（sustainable-code）は評価の対象外とする。日本語版を改良した後に合わせる（CLAUDE.md の決定）。ただし、改善案の見込みには、英語版に合わせる手間があることを含めてよい
- 書くのは docs/reviews/skill-evaluation.md だけである。コミットはしない

## 指標と測り方

各指標で、根拠（ファイルと行、記録の番号、数）を示す。根拠のない判定は「推測」と書き分ける。

1. 有用性: 作業の種類（SKILL.md の作業の表の行。設計の相談、新機能の実装、命名、テスト、レビュー、リファクタリング、バグ修正、性能）ごとに、スキルが AI の判断を変えたか・変えなかったか
   - 変えなかった部分も挙げる。reference ごと・節ごとに、3 つの一巡で読まれた回数と、判断に引かれた回数を数え、一度も読まれない・引かれない reference と節を一覧にする
2. 効果: スキルがあることで、成果物の品質（不具合、レビューの指摘、変更のしやすさ）がどう変わったか
   - 効果に数えるのは、判定の区分が「スキル」のものだけである。「スキルなし」「判別できない」と、CLAUDE.md の規則（P1〜P5）から出たものは数えない。CLAUDE.md の規則がスキルから写したものかどうかは、skill-evaluation.md の 1.2 の分け方に従う
3. トークンコスト:
   - 常に文脈にある部分（description）、起動したときに読む部分（SKILL.md。frontmatter を除く）、必要なときに読む部分（reference）に分けて見積もる
   - バイト数と文字数を数え、トークン数への換算の仕方（使った換算の比と、その出どころ）を書く。トークナイザーで数えられないときは、換算した数が概算であることを書く
   - 1 回の作業あたりの読み込み量は、作業の種類ごとに「必ず読む」の reference の大きさと、記録にある実際の読み込みから出す
   - 効果に対して割に合うかを、作業の種類ごとに判断する
   - 削っても効果が落ちない部分（重複、AI がもともと知っている一般論、3 つの一巡で読まれも引かれもしなかった節）を挙げ、削ったときの減る量を概算する。「AI がもともと知っている」は、推測であることを書く

## 一般的なやり方との比較

AI 駆動開発で広く勧められているやり方と、このスキルを比べる。

- 比べる相手（一次情報を優先し、出典の URL と確かめた日を書く）:
  - Anthropic のスキルの書き方の指針（Agent Skills の概要とベストプラクティス、skill-creator のスキルの考え方）
  - Anthropic の CLAUDE.md・プロンプトの書き方の指針（Claude Code のメモリーの文書、プロンプトエンジニアリングの文書）
  - AI エージェント向けの指示ファイルの一般的な慣習（AGENTS.md、Cursor rules など）。二次情報は、一次情報と食い違うときだけ挙げる
- 出典は、この会話でウェブから取得して確かめたものだけを使う。取得できなかったものは、記憶で補わずに「確かめられなかった」と書き、比較の表からも外す
- 比べる観点（少なくとも次のもの）:
  1. 長さと簡潔さ（SKILL.md の行数の目安、AI がもともと知っていることを書いていないか）
  2. 段階的な読み込み（SKILL.md から reference への分け方、参照の深さ、何を読むかの決め方）
  3. description（起動の条件の正確さ、常に文脈にある長さ。3 つの一巡で、呼ぶべきときに呼ばれなかった・呼ぶべきでないときに呼ばれた記録があるか）
  4. 指示の形（規則を並べるか、判断の手順・例・チェックリストを示すか。作業の壊れやすさに合わせた自由度）
  5. 検証の仕組み（スキルの効果を評価の課題で測っているか、改良のたびに確かめているか）
  6. 役割の分担（スキルに置くべきものと、CLAUDE.md・フック・リンターなどに置くべきもの）
- 観点ごとに「一般的なやり方」「このスキル」「差」「差を埋めるべきか」を表にする
  - 一般的なやり方に合わせないほうがよい点（このスキルの意図的な設計）は、理由を付けて「合わせない」と書く
  - 外部の指針は、それだけで改善の根拠にしない。このプロジェクトの記録と合わせて判断する。記録の裏付けがなく外部の指針だけに基づく案は、優先度を「低」以下にし、根拠の列にそう書く

## 評価の限界として書くこと

- 事例はこのプロジェクト 1 つだけである（言語は C#、作業は 1 人のユーザーの承認のもとで行った。一般化できる範囲を書く）
- 評価するのはスキルを使った AI 自身である（自己評価の偏り）。偏りを減らすために取ったこと（例: 結論を、この会話の文脈を持たないサブエージェントに反証させた）と、取れなかったことを書く
- 改良の後のスキルは、まだ使われていない（「対象と時点」）
- 外部の指針は時期によって変わる（確かめた日を書く）

## 成果物

docs/reviews/skill-evaluation.md に「12. AI 駆動開発の観点からの評価（指標: 有用性・効果・トークンコスト）」の章を足す。文体と表の形は 11 章に合わせる。冒頭の表の「範囲」と「状態」の行にも、12 章を足したことを書く。

- 12.1 要約（結論を 5 行以内で）
- 12.2 有用性、12.3 効果、12.4 トークンコスト（それぞれ表を使う）
- 12.5 一般的なやり方との比較（観点ごとの表と、出典の一覧。出典には URL と確かめた日を書く）
- 12.6 改善案: 1 行に 1 案で表にする
  - 列は #、対象ファイル、案、効く指標、根拠（記録 / 外部の指針）、見込み（トークンの増減の概算を含む）、優先度
  - 番号は、11 章の S1〜S9 と重ならないように S10 から振る。S4（保留）を見直すときは、その番号のまま書く
  - 優先度の「高」の案には、11.5 と同じく差分（diff）を示す
- 12.7 見送る案とその理由
- 12.8 次の一巡で確かめる方法
  - 改善の効果を測る記録の取り方（skill-log.md の「書くきっかけ」「一巡の最後に数えるもの」に足すもの）
  - 評価の課題を作って、改良の前後で比べる方法: 課題の数と中身（このプロジェクトの記録にある場面から選ぶ）、スキルあり・なし・改良の前後の比べ方、判定の基準、1 つの課題を何回流すか、かかる費用の概算
- 12.9 ユーザーに決めていただくこと（11.7 と同じ形。決めることと推す案）

## 進め方

1. 先に、評価の進め方を短く示し、私の承認を得る。示すもの:
   - 読むファイルと、読む範囲（全部を読むか、節を選ぶか）
   - 調べる外部の資料と、その探し方
   - 数の取り方（何を、どの記録から、どう数えるか。トークン数への換算の仕方）
   - 自己評価の偏りを減らす手立て
   - 本文の分量の見込み
2. 承認の後に、本文を書く。書き終えたら、根拠として挙げた記録の番号・行・数が実在するかを確かめてから報告する
3. 報告では、12.1 の要約と 12.9 の決めていただくことを示す
