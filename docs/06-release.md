## 1. 概要

Web 版の最初の版（1.0.0）を、GitHub Pages のプロジェクト サイトとして公開するための手順と確認項目をまとめる。

1.1.0（UI の洗練と効果音）の公開は、同じ手順で行う。1.1.0 で変わるところ（版、確認項目、公開後の確認）は 9 章にある。1〜8 章の 1.0.0 の値（テストの件数、タグの名前など）は、1.1.0 では 9 章の値に読み替える。

| 項目 | 内容 |
|------|------|
| 公開する版 | 1.0.0（git のタグは `v1.0.0`） |
| 公開先 | `https://fujiwo.github.io/Shos.Minesweeper/`（仕様書 7 章） |
| リポジトリ | `https://github.com/Fujiwo/Shos.Minesweeper`（公開リポジトリ。既定のブランチは `main`） |
| 公開の方法 | GitHub Actions のワークフロー（`.github/workflows/deploy.yml`）を、手動で起動する |
| 公開物 | `dotnet publish -c Release` の `wwwroot` を、サブパス用に整えたもの（3 章） |

公開の操作（push、ワークフローの起動、タグ付け）は、リリースレビューが承認され、ユーザーが明示的に指示したときだけ行う（CLAUDE.md）。

## 2. この工程で決めたこと

| # | 決めたこと | 理由 | 見送った案 |
|---|------------|------|------------|
| 1 | 公開は GitHub Actions で行い、ワークフローは手動でだけ起動する（`workflow_dispatch`） | 発行、`<base href>` の書き換え、配置を毎回同じ手順で行える。公開の前に全テストを流すので、Red のまま公開できない。push では動かないので、「公開はユーザーの指示のときだけ」（CLAUDE.md）を守れる | 手作業で発行して `gh-pages` ブランチに push する（手順を誤りやすい）。`main` への push で自動で公開する（指示のない公開になる） |
| 2 | 版は 1.0.0 とする | 仕様書の機能をすべて満たす最初の公開版である | 0.x（機能がそろっているので、試作の版にする理由がない） |
| 3 | ブラウザーのタブのアイコン（ファビコン）を、ゲームの地雷と同じ形の SVG（`wwwroot/favicon.svg`）にする。テンプレートの `icon-192.png`（Blazor のロゴ。どこからも参照されていない）は消す | 公開する物にテンプレートのロゴを残さない。形をゲームのアイコンとそろえ、新しい絵を足さない。SVG なので大きさによらずにじまない（工程 12 で、扱いを工程 14 で決めると送った事項） | PNG の各サイズとホーム画面用のアイコンを作る（PWA は対象外なので要らない。仕様書 9 章） |
| 4 | 公開物に `404.html`（`index.html` の写し）を置く | GitHub Pages は、無い URL に GitHub の英語の 404 ページを返す。`404.html` を置くと、無い URL でもアプリが読み込まれ、アプリの日本語の「ページが見つかりません」（工程 11 の区切り 7 で作ったもの）が出る | 置かない（誤った URL を開いた人に、英語のページが出る） |
| 5 | 公開物に `.nojekyll` を置く | `_framework` のように `_` で始まるフォルダーを、Jekyll の処理にかけずにそのまま配るため（調査書 8.5）。Actions で配置する場合は Jekyll は動かないが、手作業で配置し直すことになっても同じ公開物で済むように置く | — |
| 6 | 発行が作る圧縮ファイル（`.br`・`.gz`）は、そのまま公開物に含める。書き換えた `index.html` の圧縮ファイルだけは消す | GitHub Pages は自分で gzip に圧縮して配るので、これらは使われないが、害もない。発行の設定を増やさない。`index.html` の圧縮ファイルは書き換える前の中身なので、残すと食い違う | 発行の設定で圧縮を止める（設定が増える割に、得るものがない） |

## 3. 公開物の構成

ワークフローの「公開用に整える」の手順で、発行した `wwwroot` を次のように整える。

| 対象 | 整え方 | 確かめ方 |
|------|--------|----------|
| `index.html` の `<base href>` | `/` を `/Shos.Minesweeper/` に書き換える。ソースの `index.html` は `/` のまま（ローカルの `dotnet run` のため。アーキテクチャー設計書 13 章） | 書き換えた後に `grep` で確かめ、無ければワークフローを失敗させる |
| `index.html.br`、`index.html.gz` | 消す（2 章の決定 6） | — |
| `404.html` | 書き換えた `index.html` を写す（2 章の決定 4） | — |
| `.nojekyll` | 空のファイルを置く（2 章の決定 5） | — |

そのほかに、ビルドが済ませていること:

- `index.html` のプレースホルダー（`<script type="importmap">`、`<link rel="preload" id="webassembly">`、`blazor.webassembly#[.{fingerprint}].js`）は、発行のときに .NET 10 が書き換える（CLAUDE.md の「構成とポイント」）。
- `js/browser.js` は相対パスで読み込むので、サブパスでも読み込める（アーキテクチャー設計書 16 章）。

大きさ（2026-09-26 の発行物）: 最初の読み込みで取る `_framework` は、圧縮しないと約 9.3MB、GitHub Pages が配る gzip で約 3.6MB である。

ローカルでの事前の確認（工程 14 で行った）: 発行物をワークフローと同じ手順で整え、GitHub Pages と同じく「サブパスの下でファイルを配り、無いパスには `404.html` を 404 の状態で返す」小さなサーバー（作業用のスクリプト）で配った。ヘッドレスの Chrome で、アプリが読み込まれてマスを開けること、`favicon.svg` が `image/svg+xml` で配られること、`/Shos.Minesweeper/no-such-page` と `/Shos.Minesweeper/a/b/c` でアプリの「ページが見つかりません」が出ることを確かめた。

## 4. 公開の手順（工程 16）

前提: リリースレビュー（工程 15）が承認され、ユーザーが公開を指示している。

| # | 手順 | 行う人 | 確かめること |
|---|------|--------|--------------|
| 1 | 公開する変更をコミットし、`main` を `origin` に push する（コミットと push はユーザーの指示で行う） | Claude（指示を受けて）かユーザー | `origin/main` に `.github/workflows/deploy.yml` がある |
| 2 | GitHub のリポジトリの Settings → Pages → Build and deployment → Source を「GitHub Actions」にする（初回だけ） | ユーザー | Pages の設定画面に、公開先の URL が表示される |
| 3 | Actions → 「GitHub Pages に公開」→ Run workflow（ブランチは `main`）で起動する | ユーザー（または、ユーザーの指示で Claude） | `build`（テスト・発行・整える・アップロード）と `deploy` が成功する。テストの件数が、ローカルの `dotnet test` と同じ |
| 4 | 公開後の確認（6 章）を行う | Claude とユーザー | 6 章の表のすべて |
| 5 | 確認が済んだら、公開したコミットに `v1.0.0` のタグを付けて push する（ユーザーの指示で行う） | Claude（指示を受けて）かユーザー | `origin` に `v1.0.0` のタグがある |
| 6 | 公開後の確認の結果を、docs/reviews/06-release-review.md に追記する | Claude | — |

- ワークフローで使う Actions の版は、`actions/checkout@v7`、`actions/setup-dotnet@v6`、`actions/upload-pages-artifact@v5`、`actions/deploy-pages@v5` である（2026-09-26 の 1.0.0 の公開の後に、Node.js 20 の廃止の警告を受けて、その時点の最新に上げた。docs/reviews/06-release-review.md）。手順 3 で「古い版」の警告が出たら、その版を上げてから起動し直す。`upload-pages-artifact` は v4 から `.` で始まるファイルを既定で含めないので、`.nojekyll` のために `include-hidden-files: true` を指定している。
- 手順 3 のワークフローが失敗したら、公開はされない（前の状態のまま）。ログを見て原因を直し、工程 15 の確認項目のうち、直した部分に関わるものを確かめ直してから起動し直す。
