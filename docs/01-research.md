## 1. 目的と範囲

Web ブラウザー（スマートフォン、タブレット、PC）で動くマインスイーパーを Blazor WebAssembly で作るにあたり、次の三つを調べて整理する。

- 定番のルールと慣習（プレイヤーが「マインスイーパーならこう動くはず」と期待するもの）
- タッチ端末と小さな画面での操作・表示の課題と、既存の解決パターン
- Blazor WebAssembly で実装するときに考慮すべき技術的な点

この調査書では決定は行わない。仕様書で決めるべき論点と選択肢を「9. 仕様書で決めるべき論点」にまとめる。

## 2. 背景

- Microsoft 版のマインスイーパーは、1990 年に Windows Entertainment Pack の一つとして Robert Donner と Curt Johnson が作った。その後 Windows に標準で付属し、広く知られるようになった。
- 源流には諸説ある。ZX Spectrum の *Mined-Out*（1983 年）や、SunOS の *Mines*（1987 年）などが先行例として挙げられる。
- 現在は、Web 版（Google 検索のミニゲームなど）、スマートフォンアプリ、競技用のクローン（*Minesweeper X* など）など、多くの実装がある。基本ルールはほぼ共通だが、細部（最初のクリックの扱い、タッチ操作など）は実装によって異なる。

## 3. 基本ルール

- 長方形の盤面のマスの一部に地雷が隠されている。プレイヤーは地雷の位置を知らない。
- マスを開くと、次のどれかになる。
  - 地雷のマスを開いた場合、ゲームオーバー（敗北）になる。
  - 周囲 8 マスに地雷がある場合、その数（1〜8）が表示される。
  - 周囲 8 マスに地雷がない場合（0）、周囲のマスが自動で連鎖的に開かれる。
- プレイヤーは、地雷があると推理したマスに旗を立てられる。旗を立てたマスは誤って開けなくなる。
- **地雷でないマスをすべて開くと勝利**になる。旗をすべての地雷に立てる必要はない。

## 4. 定番の難易度

| 難易度 | 盤面（幅×高さ） | 地雷数 | 地雷密度 |
|--------|------------------|--------|----------|
| 初級 | 9×9 または 8×8 | 10 | 12.3%（8×8 では 15.6%） |
| 中級 | 16×16 | 40 | 15.6% |
| 上級 | 30×16 | 99 | 20.6% |
| カスタム | 任意 | 任意 | — |

- 初級は、実装によって 8×8 と 9×9 の二通りがある。どちらが多数派かは、出典によって説明が食い違う（Wikipedia は両方を併記し、ThePuzzleLabs は「多くは 8×8、9×9 のサイトもある」としている）。
- カスタムでは、盤面の最小・最大サイズと、地雷数の上限を決める必要がある。例えば、最初のクリックのマスを必ず安全にする場合、地雷数は「マス数 − 1」以下でなければならない。周囲 8 マスも安全にする場合は「マス数 − 9」以下になる。
- 地雷密度が 25% 付近で相転移が起きることが知られている（Wikipedia）。カスタムの地雷数の上限を決めるときの参考になる。

## 5. 定番の機能と慣習

### 5.1 操作

| 機能 | PC での定番の操作 | 内容 |
|------|-------------------|------|
| 開く | 左クリック | マスを開く |
| 旗 | 右クリック | 旗を立てる・外す |
| ？マーク | 右クリック（旗の次） | 「未確定」の印。Windows 版では設定で有効にする任意の機能 |
| コード（chording） | 左右同時クリック、または中クリック。実装によっては、開いた数字のマスの左クリックでも行える | 開いた数字のマスの周りに、その数と同じ数の旗が立っているとき、残りの周囲のマスをまとめて開く。上級者にとっては必須の操作 |

- コードでは、旗の位置が間違っていると地雷を開いてしまい、敗北する。
- ？マークは、右クリックの状態を「なし → 旗 → ？ → なし」と巡回させる。

### 5.2 最初のクリックの安全保証

- 多くの実装では、**最初に開いたマスは必ず地雷でない**ようにしている。Windows 版では Vista で保証されるようになった。
- 実装によっては、さらに**最初のマスの周囲 8 マスも安全にする**。こうすると最初のマスは必ず 0 になり、ある程度の範囲が開いた状態から推理を始められる。
- これを実現するには、地雷の配置を「最初のクリックの後」に決めるのが最も簡単である（6.1 を参照）。

### 5.3 表示

- **残り地雷数**: 「地雷の総数 − 立てた旗の数」を表示する。旗を立てすぎるとマイナスになる。
- **経過時間**: 最初のクリックから計り始め、勝敗が決まったら止める。Windows 版は秒単位で、上限は 999 である。
- **リセット**: Windows 版では、盤面の上にある顔のボタンがリセットを兼ね、状態（通常、押下中、勝利、敗北）に応じて表情が変わる。
- **敗北時**: 次のように表示するのが定番である。
  - すべての地雷の位置を表示する。
  - 開いてしまった地雷を赤い背景などで強調する。
  - 誤った旗（地雷がないマスの旗）に × 印を付ける。
- **勝利時**: 残りの地雷のすべてに自動で旗を立て、残り地雷数を 0 にするのが定番である（出典未確認）。
- **数字の色**: 数字ごとに色を変えるのが定番で、Windows のクラシック版では次の色が使われる（出典未確認）。プレイヤーは色でも数字を読むので、この配色を踏襲するのが無難である。ただし、背景色とのコントラストは別に確かめる必要がある（7.5 を参照）。

| 数字 | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 |
|------|---|---|---|---|---|---|---|---|
| 色 | 青 | 緑 | 赤 | 紺 | 茶（えんじ） | 青緑 | 黒 | 灰 |

### 5.4 その他の機能（実装によってある）

- 難易度ごとのベストタイムの記録
- 統計（プレイ回数、勝率、連勝数）
- 「推理だけで必ず解ける盤面」を生成するモード（No Guessing モード。6.3 を参照）
- ヒント、やり直し（Undo）
- 盤面の難しさの指標（3BV。盤面を開き切るのに必要な最小クリック数）の表示。主に競技向けの機能

## 6. アルゴリズム

### 6.1 地雷の配置

- 候補となるマスの一覧から、Fisher–Yates シャッフルで一様ランダムに地雷数の分だけ選ぶのが標準的な方法である。
- 最初のクリックを安全にする場合、候補から「最初のマス」（またはその周囲 8 マスも含めて）を除いて選ぶ。このため、地雷の配置は最初のクリックの後に行う。
- テストしやすくするため、乱数源は外から差し替えられるようにしておくとよい。シードを固定した乱数を渡せば、同じ盤面を再現できる。

### 6.2 0 のマスの連鎖的な開放（フラッドフィル）

- 0 のマスを開いたら、周囲のマスを開き、その中にまた 0 があれば、そこからさらに広げる。
- 再帰で書くと、大きな盤面ではスタックが深くなる。キューを使った幅優先探索（BFS）で書くのが安全である。
- 旗の立っているマスは、連鎖では開かない。

### 6.3 推理だけで解ける盤面（No Guessing）

- 通常のランダム配置では、終盤に運で選ぶしかない局面（二択など）が生じることがある。
- それを避けるには、盤面を生成するたびにソルバーで「推理だけで解けるか」を確かめ、解けなければ作り直す方法がとられる。
- マインスイーパーの盤面の整合性を判定する問題は NP 完全であることが知られている（Kaye, 2000）。ただし実用上は、単純な制約の推論を組み合わせたソルバーで十分なことが多い。
- 実装の手間が大きいので、最初の版では対象外にすることが多い機能である。

## 7. タッチ端末と小さな画面

### 7.1 タッチでの操作パターン

スマートフォンには右クリックも中クリックもないので、「開く」と「旗」を区別する方法が必要になる。既存の実装では、主に次のパターンが使われている。

| パターン | 操作 | 長所 | 短所 |
|----------|------|------|------|
| A. 長押しで旗 | タップで開く。長押しで旗 | 覚えやすい。最も普及している | 長押しを待つので旗を立てるのが遅い。長押しが短すぎると、開くつもりで旗になる誤操作が起きる |
| B. モード切り替え | 画面上のボタンで「開く」と「旗」のモードを切り替え、タップはそのモードの動作をする | 操作が確実で、誤操作が少ない | 切り替えを忘れて誤って開き、地雷を踏みやすい。切り替えの手間が増える |
| C. A の逆 | タップで旗。長押しで開く | 誤って開くことが減る | 直感に反し、慣れが要る |
| D. A と B の併用 | 長押しで旗。加えて、モード切り替えのボタンも置く | 好みで選べる | UI の要素が増える |

- コードは、**開いた数字のマスをタップする**ことで行う実装が多い。
- A の長押しの判定時間は、300〜500 ミリ秒程度にする実装が多い（出典未確認）。長押しが成立したことを振動（Vibration API）や表示の変化で知らせると、誤操作が減る。Vibration API は iOS の Safari では使えない。

### 7.2 ブラウザーの既定の動作との競合

タッチ端末のブラウザーには、ゲームの操作とぶつかる既定の動作がある。

| 既定の動作 | 問題 | 対策 |
|------------|------|------|
| 長押しでの文字選択・コンテキストメニュー | 長押しで旗を立てようとすると、メニューや文字選択が出る | `contextmenu` イベントの既定の動作を止める。CSS の `user-select: none`（Safari 向けに `-webkit-user-select: none` も）と `-webkit-touch-callout: none` |
| ダブルタップでのズーム | 素早く 2 回タップするとズームしてしまう | CSS の `touch-action: manipulation` |
| スクロール・ピンチズーム | 盤面を指でなぞるとページがスクロールする。盤面が画面より大きいときは、逆にスクロールやズームが必要になる | 盤面が画面に収まるかどうかによって、`touch-action` で許可する動作を決める |
| 指の移動 | 長押し中に指が少し動くと、スクロールと判定される | 押した位置から一定以上動いたら長押しを取り消す |

### 7.3 タップ対象の大きさ

| 基準 | 最小サイズ |
|------|------------|
| WCAG 2.2 達成基準 2.5.8（レベル AA） | 24×24 CSS px（間隔を含めてもよい） |
| WCAG 2.2 達成基準 2.5.5（レベル AAA） | 44×44 CSS px |
| Apple Human Interface Guidelines | 44×44 pt |
| Material Design | 48×48 dp |

### 7.4 上級の盤面を各端末に表示できるか

スマートフォンの縦画面の幅は、およそ 360〜430 CSS px である。上級（30×16）の盤面を、マスの大きさ別に表示したときの幅を次に示す。

| 向き | 列数 | 24px のとき | 32px のとき | 44px のとき |
|------|------|-------------|-------------|-------------|
| そのまま（横長） | 30 | 720px | 960px | 1320px |
| 90 度回転（縦長の 16×30） | 16 | 384px | 512px | 704px |

端末と向きごとに、上級の盤面を画面に収めたときのマスの大きさの概算を次に示す。表示領域の大きさは代表的な端末から見積もった値で、盤面の上の表示（残り地雷数、経過時間など）に 60px 程度を使うと仮定した。

| 端末と向き | 表示領域（幅×高さ、概算） | そのまま（30×16） | 回転（16×30） |
|------------|---------------------------|-------------------|---------------|
| スマホ縦 | 360〜430 × 600〜800 | 12〜14px | 18〜24px（高さで制約される） |
| スマホ横 | 640〜930 × 300〜400 | 15〜21px（高さで制約される） | 8〜11px |
| タブレット縦 | 740〜1020 × 950〜1300 | 24〜34px | 29〜41px（高さで制約される） |
| タブレット横 | 1020〜1370 × 700〜950 | 34〜45px | 21〜29px |
| PC | 1280 以上 × 650 以上 | 36px 以上（高さで制約される） | 20px 以上 |

- スマートフォンでは、**縦でも横でも、盤面全体を 24px 以上のマスで収めることはできない**。横向きにすると幅には余裕があるが、高さが足りない。縦向きで盤面を回転させるのが最も大きく表示でき、端末によっては 24px に届く。
- タブレットと PC では、盤面を回転させずに 24px 以上で収まる。
- そのため、上級をスマートフォンで遊べるようにするには、次のどれか（または組み合わせ）が必要になる。
  - 盤面をスクロールできるようにする。
  - 盤面を拡大・縮小（ピンチズーム）できるようにする。
  - 盤面を回転して、縦長にして表示する。
  - 小さいマスで表示し、押しにくさは受け入れる。
  - スマートフォンでは上級を選べないようにする。
- 初級（9×9）は、スマホの縦画面でも 1 マス 40px 程度になる。中級（16×16）は縦画面で 1 マス 22.5〜27px 程度になり、幅 360px の端末では WCAG AA の 24px を下回る。
- Web ページから画面の向きを固定する Screen Orientation API の `lock()` は、全画面表示などの条件が必要で、iOS の Safari では使えない。したがって、向きの固定を前提にした設計はできない。

### 7.5 アクセシビリティ

| 項目 | 基準・課題 | 対応の例 |
|------|------------|----------|
| 色だけに頼らない | WCAG 1.4.1（レベル A）。数字は文字なので問題ないが、旗、地雷、誤った旗、踏んだ地雷などを色だけで区別してはならない | 形の違うアイコンや記号を使う |
| コントラスト | WCAG 1.4.3（文字は 4.5:1 以上）と 1.4.11（UI の部品は 3:1 以上）。クラシックの配色（5.3）は、灰色の背景では 8（灰）や 6（青緑）のコントラストが足りない可能性がある。未開放と開放済みのマスの区別も 3:1 以上が望ましい | 配色を決めるときにコントラスト比を計算する |
| キーボード操作 | WCAG 2.1.1（レベル A）は、すべての機能をキーボードで操作できることを求める | 矢印キーでマスを移動し、Enter や Space で開く、F で旗を立てる、など |
| スクリーンリーダー | 盤面を表として読み上げられるようにするには、ARIA の `grid` と `gridcell` を使い、各マスに「3 行 5 列、未開放」のような名前を付ける。勝敗は `aria-live` で知らせる | 上級は 480 マスあるので、読み上げの量と操作の手間が大きい |
| 動きの抑制 | 利用者が OS で動きを減らす設定をしているときは、アニメーションを控える | CSS の `prefers-reduced-motion` |
| ダークモード | OS の設定に合わせて明暗を切り替えられる | CSS の `prefers-color-scheme` |

## 8. Blazor WebAssembly での実装上の考慮点

### 8.1 入力イベント

- Blazor は、ポインターイベント（`@onpointerdown`、`@onpointerup`、`@onpointercancel` など）に対応している。ポインターイベントを使えば、マウスとタッチを一つの仕組みで扱える。
- 右クリックでブラウザーのメニューが出ないようにするには、`@oncontextmenu:preventDefault` を使う。JavaScript は要らない。
- ブラウザーが指の動きをスクロールやズームとして扱い始めると、`pointercancel` が発生し、その後のポインターイベントは届かなくなる。盤面の CSS で `touch-action: none` にすればこれを防げるが、盤面の上でのスクロールとピンチズームもできなくなる。したがって、「長押しで旗」と「盤面のスクロール・ズーム」を両立させるには、次のどちらかを選ぶ必要がある。
  - ブラウザーの標準のスクロールとズームを許し、指が動いたら長押しが取り消されることを受け入れる。
  - `touch-action: none` にして、スクロールとズームを自前で実装する。この場合は JavaScript interop が必要になる可能性が高い。
- 長押しの判定は Blazor には用意されていない。`pointerdown` で時間を計り始め、`pointerup`・`pointercancel`・一定以上の指の移動で取り消す処理を自分で書く必要がある。C# の `Task.Delay` とキャンセルで実装できる。
- ブラウザーの既定の動作（7.2）の多くは CSS で抑えられるので、JavaScript interop なしで対応できる見込みが高い。

### 8.2 描画の性能

- 上級の盤面は 480 マスある。マスを開くたびに盤面全体を描き直しても、Blazor の差分描画でたいていは問題ない規模だと考えられる。ただし、端末の性能によって差があるので、実装後に実機で確かめる必要がある。
- 性能が問題になった場合は、次の手段がある。
  - マスをコンポーネントにし、`ShouldRender` で変わったマスだけを描き直す。
  - `@key` でマスの対応を安定させる。

### 8.3 タイマー

- `PeriodicTimer` などで 1 秒ごとに画面を更新できる。
- ブラウザーのタブが裏にあるとき、タイマーは間引かれる。そのため、経過時間は「更新の回数」ではなく、「開始した時刻との差」で計算する必要がある。
- テストしやすくするため、現在時刻は外から差し替えられるようにしておくとよい。.NET 8 以降の `TimeProvider` が使える。

### 8.4 保存

- ベストタイムや設定を保存するには、ブラウザーの `localStorage` を使うのが一般的である。
- Blazor WebAssembly から `localStorage` を使うには、JavaScript interop（`IJSRuntime`）が必要になる。ラッパーのライブラリもあるが、使う操作が少ないなら、直接呼び出すだけで足りる。

### 8.5 読み込みと公開

- Blazor WebAssembly は、最初に .NET のランタイムとアプリを数 MB 程度ダウンロードする。このため、初回の表示には時間がかかる。テンプレートには読み込み中の表示が用意されている。発行時には未使用のコードの削除（トリミング）と、圧縮済みファイル（Brotli、gzip）の生成が行われる。
- 静的ホスティングで公開する場合、次の点に注意する。
  - サブパスに置くときは、`index.html` の `<base href>` を合わせる必要がある。
  - GitHub Pages では、`_framework` フォルダーを配信するために `.nojekyll` ファイルが要る。
- オフラインで遊べるようにする PWA 化も、選択肢にある（任意）。

### 8.6 ゲームロジックの分離

- CLAUDE.md の方針どおり、ゲームのルール（盤面、地雷の配置、開放、勝敗の判定）は UI に依存しない C# のクラスにする。こうすると、xUnit で単体テストができる。
- 乱数（6.1）と時刻（8.3）を外から差し替えられるようにしておけば、テストで盤面や経過時間を固定できる。

## 9. 仕様書で決めるべき論点

調査の結果、仕様書で決める必要がある論点を次にまとめる。CLAUDE.md に挙げられている論点（タッチでの旗の立て方、盤面が画面に入らない場合の扱い、誤操作対策、マス目の最小サイズ）もここに含めた。

| # | 論点 | 選択肢 | 関連する節 |
|---|------|--------|------------|
| 1 | 初級の盤面 | 9×9 / 8×8 | 4 |
| 2 | カスタムの範囲 | 盤面の最小・最大サイズ、地雷数の上限 | 4 |
| 3 | 最初のクリックの安全保証 | なし / そのマスだけ / 周囲 8 マスも | 5.2 |
