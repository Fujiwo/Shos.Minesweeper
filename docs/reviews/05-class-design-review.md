## 観点

CLAUDE.md のとおり、sustainable-code-jp スキルの七箇条と Think Simple（引き算の設計）を観点にする。加えて、前の工程の成果物との整合を見る。

| 観点 | 問い |
|------|------|
| 意図を表現 | 公開メンバーの名前と説明が What で書かれているか。書いた理由（Why）と中身が食い違っていないか |
| 単一責務 | 各型の変更理由は一つか。自分では使わないものを受け渡すだけの型（仲介者）がないか |
| 的確な名前 | 名前が仕事を過不足なく表しているか。仕様書の用語と対応しているか |
| Once And Only Once | 同じ規則や値が二箇所に置かれていないか |
| 的確なメソッド | 引数が多すぎないか。呼び出す側のコードが自然に読めるか |
| ルールの統一 | アーキテクチャー設計書、CLAUDE.md の決まりに合っているか |
| Testable | 正しいことを確かめられる形か。テストの観点に漏れや誤りがないか |
| 引き算 | 頼まれていない抽象・仕組み・備えがないか |
| 整合 | 仕様書・UI デザイン・アーキテクチャー設計書と矛盾しないか。書かれた方式で、要求を実際に実現できるか |

重大度の基準は、調査書レビュー（docs/reviews/01-research-review.md）と同じとする。

## 引き算の点検

クラス設計で足した型と仕組みについて、「今日の問題の何を解いているか」を点検した。

| 型・仕組み | 解いている問題 | 判定 |
|------------|----------------|------|
| `Cell` | 仕様書 3.4 の表（どの操作がどのマスで効くか）の置き場所。`InputMapping` を盤面なしでテストできる | 残す |
| `CellAppearance` | 地雷の位置を UI に公開せずに、敗北後の見せ方を渡す | 残す |
| `CellPosition` と `DisplayPosition` を分ける | 盤面を入れ替えて表示するときの座標の取り違えを、コンパイルで防ぐ（アーキテクチャー設計書レビューの指摘 4 と同じ種類の誤り） | 残す |
| `PointerInput` | Input を Blazor に依存させずに、5 つの値を 1 つの引数にまとめる | 残す |
| `AllowedRange`、`CustomDifficultyValidation` | 範囲の判定と表示を 1 か所から得る。どの欄が誤りかを返す | 残す |
| `MineChooser`（delegate） | テストのための差し替え口（アーキテクチャー設計書 12 章）。インターフェイスとクラスより読む対象が少ない | 残す |
| `CellPresentation` | マスの見た目は、入力の流れとは変更理由が違う（アーキテクチャー設計書レビューの残る課題） | 残す |
| `DifficultyNames` | 3 か所で使う表示名を 1 か所にする | 残す |
| `Announcements` | 勝利の文の 4 通りの出し分けを、xUnit の表で確かめる | 残す |
| `ToolbarCounter`、`Icon` | 数字の書式とアイコンの描き方を 1 か所にする | 残す |
| `BoardArea` が `BoardView` の引数とイベントを中継すること | 解いている問題がない | 削った（指摘 2） |

足さなかったもの:

- ベストタイムの保存で、難易度の種類の名前（`Beginner` など）とは別に、保存用のキーの対応表を持つ案を考えた。列挙型の名前を変えると保存した記録が読めなくなることへの備えだが、名前を変える予定はなく、読めない値は「記録なし」として扱う規則（アーキテクチャー設計書 10 章）で困らない。足さない。
- `Difficulty.ValidateCustom` が、正しいときに `Difficulty` も返す案を考えた。呼び出す側の `width!.Value` などは消えるが、検証の結果と作った値を 1 つの型に持たせると、型の仕事が 2 つになる。`!` の 1 行はそのままにする。

## 良い点

- 用語と名前の対応表（1.2）があり、仕様書の語彙がそのままコードの語彙になっている。
- 盤面を変える操作を `internal` にし、「盤面を変えられるのは `Game` だけ」をコンパイラーに守らせている。アーキテクチャー設計書の「依存の向きはコンパイラーに守らせる」と同じ考え方である。
- 地雷の配置で、「最初に開いたマスの周りに置かない」規則は `Game` に残し、差し替えられるのは「候補からどれを選ぶか」だけにしている。テストで偽の選び方を渡しても、規則は本物のまま確かめられる。
- `ChordTargetsOf` を、コードで開く範囲と押下中の表示の範囲の両方に使い、定義を 1 か所にしている。
- 呼び出す側のコード（`Open` の流れ、`GamePage` の勝ったときの処理、`DifficultyDialog` の検証）が書かれていて、公開メンバーの名前が自然に読めることを確かめられる。
- 実装の区切り（8 章）が、区切りごとに動くものとテストがそろう形になっている。

## 残る課題

- タッチでは、押したマスの要素にポインターが暗黙に捕捉される。このとき `pointermove`・`pointerup` が盤面の要素に届くこと、`pointerleave` が押している途中で届かないことを、工程 11 の区切り 3（マウスとタッチの操作）で、実機で確かめる。
- マスごとに `pointerdown` の処理を登録するので、上級では 480 個になる。描き直しの時間が仕様書 6.2 の目標を満たすかは、工程 13（結合テスト）で計る（アーキテクチャー設計書 7.3、16 章）。
- 設計書の Mermaid の図は、書式を確かめただけで、描画しての確認はしていない。

### コードとの突き合わせ

- GameLogic、Presentation、Input、Display、Browser の公開メンバー（名前、引数、戻り値、`internal` の範囲）は、設計書の宣言とすべて一致した。`BestTimesJson` の置き場所（指摘 1）だけが、決定とコードで違う。
- `GamePage` の主な処理（`OpenCellAsync`、`ShowWinAsync`、読み上げの U+200B、描き直しの後のフォーカス）と、`BoardView` の押し方とキーボードの処理は、5.2 の記述どおりである。
- テストプロジェクトの参照は、7.1 の表どおりである（GameLogic.Tests → GameLogic・TestSupport、Presentation.Tests → Presentation、Tests → Web アプリ・TestSupport、TestSupport → GameLogic）。
