## 観点

CLAUDE.md のとおり、sustainable-code-jp スキルの七箇条と Think Simple（引き算の設計）を観点にする。加えて、前の工程の成果物との整合を見る。

| 観点 | 問い |
|------|------|
| 意図を表現 | 各単位の仕事が What で書かれ、How（実装の細部）が前に出ていないか |
| 単一責務 | 各単位の変更理由は一つか |
| 的確な名前 | 名前が仕事を過不足なく表しているか。要求の語彙と対応しているか |
| Once And Only Once | 同じ規則や値が二箇所に置かれていないか |
| 的確なメソッド | （この工程ではメソッドを決めないので、対象外） |
| ルールの統一 | 既存のテンプレートの流儀、CLAUDE.md の決まりに合っているか |
| Testable | 正しいことを確かめられる形か。差し替え口は足りているか |
| 引き算 | 頼まれていない抽象・仕組み・備えがないか。問題文にない制約を足していないか |
| 整合 | 仕様書・UI デザインと矛盾しないか。書かれた方式で、要求を実際に実現できるか |

重大度の基準は、調査書レビュー（docs/reviews/01-research-review.md）と同じとする。

## 引き算の点検

新しく足した単位と仕組みについて、「今日の問題の何を解いているか」を点検した。削ったもの・足さなかったものはない。

| 単位・仕組み | 解いている問題 | 判定 |
|--------------|----------------|------|
| GameLogic のプロジェクトを分ける | ルールが UI に依存しないことを、コンパイラーで守る（CLAUDE.md の設計方針） | 残す |
| `PressGesture` と `InputMapping` を分ける | 変更理由が違う（判定の時間と距離／旗モードでの割り当て） | 残す |
| `BrowserFeatures` と `BestTimeStorage` を分ける | JavaScript の呼び出しと、保存の形式・失敗の扱いは、変更理由が違う | 残す |
| `ElapsedTime` を別のコンポーネントにする | 毎秒の描き直しで盤面を描き直さない（仕様書 6.2 の性能） | 残す |
| キーのスクロールを抑える JavaScript | Blazor ではキーごとに既定の動作を止められない | 残す（Blazor だけでは実現できない） |
| インターフェイス | 作っていない（15 章） | 妥当 |

- 指摘 2 で足した 6.4 は、新しい仕組みではなく、既に決めた差し替え口（`TimeProvider`）の届け方を書いたものである。DI に登録するのは、差し替える必要があるものと JavaScript を呼ぶものだけにした。
- 指摘 3 で、円の位置を JavaScript（`getBoundingClientRect`）で求める案も考えた。イベントの `ClientX − OffsetX` で求められるので、JavaScript を足さずに済ませた。

## 良い点

- 関心事の一覧（3 章）が先にあり、クラスはその結果として決まっている。各単位の「ひとことで言うと」と「持たないもの」が書かれていて、責務の境界が読み取れる。
- 盤面の縦と横の入れ替えを GameLogic に持ち込まず、`BoardPlacement` に閉じ込めている。ルールと表示という独立したものを、独立したまま表している。
- 上バーと横バーの切り替えを CSS だけに任せ、C# は測った領域の大きさだけを使う。レイアウトの規則が二重に書かれない（Once And Only Once）。
- JavaScript を使うものと使わないものを、理由とともに表にしている。JavaScript を使うのは 4 つだけで、C# の窓口も 1 つにまとまっている。
- 作らないもの（15 章）に理由が書かれていて、後から「なぜ無いのか」を問われたときに答えられる。

## 残る課題

- `BoardView` は、マスを描くことに加えて、ポインターとキーボードの入力を意図に変える流れも受け持つ。判定そのものは `PressGesture`・`InputMapping`・`BoardCursor` に出してあるので今は許容するが、クラス設計（工程 9）で、マスの見た目（状態から CSS のクラスや読み上げの名前を決める部分）を別の C# のクラスに出すかどうかを判断する。
- 16 章のリスク（iOS の長押し、性能、`browser.js` の読み込み）は、実装と結合テストで確かめる。

### ユーザーの指摘と確認事項の扱い

設計書の提出時に、17 章で 3 点を確認事項として挙げた。ユーザーは工程 7 を承認し、1 点目に次の指示を出した。

> 効果音の部品は、Presentation に置く。ただし、Presentation が効果音の実装に依存してはならない。

- 「効果音の部品」は、設計書で SoundEffects に置いた 3 つ（効果音の種類 `SoundEffect`、鳴らす場面 `SoundEffectMapping`、波形の合成 `SoundEffectSynthesizer`）と解した。どれも .NET の基本ライブラリだけで書ける。
- 「効果音の実装」は、音を鳴らす仕組み（ブラウザーの Web Audio、WPF の再生の方法、NAudio などのライブラリ）と解した。Presentation は波形を作るところまでで、鳴らすのは各アプリである。
- Presentation に、音を鳴らすためのインターフェイス（アプリが実装する）は置かない。Presentation の部品が自分で音を鳴らすことはないので、依存を逆にする口が要らないからである（Think Simple。15 章）。WPF 版で、鳴らす流れまで共有したくなったときに、改めて考える。→ この点は、次の「ユーザーの 2 つ目の指示」で改めた。

設計書の 1 章、1.1、3 章、4 章（構成図、参照の図、理由）、5 章（図と依存の規則）、6.1、6.2、12 章、13 章、15 章、17 章をこの指示に合わせて直し、CLAUDE.md の「目的」も改めた。残りの 2 点（`Game` の操作が操作の結果を返すこと、タッチの最初の操作が長押しのときは音が鳴らなくてよいこと）には個別の回答がなかったので、前例に従い、推した案どおりに確定した。

### ユーザーの 2 つ目の指示（共通のゲームのロジックと効果音）

レビューの途中で、ユーザーに「コンソール版でも効果音を鳴らすとしたら、設計はどう変わるか」を問われ、助言した。ユーザーは続けて次のように決めた。

> コンソール版では音を鳴らさない。効果音を鳴らす実装は、コンソール版にはない。ただし、共通のゲームのロジックは、効果音をサポートしたい。効果音を鳴らす実装がない版では、効果音を鳴らなければいいだけで、共通のゲームのロジックからは、どの版かに依存させたくない。

Claude は、次の形を推し、ユーザーは「おすすめの方法を採用」とした。

- 効果音はルールではないので、GameLogic（`Game`）には入れない。`Game` は操作の結果を返すところまでとする。
- Presentation に、1 回のゲームの進め方 `GameSession` を置く。`GameSession` は、操作の結果から鳴らす効果音を決め、外から受け取った「音の出口」に渡す。
- 音の出口は、効果音を 1 つ受け取るデリゲートとする。省略すると何もしない出口になる（Null Object）。`Game` が地雷の選び方を受け取る `MineChooser` と同じ形である。コンソール版は出口を渡さないので、鳴らない。共通の側には、版を見分ける分岐も、音を鳴らせるかを表す値もない。
- 効果音のオンとオフは、鳴らす実装がある版だけの事情なので、出口の中身（Web 版の `SoundEffectPlayer`）が持つ。
- 出口は、呼ばれたらすぐに返す。

`GameSession` に移すのは、効果音をサポートするのに要るもの（現在のゲーム、新しいゲームを始めること、盤面の操作、鳴らす効果音を決めて渡すこと、直前の操作）だけにした。ベストタイムと読み上げの文は、1.1.0 の目的に要らないので移さず、WPF 版・コンソール版の一巡で 3 つの版の流れを見てから決める。

設計書の 1 章、1.1、3 章（関心事 20）、4 章、5 章、6.2〜6.4、7.1、7.2、8.2、8.4、8.6、12 章、14 章（決定 10〜12）、15 章、17 章を直し、CLAUDE.md の「目的」も改めた。この変更で、指摘 4（`GamePage` の受け持ちが増える）も軽くなった。直前の操作と、盤面の操作は `GameSession` に移る。

### 引き算の点検

| 単位・仕組み | 解いている問題 | 判定 |
|--------------|----------------|------|
| 効果音の部品のための別のプロジェクト（SoundEffects とそのテスト） | コンソール版が効果音の部品を持たないことを、コンパイラーで守る | 削った（ユーザーの指示）。守るべき線は「Presentation が効果音の実装に依存しないこと」で、プロジェクトの参照（音を鳴らすパッケージを参照しない）で守れる |
| 操作の結果（`Game` の戻り値） | 1 回の操作で起きたことを、効果音と演出が知る（仕様 5.6、5.7） | 残す。画面が前と後を比べる案より単純で、ルールの外に判断が漏れない |
| `BoardAnimation` | どのマスを、どの順で演出するかを、Razor から切り離して xUnit で確かめる | 残す。時間の値は持たせない（CSS だけに置く） |
| `SoundEffectPlayer` と `SoundSettingStorage` | JavaScript での再生と、設定の保存は、変更理由が違う。`BestTimeStorage` と同じ形にそろう | 残す |
| 音の出口（デリゲート）と `GameSession` | 共通のゲームのロジックが効果音をサポートし、どの版かに依存しない（ユーザーの 2 つ目の指示） | 残す。要求に書かれた必要なので、先回りの抽象ではない。インターフェイスではなくデリゲートにし、`GameSession` に移すものも効果音に要るものだけに絞った |
| WAV への変換、演出のタイマー、音を鳴らせるかを表す値 | 今の問題を解いていない | 作らない（15 章） |
| 盤面の置き方の持ち主を `GamePage` に移すこと | ツールバーは盤面の領域の外にあるので、置き方を両方の親が持たないと、ツールバーを盤面に付けられない | 残す。CSS のアンカーの配置（`anchor()`）なら C# を変えずに済むが、対象のブラウザーのすべてでは使えない |

### 良い点

- 効果音と演出の判断（鳴らす音、演出するマスと順）が、どれも C# のクラスにあり、動きと時間は CSS、鳴らす仕組みは JavaScript と、変更理由ごとに置き場所が分かれている。音の調整は合成、演出の調整は CSS、場面の変更は `SoundEffectMapping` と、直す場所が 1 つに決まる。
- `Game` に演出のための状態を持たせず、戻り値で返している。ルールと表示という独立したものを、独立したまま表している。
- ブラウザーの制限（利用者の操作と見なされるイベント）を仕様の根拠とともに書き、避けられない例外（決定 7）を隠さずに決定として残している。

### 残る課題

- 合成にかかる時間、`Float32Array` の読み方、試聴のページとの聞き比べ、iOS での鳴り方、演出を入れた後の性能（16 章）は、実装と結合テストで確かめる。
- クラス設計（工程 9）では、操作の結果の型の名前と形、効果音の設定の保存のキーと値の形、CSS の変数の名前を決める。
