## 観点

CLAUDE.md の「リリース」の 4 点を確かめる。

1. 全テストが Green
2. 仕様書の要求を満たしている（仕様書 8 章の受け入れ基準）
3. 動作環境の各端末・ブラウザーでの実機確認（ユーザーが行う）
4. 発行物の設定（`<base href>`、公開先に必要なファイル）

加えて、手順書とリリースノートの記述が、実際の公開物と合っているかを見る。

## 2. 仕様書の受け入れ基準

docs/06-release.md の 5.2 の表のとおり、13 項目すべてに根拠がある。このレビューで新たに確かめたのは、次の 2 項目である。公開物をワークフローと同じ手順で整え、GitHub Pages と同じ配り方（サブパス、無いパスには `404.html` を 404 で返す）のローカルのサーバーで配り、ヘッドレスの Chrome で本物のクリックとキー入力を送った。

| # | 受け入れ基準 | 確かめたこと | 結果 |
|---|--------------|--------------|------|
| 1 | カスタムで、勝利と敗北の両方まで進められる | 難易度ダイアログに幅 12・高さ 10・地雷 15 を入力して「カスタムで始める」を押し、勝つまで遊び、「もう一度」の後に負けるまで遊んだ | 盤面は 120 マス。ツールバーは「難易度、カスタム」。読み上げは「新しいゲーム、カスタム、12×10、地雷 15。」。勝利カードは「クリア！ タイム 0 秒」で、ベストタイムの行は出ない（UI デザイン 2.4 のとおり）。localStorage には何も書かれない（カスタムは記録しない。仕様書 3.8）。負けると「ゲームオーバー。地雷を開きました。」と読み上げ、難易度はカスタムのまま |
| 10 | 保存ができない環境でも、最後まで遊べる | ページを開く前に、localStorage の読み書きが例外（`SecurityError`）を投げるようにして、初級で 2 回続けて勝った | 盤面が出て、1 回目は「ベストタイムを記録しました」、2 回目は「ベスト 0 秒」（メモリーの記録が残っている）。エラーの表示（`#blazor-error-ui`）は出なかった |

## 3. 実機の確認

工程 13 でユーザーが確かめ、「正常」だった（docs/reviews/code-review.md の工程 13）。工程 13 の後に変えたのは次のものだけで、端末での操作や表示の振る舞いは変えていないので、確かめ直しは要らないと判断した。

| 変更 | 振る舞いへの影響 |

| ワークフロー、`404.html`、`.nojekyll` | 公開物の配り方だけ。アプリの中身は同じ |

## 4. 発行物の設定

| 項目 | 結果 |
|------|------|
| `<base href>` | 公開物では `/Shos.Minesweeper/`。ワークフローは書き換えた後に確かめ、無ければ失敗する。ソースの `index.html` は `/` のまま |
| `404.html` | 書き換えた `index.html` の写し。`/Shos.Minesweeper/no-such-page` と `/Shos.Minesweeper/a/b/c` で、アプリの「ページが見つかりません」が出た（工程 14） |
| `.nojekyll` | ある |
| ファビコン | `favicon.svg` が `image/svg+xml` で配られる。ライトとダークのどちらの背景でも見える形（明るい角丸の四角に地雷） |
| `index.html` のプレースホルダー | 発行で書き換わっている（importmap、preload、読み込むスクリプトの名前） |
| `js/browser.js` | サブパスで読み込め、盤面の大きさの監視が動く |
| 大きさ | `_framework` は gzip で約 3.6MB（リリースノートの「約 3.6MB」と合う） |
| ワークフローの起動 | `on:` は `workflow_dispatch` だけ。push では動かない（CLAUDE.md の「公開はユーザーの指示のときだけ」） |

## 指摘

| # | 重大度 | 場所 | 指摘 | 対応 |
|---|--------|------|------|------|
| 1 | 軽微 | `.github/workflows/deploy.yml` の `permissions` | GitHub Pages への書き込み（`pages: write`）と ID トークン（`id-token: write`）の権限が、ワークフロー全体に与えられていて、テストと発行を行う `build` のジョブも持っていた。要るのは配置する `deploy` のジョブだけである（権限は要る所にだけ与える） | 既定の権限を `contents: read` だけにし、2 つの権限を `deploy` のジョブに移した。docs/06-release.md の 5.4 に確認項目を足した |
| 2 | 軽微 | docs/06-release.md の 5.2 | 受け入れ基準 1（カスタム）と 10（保存できない環境）が「リリースレビューで確かめる」のままだった | このレビューで確かめたことを書き、このファイルを指すようにした |
