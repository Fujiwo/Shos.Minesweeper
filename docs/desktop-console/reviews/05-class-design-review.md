## 観点

CLAUDE.md の「レビューの観点」（工程 8、10、11）のとおり、次の 4 つで見た。七箇条の問いは、スキルの quality-gates.md の「七箇条をレビューの観点にする」を読み直して使った。

1. **七箇条**: 意図を表現、単一責務、的確な名前、Once And Only Once、的確なメソッド、ルールの統一、Testable
2. **引き算**（Think Simple）: 頼まれていない抽象・パターン・備えがないか
3. **整合**: 仕様書・UI デザイン・アーキテクチャー設計書・Web 版の設計と食い違わないか。書かれた方式で要求を実現できるか
4. **正しさ**: 例外の境界、後始末、実行環境の差

七箇条の外の指摘は、箇条に当てはめずに「整合」「正しさ」と書く。重大度の基準は、調査書レビュー（docs/desktop-console/reviews/01-research-review.md）と同じとする。

設計の意図（一言）: 「3 つの版で同じゲームを、判断は画面の部品と端末から切り離した型に置き、共有するのは同じ意図の部品だけにする」。

### 七箇条と引き算で見て、問題がなかった点

- **単一責務**: `GameViewModel` は受け持つことが多いが、残る判断（勝ったら記録して保存する、F2 はダイアログの間は効かない、顔の表情）は、どれも画面全体の状態を知る者にしか決められない（クラス設計書 4.3 の最後の段落）。アーキテクチャー設計書レビューの残る課題に、公開メンバーを並べたうえで答えている。
- **Once And Only Once**: 勝ったときの流れ（記録して、更新したら保存する）は、Web 版、デスクトップ版、コンソール版の 3 か所にある。アーキ 6.2 で移さないと決めたとおりで、それぞれ 2 行で、つなぐ先（保存先、知らせ方）が版ごとに違う。キーの割り当ても、アーキ 6.2 のとおり版ごとに置いている。`NO_COLOR` の判断を `FrameWriter` の 1 か所にしたこと（A3）と、余白などの数字を `WindowSizing` から XAML が `x:Static` で使うこと（4.8）は、同じ数字を 2 か所に書かない形である。
- **的確な名前**: `KeyboardMapping` を 3 つの版でそろえ、`DifficultyButtonNameOf` で `DifficultyNames.Of` との紛れを避け、`VirtualTerminalSequences` で略語を避けている。`BoardViewModel.Show(move, withAnimation)` の真偽の引数は、呼ぶ側が名前付きの引数で書く 1 か所だけなので、読める。
- **引き算**: インターフェイスは `IScreen`（実装 3 つ）だけで、音の出口とアニメーション効果の設定はデリゲートにしている。10 章に、作らないものを理由とともに挙げている。
- **Testable**: ビューモデルは Avalonia を起動せずに、コンソール版の画面の単位は端末なしに確かめられる。テストで差し替えるものは、時刻、地雷の置き方、音の出口、ファイルのパス、アニメーション効果の設定で、SKILL の判断ルール 3 に当たる。

## 良い点

- 共有の部品を移すときに、Web 版の HTML を 1 文字も変えないことを、bUnit のテストで確かめる形にしている（3.8）。移す手順と機能を足す手順を分けている（8 章の区切り 2）。
- 文字の表示の幅を数えずに済む形（行の残りを消す、カーソルを行の末尾に置く）で、全角の文字の扱いという難しい問題を避けている（simplicity.md の「複雑な問題は解かない」）。
- 例外を受け止める型と例外の種類を表にし（6 章）、アーキ 10 章の境界を型に落としている。NAudio の再生のスレッドの失敗を、例外でなく `PlaybackStopped` の引数として受ける形は、別のスレッドに例外を投げさせない。
- 実装の区切りの最初に、結果で設計が変わりうる実行環境の事項を置いている（8 章）。
- 仕様書と Web 版の実際の動きの食い違い（カーソル）を、Web 版のコードを読んで見つけ、確認事項に挙げた。
