## 観点

CLAUDE.md の「レビューの観点」（工程 8、10、11）のとおり、次の 4 つで見た。七箇条の問いは、スキルの quality-gates.md の「七箇条をレビューの観点にする」を読み直して使った。

1. **七箇条**: 意図を表現、単一責務、的確な名前、Once And Only Once、的確なメソッド、ルールの統一、Testable
2. **引き算**（Think Simple）: 頼まれていない抽象・パターン・備えがないか
3. **整合**: 仕様書・UI デザイン・Web 版の設計と食い違わないか。書かれた方式で要求を実現できるか
4. **正しさ**: 例外の境界、後始末、実行環境の差

七箇条の外の指摘は、箇条に当てはめずに「整合」「正しさ」と書く。重大度の基準は、調査書レビュー（docs/desktop-console/reviews/01-research-review.md）と同じとする。

設計の意図（一言）: 「3 つの版で同じゲームを、共有の部品は 2 つ目の利用者が来たものだけ移し、各版は判断を画面の部品から切り離して作る」。

### 七箇条と引き算で見て、問題がなかった点

- **Once And Only Once**: Web 版と 2 か所に書く配色と演出の時間（7.5）は、一致をテストで確かめる。勝ったときの流れ（6.2）は 3 つの版に残るが、記録の規則は `BestTimes.Record` の 1 か所にあり、各版に残るのは保存先と知らせ方をつなぐ数行で、版ごとに違う。誤った共通化（SKILL の判断ルール 6）を避けた判断として妥当である。
- **単一責務**: ゲームの画面のビューモデル（7.2）は受け持つことが多いが、Web 版の `GamePage` と同じく、判断はそれぞれの部品（`GameSession`、`BestTimes`、`BoardAnimation`、大きさの計算）に任せ、つなぐだけにする形である。クラス設計で、つなぐ以外の判断が入っていないかを確かめる（残る課題）。
- **引き算**: 端末の窓口のインターフェイス、MVVM のライブラリ、DI のコンテナー、エラーを見せる仕組みを作らず、15 章に理由とともに挙げている。残した差し替え口（12 章）は、どれもテストが求めるもの（時刻、地雷の置き方、音の出口、ファイルのパス、アニメーション効果の設定）である（SKILL の判断ルール 3）。
- **Testable**: コンソール版の画面の単位は、キーと大きさを引数で受けて行を返すので、端末なしで確かめられる。

## 良い点

- 共有する部品を、「この一巡で 2 つ目の利用者が来るか」という根拠で選び、移さないものにも理由を書いている（6.2）。Web 版の設計で保留にしていた点（勝ったときの流れを `GameSession` に移すか）に、3 つの版を見て答えを出している。
- 例外を受け止める場所を表で決め、それ以外は受け止めないと明言している（10 章）。1.1.0 の B1 の教訓を、設計の段階で当てはめている。
- 実行環境で変わるものを、確かめ方と合わなかったときの手と一緒に並べている（11 章）。CLAUDE.md の「実行環境での確認」を、実装の最初の区切りに結び付けている。
- 名前の理由（`Desktop` に技術の名前を入れない、`ConsoleApp` で `System.Console` を隠さない、`Sizing`）が書かれている。

## 残る課題

- ゲームの画面のビューモデルが、つなぐ以外の判断を持っていないかは、クラス設計で公開メンバーを決めるときに確かめる。
- NAudio の導入は、工程 11 でパッケージを加える前に、ユーザーに改めて確認する。
- CLAUDE.md の「開発環境」「コマンド」「コードの現状」は、プロジェクトを加える工程 11 で、Avalonia とコンソール版に合わせて書き足す。
- 11 章の確かめる事項の結果によっては、この設計を見直す。
