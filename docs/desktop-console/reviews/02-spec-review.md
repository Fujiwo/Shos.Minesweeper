## 観点

Web 版の仕様書レビュー（docs/reviews/02-spec-review.md）と同じ観点で見た。

1. **完全性**: 調査書 8 章の論点がすべて決まっているか。UI デザインと設計が、推測なしに進められるか
2. **一貫性**: 章どうし、調査書、Web 版の仕様書、CLAUDE.md、リポジトリの今の状態と矛盾していないか
3. **曖昧さ**: 同じ文から二通りの実装が生まれる箇所がないか
4. **検証可能性**: 受け入れ基準で確かめられるか
5. **使いやすさ**: 決めた操作が、想定する利用者にとって自然か

重大度の基準は、調査書レビュー（docs/desktop-console/reviews/01-research-review.md）と同じとする。

仕様書の提出時に、次の 4 点を確認事項として挙げた。ユーザーは個別の回答をせずに工程を承認したので、前例（docs/reviews/02-spec-review.md）に従い、**推した案どおりに確定した**ものとして扱う。

## 良い点

- 論点ごとに、決めた理由を、ユーザーの条件（Linux の上で公開、Windows のデスクトップ アプリ）、CLAUDE.md の計画、Web 版との一貫性に照らして書いている。対象外（9 章）にも理由がある。
- ゲームのルールを Web 版の仕様書に任せ、二つの版で変えないと明記しているので、共有の部品（GameLogic、Presentation）をそのまま使える前提がはっきりしている。
- 1.1.0 の教訓（実行環境での確認、例外の境界）を、受け入れ基準に入れている（基準 7 は配る実行ファイルで確かめる。4.6 は音の失敗でゲームを止めない。5.9 は例外でも端末を戻す）。
- 決めていない見た目（記号、色、フォント、既定のマスの大きさ）を、UI デザインで決めるものとして明示している。

## 残る課題

レビューでは解消できず、後の工程に持ち越すもの。

- 盤面を表として読み上げること（4.8 の目標）が Avalonia でできるかは、実装で確かめる。できなければ、既知の制約としてリリースノートに書く。
- Linux の ICU の扱い（指摘 4）、Linux の上で発行した Windows 向けの実行ファイルが動くか（7.1）は、アーキテクチャー設計で方針を決め、実装の最初の区切りで確かめる。
- 起動から 3 秒以内（6.1）は、単一ファイルがネイティブのライブラリを展開する時間を含めて、実装で確かめる。
- F2 が Windows のマインスイーパーの定番であること（4.3）は出典未確認である。定番でなくても、キーを足すことに差し支えはない。
