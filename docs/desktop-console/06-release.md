## 1. 概要

デスクトップ版とコンソール版の最初の版（どちらも 1.0.0）を、このリポジトリの GitHub Releases に置くための手順と確認項目をまとめる。Web 版の手順書（docs/06-release.md）と同じ形にし、違うところだけを書く。Web 版の公開（GitHub Pages）は変えない。

| 項目 | デスクトップ版 | コンソール版 |
|------|----------------|--------------|
| 公開する版 | 1.0.0（タグ `desktop-v1.0.0`） | 1.0.0（タグ `console-v1.0.0`） |
| 公開物 | `Shos.Minesweeper.Desktop-1.0.0-win-x64.zip` | `Shos.Minesweeper.ConsoleApp-1.0.0-win-x64.zip`、`Shos.Minesweeper.ConsoleApp-1.0.0-linux-x64.tar.gz` |
| 公開先 | `https://github.com/Fujiwo/Shos.Minesweeper/releases`（仕様書 7.2） | 同じ |
| 公開の方法 | GitHub Actions のワークフロー（`.github/workflows/release-desktop-console.yml`）を、版を選んで手動で起動する | 同じ |
| リリースノート | docs/desktop-console/release-notes.md の「デスクトップ版 1.0.0」の節 | 同じファイルの「コンソール版 1.0.0」の節 |

公開の操作（push、ワークフローの起動、タグ付け）は、リリースレビューが承認され、ユーザーが明示的に指示したときだけ行う（CLAUDE.md）。

## 2. この工程で決めたこと

| # | 決めたこと | 理由 | 見送った案 |
|---|------------|------|------------|
| 1 | 公開のワークフローは 1 本（`release-desktop-console.yml`）にし、起動するときに版（`desktop` か `console`）と版番号を選ぶ。手動でだけ起動する（`workflow_dispatch`） | 二つの版は、テスト、発行、まとめ、Release を作る、という同じ流れで、違うのは発行する対象だけである。版番号は版ごとに独立しているので（仕様書 7.4）、一方だけを公開できるようにする。手動でだけ動くので、「公開はユーザーの指示のときだけ」（CLAUDE.md）を守れる | 版ごとに 2 本のワークフロー（同じ手順を 2 か所に書く）。タグの push で動かす（タグを付ける操作が、そのまま公開になる。Web 版と起動の仕方が分かれる） |
| 2 | タグは、ワークフローが Release を作るときに、テストして発行したコミットに付ける（`gh release create --target`）。同じタグがもうあれば、テストの前に失敗する | GitHub Releases はタグに付くので、タグと公開物を同じ時に作ると、タグだけあって公開物がない（またはその逆の）状態にならない。公開した版を、同じ版番号で上書きしない | Web 版と同じく、公開の後に手でタグを付ける（Release はタグが要るので、先にタグを push することになり、手順が増える） |
| 3 | 公開物は実行ファイルだけをまとめる。Windows は zip、Linux は tar.gz にする。デバッグ情報（`.pdb`）は含めない | 利用者に要るのは実行ファイル 1 つである（仕様書 7.1）。tar.gz は実行の許可を保つので、展開してそのまま実行できる（zip は、展開の仕方によっては許可が落ちる）。発行の設定は変えず、まとめるときに実行ファイルだけを選ぶ | 発行のフォルダーをまるごと zip にする（`.pdb` が 100MB 近く増える）。Linux も zip にする（`chmod +x` が要りやすい） |
| 4 | 発行のときに版番号を実行ファイルに入れる（`-p:Version=1.0.0`）。csproj には版番号を書かない | エクスプローラーのプロパティで版が分かる。版番号を書く場所を、ワークフローの入力の 1 か所にする（csproj とタグの 2 か所に書くと食い違いうる） | csproj に `<Version>` を書く（版を上げるたびにコードを変えることになる） |
| 5 | リリースノートは docs/desktop-console/release-notes.md に、版ごとの節（`## デスクトップ版 1.0.0（…）`）で書く。ワークフローは、その版の節を取り出して Release の説明にする。節がなければ失敗する | 仕様書 7.4 で置き場所をここで決めるとした。Web 版の docs/release-notes.md とは版番号が独立しているので、別のファイルにする。リポジトリのリリースノートと Release の説明を同じ文にし、書き写さない | Web 版の docs/release-notes.md に足す（版番号の体系が混ざる）。版ごとに別のファイル（2 つの版で同じ注意書きの節が離れる） |
| 6 | README は作らない（9 章の確認事項 1） | 仕様書 7.2 でここで決めるとした。GitHub のリポジトリのページから Releases を辿れ、使い方は Release の説明に書く。README を作ると、Web 版・デスクトップ版・コンソール版の案内を 3 つの場所（README、Release、Web 版のページ）で保つことになる | 短い README を作り、Web 版の URL と Releases への案内を書く（9 章） |
| 7 | Linux の ICU はアプリに含めず、要ることをリリースノートに書く | アーキテクチャー設計書 13 章の決定のとおり | — |

## 3. 公開物の構成

| 公開物 | 中身 | 大きさ（2026-09-28 の試し） |
|--------|------|------------------------------|
| `Shos.Minesweeper.Desktop-1.0.0-win-x64.zip` | `Shos.Minesweeper.Desktop.exe`（自己完結の単一ファイル。描画のネイティブのライブラリを含む） | zip 43MB（展開すると 98MB） |
| `Shos.Minesweeper.ConsoleApp-1.0.0-win-x64.zip` | `Shos.Minesweeper.ConsoleApp.exe`（自己完結の単一ファイル） | zip 32MB（展開すると 70MB） |
| `Shos.Minesweeper.ConsoleApp-1.0.0-linux-x64.tar.gz` | `Shos.Minesweeper.ConsoleApp`（自己完結の単一ファイル。実行の許可付き） | tar.gz 32MB（展開すると 70MB） |

ローカルでの事前の確認（工程 14 で行った）: ワークフローの手順（版番号とタグの確かめ、リリースノートの取り出し、発行してまとめる）を、WSL の Ubuntu の上で同じコマンドで流した（タグがあるかの問い合わせと、Release を作る `gh` だけは流していない。この WSL には `zip` がないので、同じ形の zip を作る Python の代わりを使った。GitHub Actions の Ubuntu には `zip` が入っている）。次を確かめた。

- ワークフローの YAML が読める。
- 2 つの版で、Release の説明が、リリースノートのその版の節だけになる（次の版の節の前で止まる）。
- まとめたものの中身が実行ファイル 1 つで、tar.gz の中の Linux 版に実行の許可が付いている。
- まとめたものを展開した実行ファイルが動く。Linux 版は疑似端末で起動して盤面が出て Q で終わり、Windows のデスクトップ版はウィンドウ（題名「マインスイーパー」）が出て、閉じると終了コード 0 で終わった。
- Windows の 2 つの実行ファイルの版が 1.0.0（ファイルの版 1.0.0.0）になる。

## 4. 公開の手順（工程 16）

前提: リリースレビュー（工程 15）が承認され、ユーザーが公開を指示している。公開は版ごとに行う（デスクトップ版とコンソール版を続けて公開するときは、手順 3〜5 を版ごとに繰り返す）。

| # | 手順 | 行う人 | 確かめること |
|---|------|--------|--------------|
| 1 | リリースノートの見出しの「（公開前）」を、公開する日付（`（2026-09-28）` の形）に改める | Claude | ワークフローは「`## デスクトップ版 1.0.0（`」で始まる行を探すので、日付の形は問わない |
| 2 | 公開する変更をコミットし、`main` を `origin` に push する（コミットと push はユーザーの指示で行う） | Claude（指示を受けて）かユーザー | `origin/main` に `.github/workflows/release-desktop-console.yml` がある |
| 3 | Actions → 「デスクトップ版・コンソール版を公開」→ Run workflow で、ブランチ `main`、版（`desktop` か `console`）、版番号（`1.0.0`）を選んで起動する。過去の実行の「Re-run jobs」は使わない（Web 版の手順書 4 章と同じ理由） | ユーザー（または、ユーザーの指示で Claude が `gh workflow run`） | 実行が成功する。テストの件数が、ローカルの `dotnet test` と同じ |
| 4 | Releases に、その版の Release（題名「デスクトップ版 1.0.0」など）ができ、公開物と説明が付いていることを確かめる | Claude とユーザー | 6 章の表 |
| 5 | 公開後の確認（6 章）を行う | Claude とユーザー | 6 章の表のすべて |
| 6 | 公開後の確認の結果を、docs/desktop-console/reviews/06-release-review.md に追記する | Claude | — |

- ワークフローは、Release を作る権限（`contents: write`）を、ジョブだけに与えている。リポジトリの Settings → Actions → General の「Workflow permissions」が読み取りだけでも、ジョブに書いた権限で動く。組織の設定で書き込みが禁じられている場合は、Release を作る手順で失敗する（そのときはユーザーに相談する）。
- ワークフローが途中で失敗したら、Release もタグも作られない（Release を作る手順は最後にある）。ログを見て原因を直し、工程 15 の確認項目のうち、直した部分に関わるものを確かめ直してから起動し直す。

### 5.4 公開物の設定

| 項目 | 確かめ方 |
|------|----------|
| ワークフローは手動でだけ動く | `release-desktop-console.yml` の `on:` が `workflow_dispatch` だけ |
| 権限は要るジョブにだけ与える | 既定の権限は `contents: read` だけで、`contents: write` は `release` のジョブだけにある |
| 入力をスクリプトに直接埋め込まない | `inputs` は `env` で渡し、`run` の中では環境変数として読む |
| 版番号とタグの形 | 版番号は `1.0.0` の形でなければ失敗する。タグは `desktop-v1.0.0`・`console-v1.0.0`（仕様書 7.4）で、Web 版の `v1.x.x` とぶつからない |
| リリースノートの節 | docs/desktop-console/release-notes.md に「## デスクトップ版 1.0.0（」「## コンソール版 1.0.0（」の節がある |
| Web 版の公開に影響しない | `deploy.yml` を変えていない |

## 7. 元に戻す方法

| 場合 | 方法 |
|------|------|
| 公開した版に問題がある | 直した版を、版番号を上げて（1.0.1 など）公開する。同じ版番号では公開し直せない（2 章の決定 2） |
| 公開した Release を取り下げたい | Releases でその Release を削除し、タグも削除する（`git push origin :refs/tags/desktop-v1.0.0` など）。削除はユーザーの指示で行う |
