# パラダイムの使い分け

命令型・宣言型・オブジェクト指向(OO)・関数型のどれで書くかを決めるときに読む。設計時にスタイルを選ぶとき、自分の生成コードのスタイルが問題に合っているかを見直すときに使う。

## パラダイムは切り分け方である〔4.1〕

- 定義: パラダイムの違いとは、分割攻略(問題を解ける大きさに切り分けること)の「切り分け方」の違いである。命令型は手順のステップに、OO は責務を持つオブジェクトに、関数型は合成可能な関数に、宣言型は「何を実現するか」と「どう実行するか」に切り分ける。パラダイムの選択とは「この問題は、どの観点で切り分けるともっともシンプルなモデルになるか」というモデリング上の判断である。
- いつ: 新しい処理を書き始めるとき。既存コードのスタイルを変えるかどうか迷うとき。
- する: 単一のパラダイムに固執せず、問題の性質に応じて選び、組み合わせる。一つのシステムに複数のパラダイムが同居してよい。
- 確かめる: 「変更や拡張が来たとき、どこをどう触ることになるか」を選んだスタイルで説明できるか。
- 例外・注意: どれも正しく動く。違いは変更が来たときの姿であり、好みや流行で選ばない。

## OO はメソッドの内側を流れる関心を分離しない〔4.1〕

- 定義: クラスへの分割とカプセル化は「概念」の単位ではうまく働くが、一つのメソッドの内側を流れる処理の関心事(絞り込み・並べ替え・変換・表示)までは分離してくれない。複数の概念を横断する関心事は、関数型を組み合わせると分離できる。
- いつ: 一つのループの中に、絞り込み・並べ替え・整形・出力などが混ざっているとき。
- する: 各関心事をパイプラインの段(絞り込み/並べ替え/変換/各要素への処理)に一つずつ割り当て、直列に合成する。
- 確かめる: 並べ替えのルールを変えるとき並べ替えの段だけ、表示形式を変えるとき変換の段だけを触れば済むか。

```csharp
// before: 並べ替え・絞り込み・表示が一つのループに混在
staffs.Sort((a, b) => a.Number.CompareTo(b.Number));
foreach (var s in staffs)
    if (s.Name.Contains(key) || s.Number.ToString() == key) Print(s);
// after: 段ごとに関心を一つ
var lines = staffs.Where(s => s.Name.Contains(key) || s.Number.ToString() == key)
                  .OrderBy(s => s.Number)
                  .Select(s => $"{s.Name}({s.Number})");
foreach (var line in lines) Print(line);   // 各要素への処理(このためだけに ForEach 拡張を足さない)
```

## 手順が仕様なら命令型、結果が仕様なら宣言型〔4.2〕

- 定義: 命令型は「どうやって (How)」を手順と状態の変化として書き、宣言型は「何を (What)」実現したいかを書いて実行の詳細を処理系に委ねる。手順が仕様なら命令型、結果が仕様なら宣言型。迷ったら「このコードの読み手に伝えたいのは How か What か」を自問する。
- いつ: 書き方を選ぶとき。手書きのループ・インデックス・一時変数が並んでいるとき。
- する: 命令型にするのは、実行手順そのものが関心事の場面に限る(書き込み順序やタイミングが仕様のハードウェア制御、手順自体がアルゴリズムの本体である性能を追い込んだ実装、手順と失敗時の制御が仕様のワークフロー)。データの絞り込み・変換・集計とビジネスルールの定義は宣言型で書く。外側のワークフロー制御を命令型、内側のデータ処理を宣言型にする組み合わせを基本形にする。
- 確かめる: 行数ではなく、読み手が追うべき情報量が減ったか(例: 二重ループが「ソート」であることを頭の中で復元させていないか)。
- 例外・注意: 宣言型が常に優れているわけではない。宣言型は実行過程が見えにくく、デバッグしにくいことがある。手順が仕様の処理を無理に宣言型へ書き換えない。

命令型で意図が埋もれる理由(宣言型にすると裏返る):

| 命令型の問題 | 宣言型での改善 |
|---|---|
| ノイズが多い(ループ変数・インデックス・一時変数が本質を覆う) | 実装詳細が宣言的な操作の内側に隠れる |
| 意図が実装詳細に埋もれる | 「何をしたいか」がそのまま読める |
| 境界やインデックスの管理を書き手が担うのでエラーが起きやすい | 境界チェックや並べ替えの正しさは言語とライブラリが保証する |

## ルールは対応表(データ)として宣言する〔4.2〕

- 定義: ビジネスルールを if 文の連なりではなく、対応表というデータとして宣言する。ルールの追加は表への1行追加になり、既存の制御フローを触らずに済む。
- いつ: 種類ごと・条件ごとに計算を変える分岐が並んでいるとき。
- する: 「条件 → 計算」の対を、対応表またはパターンマッチの一覧として書く。業務ルールの一覧がほぼそのままコードの形になるようにする。
- 確かめる: ルールの一覧を、コードの一箇所を読むだけで一望できるか。

```csharp
static readonly Dictionary<CustomerType, Func<Order, decimal>> DiscountRules = new()
{
    [CustomerType.Premium] = order => order.Total * 0.15m,
    [CustomerType.Regular] = order => order.Total > 1000 ? order.Total * 0.05m : 0,
    [CustomerType.New]     = order => order.Items.Count > 5 ? order.Total * 0.1m : 0
};
```

## OO: 状態と、状態を守るルールを同じ場所に置く〔4.3〕

- 定義: OO の切り分け方の核心は、状態(データ)とそれを扱う責務(振る舞い)を一体にしてオブジェクトに閉じ込めることである。状態と、状態を守るルールが同じ場所にあるのがカプセル化である。
- いつ: 状態を持ち、状態遷移にルールがある対象(業務概念、UI コンポーネント、ワークフローの進行状態など)を表すとき。
- OO が向く合図: 業務の言葉が「主語+動詞」で語られ(例:「顧客が注文を確定する」)、概念と振る舞いがそのまま型と操作として現れるとき〔4.3〕。ただし名詞を機械的にクラス化しない(object-design.md)。
- する: 状態を外に公開せず、変更は操作経由に統一する。ルール(例: 残高を超える引き出しはできない)をその操作の中に置き、迂回経路を作らない。
- 確かめる: 「値がおかしい」というバグの調査範囲が、状態を変える少数の操作に絞られるか(公開された可変状態なら調査範囲はコードベース全体になる)。

## OO: カプセル化は内側へ、ポリモーフィズムは種類の増減へ変更を閉じ込める〔4.3〕

- 定義: カプセル化は一つのオブジェクトの内側に変更を閉じ込め、ポリモーフィズムは共通の契約を通じて、オブジェクトの種類の増減に対して変更を閉じ込める。「共通の流れ」と「変わる部分(差分)」の境界を型で表したものである。
- いつ: 同じ扱いを受ける対象の種類が増えていく見通しが具体的にあるとき。
- する: 利用側は共通の契約だけを見るようにし、差分は各実装の側に閉じ込める。責務の割り当て・依存の向き・SOLID の詳細は object-design.md に従う。
- 確かめる: 種類を一つ追加したとき、利用側のコードが1行も変わらないか。
- 例外・注意: OO の弱点(境界を横断する処理、可変状態によるテストや並列処理の難しさ)は object-design.md の「OO の利点と弱点」を参照。

## 関数型: 純粋関数は考えることを減らす〔4.4〕

- 定義: 純粋関数とは、(1) 同じ入力に対して常に同じ出力を返し、(2) 外部の状態を変更しない関数である。その効能は「考えることが減る」ことである。テストは入力と出力の対を並べるだけで書け、呼び出し順序も隠れた状態も疑わずに済む。
- いつ: 計算・変換・判定(税額計算、割引判定、料金算出など)を書くとき。
- する: 計算は引数だけから結果を返す形にし、グローバルな状態や入出力をシグニチャの外から持ち込まない。
- 確かめる: その関数の正しさを、関数の外側を調べずに確かめられるか。

## 関数型: 副作用は排除ではなく管理する〔4.4〕

- 定義: 副作用は完全にはなくせない(保存も表示も副作用であり、副作用のないプログラムは役に立たない)。実務的な指針は、副作用の排除ではなく副作用の管理である。
- いつ: 計算と入出力・永続化が一つの関数に混ざっているとき。
- する: 純粋に保てる部分(計算・変換・判定)と副作用が必要な部分(入出力・永続化)を分離し、純粋な部分をできるだけ大きくする。
- 確かめる: プログラムの大部分が、テストしやすく予測可能な領域になっているか。

## 関数型: 不変性と、式で書く習慣〔4.4〕

- 定義: 不変データは、変更するかわりに新しい値を返す。一度作られた値は変化しないので、「いつの間にか誰かに書き換えられていた」類のバグが原理的に起こらない。文は「何かを実行する」記述、式は「値を生成する」記述であり、式で書いたコードには途中経過の変数への代入(小さな状態変更)が現れない。
- いつ: 値を受け渡す型を定義するとき。代入を重ねて結果を組み立てているとき。
- する: 言語が不変データやパターンマッチ・式形式の分岐を持つなら、式で書ける処理は式で書く。
- 確かめる: 状態変更の追跡コストが下がり、並列処理やテストで前提にすべき状態が減ったか。

## コレクション変換は宣言型・関数型が定石〔4.4〕

- 定義: 絞り込み → グループ化 → 集計 → 並べ替えのようなパイプラインは、各段が入力を受けて出力を返すだけで元データを書き換えない、純粋関数の直列合成である。コレクションの変換処理は宣言型・関数型のスタイルで書くのがほぼ定石である。
- いつ: コレクションの絞り込み・変換・集計を書くとき。
- する: 対象言語の宣言的なコレクション操作で、仕様の記述(「期間で絞り込み、カテゴリーでまとめ、集計し、売上順に並べる」)がそのままコードの構造になるように書く。
- 確かめる: 別々の関心事(絞り込み・グループ化・集計)が一つのループの中で絡み合っていないか。

## 関数型を過剰に適用しない〔4.4〕

- 定義: すべてを関数型で書こうとすると、かえって読みにくくなる。関数型もまた道具であり、万能薬ではない。
- いつ: 状態遷移が本質の問題(ワークフロー、UI)を不変データで表そうとしているとき。高階関数や合成を多段に重ねているとき。
- する: 状態の受け渡しのためのコードが膨らむなら、OO や命令型に戻す。抽象度の高い合成は、既存コードの流儀とチームの習熟度に合わせて控える。
- 確かめる: 関数型にしたことで、読み手が追う情報量は本当に減ったか。

## 組み合わせの基本形〔4.4、4.5〕

- 定義: OO で構造を作り、関数型でロジックを書き、ワークフロー制御は命令型で書く。ドメインの概念と責務の境界はクラスとインターフェイスで表し、その内側の計算・変換・判定は純粋関数と宣言的なコレクション操作で書く。
- いつ: 一つの機能の中に、状態を持つ概念・データ変換・手順が混在するとき。
- する: 要求ごとに問題の性質を見極め、性質ごとにスタイルを選ぶ(下の判断例)。
- 確かめる: 各部分のスタイルが、その部分の問題の性質に対する素直な表現になっているか。

## 判断例: オンライン注文システム〔4.5〕

パラダイム選択の第一歩は、コードを書くことではなく、各要求が「どんな性質の問題か」を見極めることである。

| 要求 | 問題の性質 | 選ぶスタイル |
|---|---|---|
| 商品カタログの検索・絞り込み | 入力から出力への変換。状態を持たない | 宣言型・関数型 |
| ショッピングカート | 「商品と数量の集まり」という状態+追加・削除・合計のルール | OO(構造)。内側の合計計算は変換なので関数型 |
| 注文処理(検証 → 在庫確保 → 決済 → 確定) | 手順と失敗時の制御(決済失敗なら在庫を解放して中断)が仕様 | 命令型 |

## 判断例: 割引計算の3案〔4.5〕

ルール: プレミアム会員は10%引き、合計1,000超は5%引き、それ以外は割引なし。三案とも同じ結果を返す。

| 案 | 向く条件 | 限界 |
|---|---|---|
| 命令型(if の連なり) | ルールが2〜3個で安定している。もっとも直接的で誰でも読める | ルールが増えるたびに if が伸び、条件の重なりや順序のバグが入りやすい |
| 宣言型・関数型(パターンマッチの純粋関数) | ルールが「条件と計算式の対」として整理できる間。一覧が一望でき、テストも容易。もっとも簡潔 | ルールを実行時に追加・削除したい、ルールごとに複雑な付随処理が要る、となると式に収まらない |
| OO(ルールごとの型+ルールの並び) | ルールが頻繁に増減する、ルールごとにテストや設定を独立させたい | もっとも仕掛けが大きい |

- 選ぶ閾値: ルールの数・変更頻度・実行時に可変である必要。決め手はコードの現在の姿ではなく、変更の見通しである(「ルールはこの先どう増えるか」「誰がどれくらいの頻度で触るか」)。パラダイム選択は好みの問題ではなく、変更に対する設計判断である。
- 見通しの根拠(要求やユーザーの説明にある、ルールが実際に増えてきている)を指せないうちは、OO の仕掛けを先回りして作らない(SKILL.md の判断ルール1)。

## 判断の4問〔4.5〕

1. この問題の本質は何か: 状態と責務のモデル化か(→ OO)、入力から出力への変換か(→ 関数型・宣言型)、手順と制御か(→ 命令型)
2. 変更はどこに来るか: 概念の種類が増えるなら OO の境界が、変換のルールが増えるなら関数型の合成が変更を吸収する
3. 読めるか: どれほど適切でも、読み書きできる人がいなければ保守できない。既存コードにないスタイルは段階的に導入する
4. 一貫性は保てるか: 同じコードベースの同じ種類の問題には同じスタイルを使う。無秩序な混用は適材適所ではなく、ただの混乱である

自分への制約: パラダイムを決めずに書くと、出力は平均的なスタイル(多くは命令型の直接的なコード)に寄る。それは悪いとは限らないが、設計判断の結果ではない。書く前に「この変換は副作用のないパイプラインで書く」「割引ルールは増える見通しがあるのでルールごとの型に分ける」のようにパラダイムと構造を決め、その理由を報告で一言示す。

## 比較表〔4.6〕

| パラダイム | 適用場面 | 利点 | 注意点 |
|---|---|---|---|
| 命令型 | 手順が仕様の処理/ハードウェア制御/性能を追い込むアルゴリズム | 直接的/実行コストを予測しやすい | 意図が実装詳細に埋もれる/状態管理の負担が読み手に乗る |
| 宣言型 | データの絞り込み・変換・集計/ルールや設定の定義 | 意図が明確/簡潔/最適化を処理系に任せられる | 実行過程が見えにくくデバッグしにくいことがある |
| OO | ドメインモデル/状態管理/大規模システムの構造化 | 概念の直接表現/変更の局所化/分業の境界を型で定義できる | 過度な抽象化のリスク/横断的関心事の分離が苦手 |
| 関数型 | データ変換パイプライン/並列処理/計算ロジック | 予測可能でテストが容易/並列処理が安全 | 学習コスト/状態が本質の問題には不向き |

## パラダイム選択のチェックリスト〔4.6〕

このチェックリストは「正しいパラダイム」を機械的に決めるためのものではなく、選択の理由を説明できる状態を作るためのものである。「なぜここは宣言的なコレクション操作なのか」「なぜここはクラスに切り出したのか」に答えられるようにする。

問題の性質:
- [ ] この処理の本質が「状態と責務」「変換」「手順」のどれかを言語化したか
- [ ] 手順そのものが仕様である処理を、無理に宣言型へ書き換えていないか
- [ ] コレクションの絞り込み・変換・集計を、手書きのループで書いていないか

変更への備え:
- [ ] 今後増えそうな変更(概念の追加か、ルールの追加か)と、選んだパラダイムの「変更を吸収する場所」が対応しているか
- [ ] 状態を持つ必要のない処理が、状態を持つクラスとして書かれていないか
- [ ] 純粋に保てる計算ロジックが、入出力などの副作用と分離されているか

文脈:
- [ ] 選んだスタイルを、このコードベースの読み手が読み書きできるか
- [ ] 同じコードベースの同種の問題に対して、一貫したスタイルになっているか
- [ ] 書く前にパラダイムと構造を自分で決め、その理由を説明できるか
