# Think Simple(シンプルさ)

設計を始めるとき、生成したコードを見直すとき、「複雑になってきた」と感じたときに読む。最上位の価値である Think Simple の原則と、複雑さを見分けて削るための語彙をまとめる。

## Think Simple: 複雑な問題は解かない〔8.1〕

- 定義: 複雑な問題を解くにはどうしたら良いか。複雑な問題を解くような羽目に陥らないようにする。ソフトウェア開発の複雑さの多くは、問題そのものではなく解き方の側に潜んでいる。
- 七箇条の中核にある価値がシンプルさである。命名・責務・テスト・リファクタリングはすべて、この価値にコミットするための手段である。
- **シンプルさは知識ではなく実践である。** 「シンプルに作る」と知っているだけでは意味がない。課題に取り組むたびに、シンプルさを上げる方向で実際に手を動かす(価値へのコミット)。
- 複雑さとの戦い方には、工学的アプローチ(分割・モデル化・計画)と、アジャイルのアプローチ(単純なうちに解く・複雑にしない・フィードバックで補正する)がある。両者は排他ではなく、両方揃って初めて複雑さと戦える。

## シンプルさの二つの原則〔8.2〕

### 冷蔵庫にキリンの原則〔8.2.1〕
- 定義: 問題は単純なまま解く。複雑にしない。問題は、出されたときが一番単純である。
- いつ: 要求を読んで解き方を考え始めたとき。「でも、もし〜だったら」と考え始めたとき。
- する: 問題文(依頼・仕様・テスト)にない制約や障害を勝手に足さない。書かれた要求をそのまま満たす、最も単純な解から始める。
- 確かめる: 自分が扱っている制約のそれぞれについて、依頼・仕様・既存コードのどこに根拠があるかを指せるか。指せない制約は、自分が足したものである。
- 例外・注意: 根拠の曖昧な制約が結果を大きく左右するなら、足すのではなく、仮定として明示するかユーザーに確認する(SKILL.md の行動原則3)。

### 開発者Bの思考: 問題を複雑にしているのは自分〔8.2.2〕
- 定義: 起こってもいない問題を次々と付け加え、解決策を示されてもまた新たな問題を持ち出して、問題を解けない方向へ持っていく思考。本人はそれに気付いていない。
- コードでは、「将来こういう要件が来るかもしれない」「あらゆる入力に備えて」と、起こってもいない事態への備えを足し続けることとして現れる。そうして書かれたコードは、開発者Bの思考がそのまま形になったものである。
- する: 備えを足す前に、それが「今の問題」か「まだ存在しない問題」かを区別する。後者なら足さない。
- 例外・注意: 前もってリスクを評価すること自体は重要である。評価はしてよい。問題を足して解けなくすることが誤りである。気付いたリスクは報告し、対策をコードに足すかどうかは要求に照らして決める。

### サイバラの原則〔8.2.3〕
- 定義: 複雑な問題を扱わなければならない状況に、自分を持っていかない。手が付けられないほどバグが溜まったコードを後から効率良く直す魔法は存在しない。
- 「持っていかない」ための日々の実践(4本柱)を、開発の初期から小刻みに繰り返す:

| 柱 | エージェントの実践 |
|---|---|
| シンプルなコーディング | 一手ごとに引き算チェックを行い、複雑さを持ち込まない |
| 常に走るテスト | テストファーストで進め、一手ごとにテストを実行する(testing.md) |
| リファクタリング | 複雑になった箇所をその場で戻す。気づいたときが最も安い(refactoring.md) |
| 継続的なフィードバック | 一手ごとのセルフレビューで、ずれを早い段階でつぶす(quality-gates.md) |

- リファクタリングは複雑になったものを**戻す**技法、Think Simple はそもそも複雑に**しない**態度である。戻す技法を毎日使い続けることが、陥らない態度の実践形になる。両者は対であり、どちらか一方では成立しない。

## 複雑さの正体を見分ける〔8.3〕

### 本質的複雑さは封じ込め、偶発的複雑さは排除する〔8.3.2〕
- 定義: 本質的複雑さは問題領域そのものが持つ複雑さ(例: 税制の計算ルール)。偶発的複雑さは、問題と関係なく、実装の都合や解き方のまずさで持ち込まれた複雑さ(例: ビジネスロジックに紛れ込んだ設定読み込みや DB 接続、将来のためだけの抽象階層)。本質的複雑さは封じ込め、偶発的複雑さは排除する。
- いつ: コードが複雑だと感じたとき。複雑な処理を設計するとき。
- する: 本質的複雑さは担当する型の境界の内側に閉じ込め、外からはシンプルなインターフェイスに見えるようにする(object-design.md)。偶発的複雑さは、問題の一部ではなく持ち込んだ荷物なので削る。
- 確かめる: その複雑さを取り除いたとき、要求のどれかが満たせなくなるか。満たせるなら偶発的である。
- 例外・注意: **「本質的だから仕方ない」の罠。** 「本質的に複雑」が「複雑さが不可避」という意味なら同語反復で、何も説明していない。本質的だと決めつけて諦める前に、本当に避けられないのかを考察する。「本質的」というラベルの下には、避けられたはずの偶発的複雑さがかなりの割合で隠れている。

### YAGNI: 将来のための複雑さは今のムダ〔8.3.3〕
- 定義: You Aren't Gonna Need It。必要になってから作る。偶発的複雑さの中でも、最も善意の顔をして入り込むのが「将来への備え」である。
- いつ: インターフェイス・抽象基底クラス・ジェネリクス・拡張ポイント・設定項目を足そうとしたとき。
- する: 今日の問題を解く最小の形で書く。二つ目の実装が実際に必要になったとき(または要求に明記されたとき)に抽象化する。
- 確かめる: その抽象は、今日の問題の何を解いているか。解いているのが「いつか来るかもしれない要件」なら削る。
- 例外・注意: **必要が見えてから入れる抽象は形が合うが、必要が見える前に入れる抽象は当てずっぽうである。** 先回りした拡張ポイントは、実際の要件が来たときに形が合わないことが多い。それまでの間ずっと、読む人全員に「この階層は何のためにあるのか」と考えさせるコストを払わせ続ける。読解コストを下げる抽象との線引きは SKILL.md の判断ルール1〜3 に従う。

```csharp
// before: 使われるのは CSV だけなのに「将来のデータソース」に先回り
interface IDataSource<T> { IEnumerable<T> Read(); }
abstract class DataSourceBase<T> : IDataSource<T> { /* Read → ReadCore */ }
class CsvDataSource(string path) : DataSourceBase<string[]> { /* ReadCore */ }

// after: 今必要な最小の形
static IEnumerable<string[]> ReadCsvLines(string path)
    => File.ReadLines(path).Select(line => line.Split(','));
```

### シンプルと簡単は違う〔8.3.4〕
- 定義: シンプルに表現したり、シンプルな表現を理解したりするのが、簡単だとは限らない。抽象的な記述は、シンプルでかつ難解なことが多い。シンプルさの基準は、書きやすさでも初心者向けであることでもなく、**意図がまっすぐ表現されていて、余計なものがない**ことである。
- いつ: 宣言的な書き方と手続き的な書き方で迷うとき。「分かりにくいから」と表現を避けたくなったとき。
- する: 慣れの問題(簡単かどうか)と構造の問題(シンプルかどうか)を混同しない。例: 同じ意図を宣言的に書いた1行は、ループ10行よりシンプルだが、慣れない読み手には簡単に見えない。見えないのは慣れの問題であって、構造の問題ではない。
- 例外・注意: 読み手の慣れと既存の流儀をどう扱うかは SKILL.md の判断ルール8 に従う。この区別を欠いたまま特定の表現を禁じる規約は、保守性を上げない(quality-gates.md)。

## シンプルさは意図の表現に現れる〔8.4〕

### シンプル=S/N比が高い〔8.4.1〕
- 定義: シンプルなコードとは、S/N比の高いコードである(S/N比・意図・ノイズの定義は modeling.md)。説明責任(What を How より前に出す)、宣言型スタイル、メソッド抽出、コメントは Why だけ、はすべてノイズを減らして意図を際立たせる技法であり、シンプルさはそれらが最終的に到達する状態の名前である。

### 読む人が扱える複雑さの限界を超えない〔8.4.2〕
- 定義: 美しいソースコードの指標は、シンプルであること。そのソースコードを読む人が扱える複雑さの限界を超えないこと。人は一度に複雑なことを細部まで完璧には考えられない。それがサブルーチンがある理由である。基準線は機械の都合ではなく、人間の認知の限界に引かれる。
- いつ: 入れ子のループ、込み入った添字計算、同時に追う状態が多いコードを書くとき。
- する:
  - 二重ループは、内側の処理に名前を付けて抽出し、各メソッドを一重ループにする(「複数の名前から指定文字列を見つける」は一重ループの問題の組み合わせである)。ネストの目安とそれを超える条件は SKILL.md の判断ルール10 に従う。
  - 多次元の配列の配列は一次元の配列とアクセサで扱い、座標変換のような複雑さは一箇所に封じ込めて、利用側に考えさせない。
- 確かめる: 各メソッドを読むとき、同時に頭に置く必要がある事柄は少ないか。
- 例外・注意: 限界を超えたコードは、正しくても読めない。読めないコードは検証できず、理解負債になる。

```csharp
// 二次元の盤面を一次元配列で持ち、座標変換をインデクサーの一箇所に封じ込める
class GameBoard {
    const int Size = 8;
    readonly int[] cells = new int[Size * Size];
    public int this[int row, int column] {
        get => cells[row * Size + column];
        set => cells[row * Size + column] = value;
    }
}   // 利用側は board[row, column] と書くだけで、内部が一次元であることを考えずに済む
```

## シンプルさにコミットする〔8.5〕

### 自己点検の言い換え表〔8.5.1〕

設計に迷ったとき、レビューで指摘を書くとき、自分の作業計画を立てるときに、思考が左右どちら側にいるかを点検する。左側は真面目で勤勉ですらあるからこそ危ない。

| シンプルでない考え方 | シンプルに考えると |
|---|---|
| この複雑な問題をどうやって解こうか? | もっと問題を単純にするにはどうすればよいか? |
| 将来の複雑な問題にどうやって立ち向かっていくべきだろうか? | 今後どうやれば問題を複雑にしないで済むだろうか? |
| どうすればよいのだろうか? | 何をやろうか? |
| 考え得る解決策をすべて列挙して、そのすべてをよく検討しよう | 現在ある解決策を少しずつ実際に試し、結果のフィードバックで次の手を調整しよう |
| 障害になるものをすべて列挙し、そのすべてについて対策を練ろう | できない・やらない理由ばかり列挙せずに、まずやり始めて、その結果からフィードバックを得よう |

### 二つの原則のコーディングでの実践形〔8.5.2〕

| 原則 | 実践形 | 手段 |
|---|---|---|
| サイバラの原則 | 仕様も検証方法も明確でない大きな問題ではなく、明確な仕様があり検証も自動で行われる単純な問題(「二月の最終日か」「うるう年か」)と向き合う方向へ、自分を持っていく | 命名、What 視点、責務の分割(naming.md、object-design.md) |
| 冷蔵庫にキリンの原則 | すべてを考慮して一度に解こうとせず、その時点の問題を一つずつ実際に解きながら解にたどり着く | テストファースト(testing.md) |
| (戻す) | 複雑になったものを戻す | リファクタリング(refactoring.md) |

例: 日付の妥当性チェックを、うるう年まで考慮した条件分岐の入れ子として一気に書かない。「日付として正しくなければ例外を投げる」とまず書き、「日付として正しいとは、年が正しく、月が正しく、日が正しいこと」と一段ずつ確定していく。

## 引き算の設計〔8.6〕

- 定義: 何を作らないか。何を削るか。どこで「それは要らない」と言うか。足し算が AI の得意技になったからこそ、仕事は引き算になる。
- 背景: 生成コストが激減し、複雑さが安く量産される時代になった。一方で理解は速くならず、安く量産された複雑さのツケは理解負債として積み上がる。しかも AI の出力には、確率的にもっともらしい「あれもこれも」の考慮を盛り込み、頼まれていないのに「将来の拡張のため」とジェネリクスの階層やデザインパターンを導入する癖がある。YAGNI 違反を善意の顔で平然と行う。
- いつ: コードを生成した直後、差分を報告する前。自分の生成物は常に引き算の対象として見る。
- する: 自分の生成物から、頼まれていない抽象・パターン・備えを削る。削る理由は精神論(「もっとシンプルに」)ではなく、次の語彙で説明する。
- 確かめる: 下の点検表の各行に、該当箇所がないか。

| 点検すること | 語彙 | 削り方・報告の例 |
|---|---|---|
| 実装が一つしかないインターフェイス階層、使われていない拡張ポイント・引数・設定項目 | YAGNI 違反 | 「この階層は YAGNI 違反なので、実装が二つ目に増えるまで削った」 |
| ビジネスロジックに紛れ込んだ設定読み込み・DB 接続・ログなど | 偶発的複雑さ | 「設定読み込みは偶発的複雑さなので、ビジネスロジックから分離した」 |
| 意図に存在しない一時変数・添字・手続きの記述 | ノイズ(S/N比が低い) | 「このループはノイズが多いので、意図が見える宣言的な形に書き直した」 |
| 問題文にない入力・状況への備え(起こってもいない事態への防御) | 冷蔵庫にキリン/開発者Bの思考 | 「要求にない○○への対応は入れていない。必要なら追加する」と作らなかったものを報告する |
| 頼まれていないデザインパターン・ジェネリクス化 | YAGNI 違反/偶発的複雑さ | 必要が見えてから入れる。見送った候補は報告に一行添える |

- 例外・注意: テストのための差し替え口や、読解コストを下げる抽象(メソッド抽出・概念への命名・データの群れへの型付け)は削る対象ではない(SKILL.md の判断ルール2・3)。本質的複雑さを封じ込めるための境界も削らない。公開境界での前提条件のガード節・型による検証は契約の明示(説明責任の実行形)であり、削る対象ではない(quality-gates.md)。削るのは、要求にない入力や状況をわざわざ処理する分岐である。複雑さを断る語彙こそが、七箇条の中核であるシンプルさを守る最後の砦である。
