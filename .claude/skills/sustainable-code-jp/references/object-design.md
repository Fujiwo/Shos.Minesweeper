# オブジェクトの設計: 責務・境界・協調・依存

クラスやモジュールの分け方、責務の置き場所、公開する操作、依存の向きを決めるとき、または責務の混ざったコードを切り出すときに読む。要点は、現実世界をプログラムに写すことではなく、関心事ごとに責務と依存を配置し、変更の影響を閉じ込めることである。

例の題材は、ボール・パドル・ブロックの集まりからなるブロック崩しゲームである(ボールが跳ね返ってブロックを消し、パドルはキー入力で動く。ステージ・ブロックの種類・得点がある)。

## 設計を問う4つの問い〔5.導入〕

「何かが整理された感じ」を言葉にできなければ、設計はできない。分割を決めたら次に答える。

1. なぜこの単位に分けたのか(どの関心事に対応するか)
2. 二つのオブジェクトの状態に触る処理は、どちらの仕事にするのか
3. 公開する操作の名前と範囲は、何を根拠に決めたのか
4. 種類や構成を増やしたくなったとき、どこが変わり、どこが変わらずに済むのか

## 関心事の列挙が先で、クラスはその結果〔5.1〕

- 定義: モデルとは関心の外のものを取り去ってシンプルにしたものである。目的に照らして何を含め、何を捨てるかを選び取る選択こそが設計である。クラスの一覧が先にあるのではなく、関心事の整理が先にあり、その結果としてクラスが決まる。現実世界の名詞を並べることと、目的に合うモデルを設計することは別の行為である。
- いつ: 新しい機能のクラス構成を考えるとき。要求文の名詞をそのままクラスにしようとしているとき。
- する: 目的に必要な関心事を先に列挙する(例: 進行/移動/操作/状態)。各関心事に対応する単位を作る。行為の側(「入金を依頼される」「本人確認をする」)からも場と責務を捉え直す。演出や表示のように目的の本質でないものは、モデルの外に置くことを検討する。
- 確かめる: 各クラスがどの関心事に対応するかを1行で言えるか。関心事に対応しないクラスや、目的に使われない属性がないか。
- 例外・注意: 何を含めるかの正解は、ソフトウェアの目的と今後どこが変わりそうかで決まる。

「クラス」は3つのレベルで使われるので混同しない: 概念レベル=責任の集合/設計レベル=応答できる操作の集合/実装レベル=コードとデータ(言語の構文)。責務・協調・依存の判断は主に概念と設計のレベルで行い、特定言語の構文に依存させない。継承も、設計レベルでは kind-of(〜の一種である)の関係として判断し、実装レベルの派生クラスの構文と混同しない〔5.1〕。3つのレベルを同じ名前で貫けること(語彙を言い換えずに済むこと)は OO の強みである。

## OO の利点と弱点〔5.1〕

OO も万能ではない。弱点は他のパラダイムで補う(paradigms.md)。

| | 内容 |
|---|---|
| 利点: 柔軟な抽象化 | インターフェイスや抽象型で、実装の詳細に依存しない共通の契約を定義しやすい |
| 利点: GUI との親和性 | 状態を持つ UI 部品とイベント処理を一つのオブジェクトとして直感的に表せる |
| 利点: カプセル化による関心事の分離 | データと振る舞いを一体にして内部を隠し、仕様変更の影響範囲をオブジェクト内に閉じ込めやすい |
| 利点: ポリモーフィズム | 呼び出し側を変えずに、新しい種類のオブジェクトを追加・差し替えできる |
| 弱点: 実行時の追跡・デバッグの難しさ | 状態や動的ディスパッチで振る舞いが実行時に切り替わり、読むだけでは実際の挙動を把握しにくい |
| 弱点: 横断的関心事への弱さ | ログ・認証・認可のように複数のオブジェクトを横断する処理を、責務の分割だけで扱うのは難しい |
| 弱点: 可変状態の共有による並行処理の難しさ | 内部状態が変化するため、排他制御やデバッグが難しくなりやすい |

## 責務の割り当て〔5.2〕

- 定義: 設計の中心作業は「それは、どのオブジェクトの仕事ということにするか」を決めることである。責務の所在に、現実世界のどこかに書かれた正解はない。設計者が決める。
- いつ: 一つの処理が二つ以上のオブジェクトの状態に触っているとき。
- する: 処理を「誰の状態を変えるか」で分け、それぞれを状態の持ち主に割り当てる(例: ブロックを消すのはブロックの集まりの責務、跳ね返るのはボールの責務)。各オブジェクトは自分の状態だけを変更し、相手の状態には触れない。
- 確かめる: 他のオブジェクトの状態を直接書き換えている箇所がないか。

## 「ひとことで言うと何?」テスト〔5.2〕

- 定義: 責務を割り当てたら「このクラスの仕事をひとことで言うと何?」と問う。ひとことで言えないなら、複数の責務が混ざっている可能性がある。そのひとことがそのままクラスの名前になっているのが、良い割り当ての状態である。
- いつ: クラス・モジュール・メソッドを作ったとき、名前を付けるとき、レビューするとき。
- する: 仕事をひとことで書き出す。「〜と〜をする」のように列挙が入るなら、責務ごとに分ける。
- 確かめる: ひとことと名前が一致しているか。一致しないなら、名前か分け方のどちらかを直す(命名の詳細は naming.md)。

## 責務のスコープは小さいほどよい〔5.2〕

| 責務の範囲 | 置き場所 |
|---|---|
| メソッド一つ分 | 変数やプライベートメソッドへの切り出し |
| クラス全体に関わる | クラスのメソッドやプロパティ |
| そのクラスの守備範囲を超える | 他のクラスへ出す |
| どこでも使える汎用のもの | 汎用のクラスや関数 |

- 巨大な一つの関数より、責務ごとに分けた小さな単位の集まりの方がシンプルである。ただし闇雲に分けない(分け方の3観点は modeling.md)。
- スコープは育つ。式 → 関数 → そのデータの持ち主のメソッド、と責務の置き場所を見極めながら移していく。

## 変更理由を一つにする〔5.2〕

- 定義: 単一責務の原則は「クラスに変更が起こる理由は一つであるべき」という原則であり、その真価は仕様が変化するときに発揮される。変更理由がいくつもあるのに修正先が1箇所しかないのが、違反の実際の姿である。
- いつ: 一つの関数・クラスが大きくなっているとき。どの仕様変更でも同じ場所を直すことになるとき。
- する: 独立に変わりうる仕様の部分(例: 物理、操作、構成、ルール)を変更理由として列挙し、「この変更 → この修正先」を1行ずつ対応させる。一つの理由が一つのオブジェクトに対応するように責務を配り直す。
- 確かめる: 各変更理由の修正先が、一つずつ別のオブジェクトになっているか。
- 例外・注意: SRP を「クラスを小さくする規則」と読み違えない。機械的に細かく刻んでも良い設計にはならない。問うべきは「この部分が変更される理由は何か。その理由は一つか」である。

## 名前とサービス境界〔5.3〕

- 定義: 名前を付けることは、「この範囲の概念をこう呼ぶことにする」と宣言し、それであるものとそうでないものの境界を引くことである。境界は外から見て決め、実装は名前に表さない。実装を名前に漏らすと、実装を変えたとたんに名前が嘘をつき始める。
- いつ: クラスや公開メソッドの名前と公開範囲を決めるとき。
- する:
  - 先にサービスを利用する側のコードを書き、そこから各オブジェクトが公開すべき操作とその名前を逆算する。利用者の関心がそのまま公開操作の一覧と名前になる。
  - 内部のデータ構造やアルゴリズム(配列である、走査している)を名前に入れない(`BrickArray` ではなく `BrickSet`)。
  - 利用者固有の事情を名前に入れない(`collideWithGameBall` ではなく `collideWith`)。サービスの名前は、サービス自身が提供する内容だけを表す。
- 確かめる: 利用者のコードが、相手の内部の事情(フラグ・座標などの状態)に踏み込んでいないか。内部実装を変えても利用者と名前が変わらずに済むか。
- 名前と公開範囲が利用者視点で決まっているとき、オブジェクト間に契約が成立する。協調も依存の設計も、この契約の上に成り立つ(契約の書き方は quality-gates.md)。

```csharp
// before: 利用者が相手の実装の都合に踏み込んでいる
if (paddle.RightPressed) paddle.X += 7;
// after: 利用者の関心だけを公開サービスとして呼ぶ
paddle.Step();
```

## 協調: 関連・集約・委譲を役割分担として捉える〔5.4〕

| 関係 | 意味 | 判断 |
|---|---|---|
| 関連 | 意味的なつながりがあり、メッセージをやり取りする | 関係の濃さに応じて、保持するか、その場で引数として渡すかを選ぶ |
| 集約 | 全体が部分を持つ(has-a) | 全体から部分への操作の伝播(全体のリセット → 部分のリセット)があるか |
| 委譲 | 受け取った仕事を、それにふさわしい相手へ任せる | 下の Expert と「役割の所在」に従う |

## 情報を持つ者に判定を任せる(Expert)〔5.4〕

- 定義: 責務は、それを果たすのに必要な情報を持つ者へ割り当てる。情報と責務を同じ場所に置く。
- いつ: ある判定に必要なデータを、別のオブジェクトから取り出して計算しているとき。
- する: 判定そのものを、データを持つオブジェクトのメソッドにする(例: 当たっているかの判定は、自分の位置と大きさを知るブロック自身が引き受ける)。
- 確かめる: 判定のために他オブジェクトの内部値を取り出す箇所がなくなったか。

## 委譲しても役割の所在は移らない〔5.4〕

- 定義: 委譲するかどうかと、「それが誰の役割か」は別問題である。委譲しても役割の所在は移らない。オブジェクトの役割とは外部に向けてどのようなサービスを提供するかであり、内部でどう実現するか(自前でやるか、誰かに任せるか)とは独立に決まる。例: Game がキー入力への反応を Paddle に委譲しても、「プレイヤーの入力を受け付ける」役割は Game が外部に対して負い続ける。
- いつ: 委譲を重ねているとき。「結局この処理は誰が責任を持っているのか」に答えにくいとき。
- する: 各オブジェクトについて「外部へのインターフェイス(公開しているサービス)」と「内部の実現手段(委譲先)」を分けて言えるようにする。責務の置き場所が変わったら(例: 「2回当てないと消えない」仕様が来たら、消えるかどうかの判断を個々の要素へ移す)、協調の形を組み替える。
- 確かめる: 委譲の連鎖をたどらずに、責任を持つオブジェクトを名指しできるか。

## 再利用のための継承は合成に変える〔5.4〕

- 定義: 共通処理を持つ基底クラスを作って継承で再利用するのではなく、共通処理を持つクラスのインスタンスを、必要とする側が保持する(合成優先の原則)。合成関係にあるオブジェクトへ処理を転送する実装手法が委譲である。
- いつ: 「どちらも移動する」のような共通処理を理由に、基底クラスを作ろうとしているとき。
- する: 共通処理を独立したオブジェクトにし、各クラスがそれを持って仕事を任せる。
- 確かめる: 各クラスの全体像が、基底クラスを見なくても把握できるか。
- 例外・注意: 継承の害は、責務が基底と派生に分散して全体像が見えなくなること、階層が深いほど結合が高まり基底への変更が派生を意図せず壊すこと(壊れやすい基底クラス問題)、変更の影響範囲が予測しにくくなることである。一方、種類として振る舞いを差し替えるための多態の継承(is-a で契約を守る)は別である。分かれ目は「共通処理を再利用したいという動機だけで階層を作っていないか」の一点である。

横断的関心事(ログ・認証・認可・トランザクション管理)は委譲だけでは力不足なことがある。AOP、デコレータ、依存性注入(DI)を選択肢にする。

## 依存: ひとつの変更 → ひとつの修正〔5.5〕

- 定義: 保守性の基本は「ひとつの変更 → ひとつの修正」である。凝集度が高い=一つの変更理由に関係するコードが1箇所に集まっている(修正が1箇所で済む)。結合度が低い=あるオブジェクトの内部変更が他へ波及しない(修正が閉じる)。高凝集とは一つの明確な目的と名前を持ち中身が首尾一貫していること、疎結合とは単純なインターフェイスを持ち、関係のないものとはできるだけ話さないことである(疎結合の本来の意味は modeling.md の「独立したものは独立したまま表す」)。
- いつ: 依存関係を作る・評価するとき。
- する: 各オブジェクトを、相手の公開サービス(契約)だけに依存させる。仕様として互いに独立に決まる事柄(例: 物理法則とブロックの並べ方)の間に依存を作らない。
- 確かめる: 一つのオブジェクトの内部実装(例: 配列から別のデータ構造へ)を変えても、他のオブジェクトが1行も変わらないか。

## 変更要求シナリオ → 壊れる箇所 → 原則の順に考える〔5.5〕

- 定義: 原則が先にあって設計を決めるのではない。「この変更が来たら、どこが壊れるか」という問いが先にあり、原則はその問いに答えるときの語彙と判断基準を与える。
- いつ: 設計を評価するとき。拡張の仕組みを入れるか迷うとき。
- する: 具体的な変更要求を持ち込み、壊れる箇所を特定してから手当てを選ぶ。

| 変更要求の型 | 壊れる箇所 | 手当て(原則) |
|---|---|---|
| 構成を増やす(ステージ追加) | 構成ロジックを直書きしたクラス | 構成をデータとして外から与える(OCP) |
| 種類を増やす(硬いブロック) | 種類で分岐する switch が育つ | 「自分で答える」責務を各種類へ移す(多態、OCP、LSP) |
| 入力方式を変える(マウス・タッチ) | 装置の詳細を知っている上位のクラス | 上位が定めた抽象に詳細側を合わせ、外から注入する(DIP、DI)。利用者が使わない操作への依存を強制しない(ISP) |

- 確かめる: 変更要求ごとに「新しいクラスやデータを足すだけで、既存のクラスが変わらない」状態になったか。
- 例外・注意: 手当ては、変更の見通しが具体的なときだけ入れる(判断ルールは SKILL.md の「シンプルさ vs 拡張性」)。多態で分岐を型の差し替えに変えると、どの実装が呼ばれるかは実行時にしか確定せず、読むだけでは追えなくなる。

## SOLID 原則〔5.5〕

| 原則 | 定義 |
|---|---|
| 単一責務の原則(SRP) | それぞれ一つだけの責務を持つべき |
| 開放閉鎖の原則(OCP) | 拡張に対して開かれて、修正に対して閉じているべき |
| リスコフの置換原則(LSP) | 派生クラスのオブジェクトが基底クラスのオブジェクトと置換可能であるべき |
| インターフェイス分離の原則(ISP) | インターフェイスの実装先で使わないメソッドがないようにインターフェイスを分ける |
| 依存性逆転の原則(DIP) | 上位モジュールは下位モジュールに依存してはならない。詳細が抽象に依存すべき |

## デメテルの法則〔5.5〕

メソッドが呼んでよいのは、自分自身・引数で渡されたもの・自分が生成したもの・自分が直接保持しているものだけにする(他人と話すな)。内部構造をたどった瞬間、たどる側はその内部構造の変更に巻き込まれる。問い合わせは判断ごと1段で済ませる。

```csharp
if (ball.Position.Y > screen.Height) GameOver();   // before: 内部構造をたどる
if (ball.HasFallenBelow(screen.Height)) GameOver(); // after: 判断ごと問い合わせる
```

## パターンは協調の典型形として使う〔5.5〕

- 定義: デザインパターンと GRASP は、カタログとして暗記するものではない。「この問題には、この責務配置と協調の形が効く」という典型形として使う。
- いつ: パターンを使いたくなったとき。
- する: 問題(例: 跳ね返り方が複数あり切り替えたい)を先に言い、責務の配置(それぞれの計算方法を独立したオブジェクトへ)を決め、その結果としてパターン(Strategy)になる順で使う。パターン名は、設計を語る語彙として報告に使う。
- 確かめる: パターンの名前を外しても、その構造を問題から説明できるか。

GRASP のうち、判断に使うもの:
- Expert: 責務は、必要な情報を持つ者へ割り当てる
- Creator: オブジェクトの生成は、それを保有・利用する者へ割り当てる
- Low Coupling / High Cohesion: 「ひとつの変更 → ひとつの修正」の評価軸
- Polymorphism: 種類による分岐は、型の差し替えで表す

## 原則は補助線〔5.5〕

- 定義: SOLID は補助線である。高凝集・疎結合、SOLID、デメテルの法則、デザインパターン、GRASP は、いずれも「この変更が来たらどこが壊れるか」を見積もるための語彙と判断基準であり、暗記して機械的に適用する規則ではない。原則もパターンも、変化する関心ごとに責務と依存を配置し、変更の影響を閉じ込めるという同じ一つのことを別の角度から述べている。
- いつ: 原則名を根拠に構造を足そうとしているとき。
- する: 原則名だけを理由にせず、どの変更がどこを壊すのかを具体的に示してから適用する。
- 確かめる: 「どの原則に従ったか」ではなく「どの変更が閉じるようになったか」で説明できるか。

## 設計を最小の図で説明する〔5.6〕

- 定義: 設計は、決めて終わりではなく、説明できて初めて機能する。図の価値は、正式な文書ではなく、思考の枠組みと対話の道具にある。描き込みすぎると、かえって伝わらなくなる。
- いつ: 複数のクラスの責務と依存を変えたとき。設計の選択肢をユーザーに示すとき。
- する: 必要なら Mermaid のクラス図などで、集約・依存の向き・継承の範囲だけを示す。「もっとも意図が伝わるシンプルな図は何か」を自問して要素を絞る。
- 確かめる: 図から、逆向きの依存がないか、どこにも置き場のない責務(例: 得点)がないかが読み取れるか。

## OO を絶対化しない〔5.6〕

- 定義: OO がすべての問題に最適なわけではない。構造は OO、その内側のデータ変換は関数型で書く(組み合わせ方は paradigms.md の「組み合わせの基本形」)。
- いつ: 集計(例: 消えた要素の点数の合計)を、オブジェクトの協調として書こうとしているとき。モデルの状態から描画命令の列への変換も、変換として書く方が見通しが良い場合がある。
- する: 集計・変換はデータの変換として書く(paradigms.md)。どこで何を使うか: 責務と状態の構造化には OO、データ変換と並行処理には関数型、性能が支配する領域にはデータ指向設計。
- 確かめる: その処理を、オブジェクトの協調より変換として書いた方が素直ではないか。
- 関心を選び取り、変更理由を観察し、境界を決め、依存の向きを整える、という判断は、関数・モジュール・サービスの境界設計にもそのまま使える。

## 自己点検と報告の語彙〔5.7〕

クラス構造は瞬時に生成できるが、責務の所在・依存の向き・名前とサービス境界の妥当さは生成しただけでは保証されない。自分が生成・変更した構造を、次の3問で点検する。答えられない場合は構造を見直すか、報告で不確かさとして示す。

- [ ] このクラスの変更理由は一つか(変更理由を列挙し、修正先と対応させて示せるか)
- [ ] この依存は抽象に向いているか(相手の公開サービスだけに依存し、内部構造をたどっていないか)
- [ ] この名前は利用者の関心を表しているか(実装や利用者固有の事情が漏れていないか)

責務の境界と依存の向きは、テストのしやすさに直結する。依存が公開サービスだけに限られたオブジェクトは単独で検証できる(testing.md)。
