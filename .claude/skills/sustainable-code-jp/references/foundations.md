# 基盤: 美しいコードと七箇条

実装するとき、コードの品質を評価するとき、SKILL.md のセルフチェックの各項目を深く判断したいときに読む。美しいコードの定義、七箇条の各箇条の原文基準と判断、技術的負債と理解負債、この判断基準の前提と判断の軸、用語集をまとめる。

## 美しいコードとは何か〔1.1、0.4〕

- 定義: **美しいコードとは、拡張と保守がしやすいコードのことである。** 見た目の綺麗さやインデントの揃いのことではない。**プログラミングという作業は、常に現状のコードの変更である。** 動くのは当たり前の前提であり、比べるべきは「汚くて動く」と「きれいで動く」である。プログラムは寿命を終えるまで動き続けられて、ようやく「動くプログラム」と言える。
- サステナブルコードとは、人間と AI の双方が理解し続けられ、変更し続けられるコードである。意図を伝える名前、狭いスコープ、明確な責務の境界は、人間の認知負荷を下げると同時に、AI が文脈を誤読しにくい環境も作る。
- 汚いコードは負債となり、利息のように開発コストを膨らませる。美しいコードは将来の変更を容易にする資産である。
- いつ: 「動けばよい」「きれいにするのは後で」と考えたくなったとき。記述量の少なさや書く速さで案を選びそうになったとき。
- する: 次の三つを満たすように書く。変更が容易である/テストできる/理解しやすい。コードの良し悪しは、書いた瞬間の記述量ではなく、ライフサイクル全体のコストで評価する。
- 確かめる: 次にこのコードを変更する人(半年後の自分や別のエージェントを含む)が、どこを直せばよいかを迷わず特定できるか。
- 例外・注意: 規模が2倍になると、要素どうしの関係の数はそれ以上に増えるので、複雑さは2倍より大きくなる。美しさを保たないと悪循環で複雑になり、開発は持続できなくなる。AI を使った開発でも同じことが起こる。

### 美しいコードが向上させる品質〔1.1.2、1.3.1〕

- 美しいコードが直接向上させるのは、**理解容易性**(意図が明確)・**変更容易性**(修正・拡張が容易)・**検証性**(テストしやすい)の三つである。保守性は、この三つが組み合わさって得られる品質の総称である。
- これらは開発者から見える内部品質であり、長期的にユーザーから見える外部品質を支える。効率性は可読性とトレードオフになりうる(扱いは SKILL.md の判断ルール5)。

## 美しいコードのための七箇条〔1.2〕

七箇条は個別のテクニックではなく、相互に関連し合う一体の指針である。統合的に適用して最大の効果を発揮する。1行版は SKILL.md のセルフチェックにある。ここでは各箇条の原文の基準と、判断の仕方を書く。

### 第一箇条: 意図を表現〔1.2.1〕
- 定義: 意図が表現されていること/意図の理解が容易であること/意図以外の記述が少ないこと/How(どうやってやるか)でなく What(何をやるか)が記述されていること/できれば、Why(なぜやるか)も記述されていること。
- いつ: ループ、インデックス、一時変数、文字列の組み立てなど、手続きを書くとき。
- する: コードはコンピューターへの指示ではなく人間同士のコミュニケーション手段として、人が人に話すように書く。ループ変数やインデックスといった意図以外のノイズを除き、What を書く。
- 確かめる: コードをそのまま読み上げると、「何をするか」の文になるか。
- 例外・注意: `return a + b;` と `var sum = a + b; return sum;` は厳密には意図が異なる記述である(後者は「a + b を合計値とする。合計値を返す」)。どちらが良いという話ではない。表したい意図に合う方を選ぶ。

```csharp
// before: How(手続き)がノイズとして混ざる
var result = "";
for (var index = 0; index < names.Length; index++) {
    if (index > 0) result += ", ";
    result += names[index];
}
return result;
// after: What(何をするか)だけが残る
return string.Join(", ", names);
```

### 第二箇条: 単一責務の原則〔1.2.2〕
- 定義: プログラムの単位が唯一の仕事を記述していること/その仕事がそのプログラム単位内で記述しつくされていること。この二つを満たすことを**高凝集**という。責務が単一であるだけでなく、その責務が他にできるだけ漏れていないことが大切である。単一責務の原則(SRP)は「クラスが変更される理由は一つでなければならない」と定義される。
- いつ: 一つのクラスやメソッドに、計算・永続化・表示の形式など、異なる理由で変わるものが並んだとき。
- する: 変更理由ごとに単位を分ける(例: 従業員クラスに給与計算・データ保存・レポート生成が同居していたら、`BonusCalculator`・`EmployeeRepository`・`EmployeeReportGenerator` に分ける)。
- 確かめる: その単位の変更理由を列挙すると一つか。その仕事を記述するコードが、他の単位に散らばっていないか。
- 例外・注意: 責務の割り当て方と、SRP を「小さくする規則」と読み違えないことは object-design.md にある。

### 第三箇条: 的確な名前付け〔1.2.3〕
- 定義: 名前が唯一の仕事を一言で必要十分に表す/同じものは同じ名前、違うものは違う名前。名前は利用者の視点で決める。
- する: 基準の全文と技法(SON、命名のアンチパターン、段階的な改善の手順)は naming.md に従う。

### 第四箇条: Once And Only Once〔1.2.4〕
- 定義: 同じ意図のものが重複して書かれていないこと/それであるものとそれでないものの区別が付くこと。同じ意図のコードが重複していなければシンプルになり、実装・拡張・保守で同じ作業を繰り返さずに済む。
- いつ: 似たコードを書こうとしたとき、見つけたとき。
- する: 重複の種類を見分ける。実装の重複(同じコードが複数箇所にある)/知識の重複(同じビジネスルールが複数箇所で実装されている)/構造の重複(似た構造が繰り返される)。同じ意図だと判定できたら一箇所に集め、他はそれを呼ぶ(例: 合計額の計算は小計の計算を呼ぶ)。
- 確かめる: そのルールを変えるとき、直す場所が一箇所で済むか。
- 例外・注意: 重複を見つけたら、それが「同じ意図」の重複なのかを見極めたうえで集める。たまたま似ているだけの別の意図のコードを無理にひとまとめにすると、かえって変更しにくくなる。

### 第五箇条: 的確に記述されたメソッド〔1.2.5〕
- 定義: メソッド内が同じ抽象度の記述の集まりで構成されていること/メソッド内が、自然な粒度で記述されていること(話し言葉のように)/ほどよい量(記述が多過ぎない)。
- いつ: 高いレベルの手順の間に、接続の開閉や SQL の組み立てなど低いレベルの詳細が混ざったとき。メソッドが長くなったとき。
- する: 低いレベルの詳細を、意図を表す名前のメソッドに抽出する。上位のメソッドは、人間が自然に思考する粒度の手順の列にする。
- 確かめる: 上位のメソッドを読み上げると、話し言葉の手順の説明になるか。文が9つ程度に収まっているか(人が短期記憶で一度に扱える情報のまとまりは多くても9個程度であり、「大切なことを20個言います」より「3つ言います」の方が伝わる)。
- 例外・注意: 文9つの扱いは SKILL.md の判断ルール10 に従う。

```csharp
// before: 抽象度が混在している
void ProcessOrder(Order order) {
    ValidateOrder(order);
    using (var connection = new SqlConnection(connectionString)) {
        connection.Open();
        new SqlCommand("UPDATE Orders SET Status = ...", connection).ExecuteNonQuery();
    }
    SendConfirmationEmail(order);
}
// after: 同じ抽象度の手順だけが並ぶ(詳細は UpdateOrderStatus の中へ)
void ProcessOrder(Order order) {
    ValidateOrder(order);
    UpdateOrderStatus(order, OrderStatus.Processed);
    SendConfirmationEmail(order);
}
```

### 第六箇条: ルールの統一〔1.2.6〕
- 定義: 全体が同じルールに従っていること。一貫したルールは、学習コストを下げ、予測可能性(似た状況では似た解決策が期待できる)を上げ、保守性を高める。
- 統一すべき要素: 命名規則(クラス名・メソッド名・変数名)/コーディングスタイル(インデント・括弧の位置)/設計パターン(エラーハンドリング・ログ出力)/アーキテクチャパターン(レイヤー構造・依存関係)。
- する: 書く前に、既存コードの流儀を上の4要素について調べ、それに合わせる。
- 確かめる: 追加したコードを既存コードの隣に置いたとき、流儀の違い(大文字小文字の規則、エラーの返し方など)が目立たないか。
- 例外・注意: 問題にしているのは個人の局所的な好みではなく、コードベース全体の一貫性である。どの流儀を選ぶかよりも、選んだ流儀を全体で守り続けることの方が重要である。

### 第七箇条: Testable〔1.2.7〕
- 定義: 正しい記述であることが分かるようになっていること。Testable な設計が目指すのは**フィードバックの最大化**である。
- 要点: 外部への直接依存を避けて依存を渡せる構造にする/専用型でコンパイル時にフィードバックを得る/カバレッジを目標にしない(メトリクスハック)。
- する: テストしやすい構造、フィードバックの種類、テストの書き方は testing.md に従う。

## 概念を抽出して名前を付ける: 最小例〔0.6〕

条件式に埋め込まれた概念は、読み手が毎回解読しなければならない。概念を切り出して名前を付ければ、半年後の自分も、別の開発者も、AI も意図を誤読しない。

```csharp
// before: 正しく動くが、「VIP顧客とは何か」が条件式に埋もれている
if (customer.PurchaseHistory.Count > 10 &&
    customer.LastPurchase > DateTime.Now.AddMonths(-3) &&
    customer.TotalSpent > 10000) { /* VIP処理 */ }
// after: 概念を抽出し、名前を付ける
bool IsVipCustomer(Customer customer) =>
    HasFrequentPurchases(customer) &&
    IsRecentlyActive(customer)     &&
    HasHighLifetimeValue(customer);
```

- before も正しく動く。問題は動作ではなく、意図が読み取れないことである。

## 技術的負債と理解負債〔0.2、1.3〕

### 技術的負債は具体的なコードの形で存在する〔1.3.2、1.3.3〕
- 定義: 技術的負債は、短期的な解決策を選ぶことで生じる将来のコストである(後で利息付きで払わされる、設計上の借金)。抽象的なスローガンではなく、意図の読み取れない名前(`ProcessData`)や、規則を追加するたびに増殖する if-else の分岐という、**コードの具体的な形として存在する。だからこそ七箇条で返済できる。**
- 利息: 理解に時間がかかる/変更時のリスクが高い/テストが困難/バグの温床になる。
- いつ: 規則の追加のたびに分岐を足すコード、意図の読めない名前を見つけたとき。
- する: 負債を臭いとして名指しし、七箇条のどれに反しているかで返済の仕方を決める(例: 文字ごとの if-else の連鎖は、変換規則の対応表と、一文字を変換する名前付きメソッドに置き換える)。範囲外なら報告にとどめる(SKILL.md の変更範囲の節度)。
- 確かめる: 返済後、規則の追加が対応表への1行の追加で済むか。

### 負債の逆転: 理解負債〔0.2、1.3.2〕
- 定義: 理解負債とは、コードは動いているのに、「なぜこうなっているのか」「どこを直せばよいのか」を誰も説明できない状態である。
- 負債の逆転:

| | 先行しているもの | 遅れているもの | 返し方 |
|---|---|---|---|
| 従来の技術的負債 | 頭の中の正しい理解 | コードの整理 | リファクタリングで、コードを理解に追いつかせる |
| 理解負債 | 完璧に動き、テストも通るコード | そのコードがなぜそう書かれたかの理解 | 理解の方がコードに追いつけない |

- 負債の形は変わっても、正体が理解容易性・変更容易性・検証性の欠如であることは変わらない。
- 理解負債は普段は目立たない。見た目は整い、テストも通り、差分も小さく見える。だから気づかれないまま積み上がり、仕様変更・バグ修正・障害対応の場面で一気に表面化する。
- 理解負債は人間だけの問題ではない。コードベースが大きく複雑になるほど、AI 自身も全体像をつかみにくくなる。複雑さの増加を考えずに変更を重ねると、人間にも AI にも十分理解されていない、保守や拡張の難しいコードの集まりができあがる。
- **生産性の錯覚**: 結果がすぐ表示され差分がすぐ増えると、作業が進んでいるように感じる。実際には要件確認・設計の見直し・レビュー・テスト・手戻りが残っており、書く速度だけが上がってもプロジェクト全体は同じ比率では速くならない。速さは前借りできても、理解は前借りできない。
- いつ: 大量のコードを短時間で生成したとき。テストが通ったことで完了と判断しそうになったとき。
- する: 進捗を差分の量やテストの通過だけで測らない。自分の変更について「なぜこう書いたか」「次に変えるならどこを直すか」を言えない箇所を探し、言えるようになるまで構造か名前を直す。
- 確かめる: 変更の What と Why を、コードを見ずに自分の言葉で説明できるか(報告の型は collaboration.md)。
- 例外・注意: 三つの負債(技術負債・理解負債・意図負債)と、その対策の全体は quality-gates.md にある。

## 判断例: 七箇条による評価〔1.5〕

状況: 次のようなメソッドを評価する。`UserManager.DoStuff(string data)` が、null と空文字の確認、カンマでの分割と要素数の確認、コンソール出力、接続文字列を直書きしたデータベースへの保存、SMTP でのメール送信を、一つのメソッドの入れ子の中で行っている。

| 箇条 | 問題点 |
|---|---|
| 意図を表現 | `DoStuff` という名前では何をするかが分からない |
| 単一責務 | バリデーション・保存・メール送信という複数の責務が混在している |
| 的確な名前 | メソッド名・変数名が不適切である |
| Once And Only Once | 将来的に重複が発生しやすい構造である |
| 的確に記述されたメソッド | 抽象度が混在し、長すぎる |
| ルールの統一 | コーディングスタイルが統一されていない |
| Testable | データベースと SMTP に直接依存しているため、テストが困難である |

- 判断: 何をするかを表す名前(`RegisterUser`)を持つサービスにし、入力の解析を専用の型に、保存とメール送信を注入される依存に分ける。
- 理由: 各箇条の問題が、意図を表す名前・責務の分離・依存の注入という同じ方向の変更で解消する。七箇条は一体の指針なので、一つずつ別々に直すのではなく、まとめて見て判断する。
- 自己点検の根拠: 責務の混在、`object` や `data` のような曖昧な名前、外部システムへの直接依存は、制約を与えずに AI がコードを生成したときに現れやすい特徴である。AI の出力は学習データの統計的な平均に近づきやすく、制約を明示しなければ、一見動作するが構造的な懸念を抱えたコードになりやすい。自分の生成物は、まずこの三点から疑う。
- 七箇条による評価は、人間が書いたコードにも、AI が生成したコードのレビュー観点としても、そのまま使える(レビューへの適用は quality-gates.md)。

## 前提: なぜこの判断基準に従うのか

- **美しいコードとは、拡張と保守がしやすいコードのことである。** 「動く」は前提であり、比べるのは「汚くて動く」と「きれいで動く」である。プログラミングという作業は、常に現状のコードの変更である。〔1.1〕
- 開発の重心は読むことにある。エージェントが書くコードは、最初から「他人のコード」である。〔0.1〕
- **理解負債**: コードは動いているのに、「なぜこうなっているのか」「どこを直せばよいのか」を誰も説明できない状態。AI の生成速度で積み上がり、AI 自身の理解も妨げる。〔0.2〕
- 制約を与えられない AI の出力は平均的な設計に寄り、「あれもこれも」と複雑さを足し算する癖がある。AI が生成するコードは、必ずしもサステナブルではない。〔0.4、8.6〕
- 質とスピードはトレードオフではなく連動する。理解しやすいコードは変更が速く、変更が速いから検証も改善も速い。〔0.4〕

## 判断の軸〔8.1、8.2.3、8.4.2、10.5〕

```
最上位の価値: Think Simple
  読む人が扱える複雑さの限界を超えない/複雑な状況に自分を持っていかない
  ├ 動き1 境界を分けて名前を付ける … Name and Conquer・SON
  ├ 動き2 意図を What として表す …… 七箇条・説明責任・S/N比
  └ 動き3 検証できる形に置く ……… Testable・契約
```

四つの武器(美しいソースコードのための七箇条/Name and Conquer/SON/Testable な設計)は、この三つの動きを支える一つの体系である。〔0.6〕

## 用語集

| 用語 | 定義(詳細) |
|---|---|
| 七箇条 | 意図を表現/単一責務の原則/的確な名前付け/Once And Only Once/的確に記述されたメソッド/ルールの統一/Testable。相互に関連し合う一体の指針(このファイル) |
| 説明責任 | ソースコード自身が、意図と責務の範囲(何をするか・何をしないか)を読むだけで伝えること。How より What を書く(naming.md) |
| S/N比 | 意図が信号、意図以外の記述が雑音。シンプルなコードとは S/N比の高いコード(modeling.md) |
| 関心の分離 | モデリングの基本原理。関心事を切り出し、それぞれに名前を付ける(modeling.md) |
| Why→What→How | 何故作るか → 何を作るか → どう作るか の順に考える。目的が手段を駆動する(modeling.md) |
| 分かる=分けられる | 「これであるもの」と「これでないもの」の境界を言えること。分けられないものは、まだ分かっていない(modeling.md) |
| Name and Conquer | 注目すべきものを見つけて名前を付け、概念を他から切り分けて問題を支配する技法(naming.md) |
| SON | サービス指向名前付け。名前=インターフェイス=サービス。使う側の視点で名前を決める(naming.md) |
| 語彙 | 型・メソッド・変数は、プログラムを記述するための語彙。名前を知らないものは見えない(naming.md) |
| 責務と変更理由 | 「どのオブジェクトの仕事ということにするか」を決める。ひとつの変更 → ひとつの修正(object-design.md) |
