# 命名: 説明責任・Name and Conquer・SON

型・メソッド・変数・モジュールに名前を付ける、名前を見直す、命名を相談される、他人や自分のコードの名前をレビューするときに読む。

## 命名はモデリングの核心〔2.2〕

- 命名は識別子の選択ではなく、設計であり、モデリングの中心的な行為である。プログラミングという行為は**設計+実装+テスト**であり、ソースコードは人間が理解でき、機械が実行でき、検証できるモデルである。
- 人間が理解しやすいのは、人の「頭の中のモデルにもっとも近いもの」である。手順ごとに名前を付けると、同じくらいの抽象度の記述で揃う(長い一文の調理手順より、「材料を切る」「炒める」「煮る」と名前を付けた手順の方が分かる)。
- 分析モデル・設計モデル・実装モデルの間の一貫性を保つもっとも重要な手段が命名である。
- 関心事を分離したとき、その境界を支えるのは名前である(Parser・Validator・Repository・NotificationService)。名前がいい加減なら、関心事の境界はぼやける。関心の分離そのものは modeling.md を参照。

## 説明責任〔2.1〕

- 定義: ソースコード自身が説明責任を果たすように書く。「どのように処理するか(How)」より「何をしたいか(What)」を書く。意図が明確であること(何がやりたいのか)、責務の範囲が明確であること(何をするのか・何をしないのか)が、読むだけで伝わるようにする。
- いつ: コードを書くとき、名前を決めるとき、読んで「何をしたいのか」がすぐ言えないとき。
- する: 呼び出し側が What だけで読めるように、判定や計算に名前を付けて切り出す。条件式や手順を裸で並べない。
- 確かめる: 呼び出し側の数行を読んで、意図と、そのコードが何をしないかを言えるか。形そのものが使い方を伝えているか(アフォーダンス)。
- 例外・注意: 曖昧な名前が意図と責務を覆い隠す問題は、AI が生成したコードにも同じく現れる。自分の生成物も、名前が説明責任を果たしているかで点検する。

```csharp
// before: How が並び、意図が読めない
static void ChkFunc2(int y, int m, int d) {
    if (y < 1) Console.WriteLine(txt);
    else if (m < 1 || m > 12) Console.WriteLine(txt);
    else if (m == 2) { if (y % 4 == 0 && ...) ... }   // 以下、分岐が続く
}
// after: What の語彙で読める
bool IsValid => IsValidYear && IsValidMonth && IsValidDay;
bool IsValidDay => Day >= 1 && Day <= LastDayOfMonth;
int  LastDayOfMonth => Month switch { 2 => LastDayOfFebruary, 4 or 6 or 9 or 11 => 30, _ => 31 };
if (!date.IsValid) ui.ShowError("日付が正しくありません。");
```

注: `日付として正しい`・`うるう年か` のような日本語識別子で書くと意図の伝わりやすさが際立つが、実務の識別子は英語が基本である。

## 第三箇条「的確な名前付け」の基準〔1.2.3〕

- 名前が、それの(唯一の)仕事を(一言で必要十分に)表現していること
- 同じものは同じ名前で、違うものは違う名前で表現されていること
- 既知の名前を別の意味で使用しない
- 問題領域の言葉を意味を変えて使用しない

名前を付けることで、概念を確定させ、境界を明確にし、責務を限定し、意図を表現する。

## Name and Conquer〔2.3〕

- 定義: 複雑さに対処する基本戦略は、大きな問題を小さく分ける Divide and Conquer(分割攻略)と、注目すべきものを見つけて名前を付ける Name and Conquer(命名攻略)の二つである。名前を付けることは概念を確定させることであり、概念とそれ以外の境界、すなわち「それは何か/それは何でないか」を決めることである。混沌の中から秩序を作り出す行為である。
- いつ: 役割の曖昧なクラスやメソッド(`SystemManager.DoWork(object)` の類)があるとき。コードや要求の中に、まだ名前の付いていない「注目すべきもの」があるとき。
- する: 注目すべきものを見つけ、名前を付けて切り出す。付けた名前で「この範囲の概念を X と呼ぶ」と言い、X に入るものと入らないものを決める。名前が座ると、暗黙知が形式知になり、第三者(人にも AI にも)に理解できるようになる。
- 確かめる: 名前を聞いただけで、その概念に含まれるものと含まれないものを言えるか。
- 例外・注意: 切り出した概念は階層を成してよい(注文管理 → 注文処理 → 注文検証・価格計算・在庫確認 → 顧客検証・商品検証・支払い検証)。

### 抽象化レベルの3指針〔2.3.3〕

抽象化レベルが高すぎると概念が曖昧になり(`DataProcessor.Process(object)`)、低すぎると実装の詳細に縛られる(`SqlServerCustomerTableSelector.SelectFromCustomerTable(sql)`)。適切な例は `CustomerRepository.FindById` / `Save`。

| 指針 | 判断 |
|---|---|
| ドメイン概念 | ビジネス領域の自然な概念に対応しているか |
| 操作の意図 | 技術的な手段ではなく、何をしたいかを表しているか |
| 実装非依存 | 特定の技術や実装方法に依存していないか |

### 名前による責務の限定〔2.3.4〕

- 定義: 適切な名前は、そのコンポーネントが何をするかと同時に、何をしないかを明確にする。名前が付くことで責務の範囲が限定され、高凝集(一つのまとまりの中身が同じ目的のために揃っている状態)になる。
- いつ: 既存のクラスにメソッドやフィールドを足すとき。
- する: 足そうとしているものが名前の範囲に入るかを判定し、入らないなら別の名前の単位に置く(`PriceCalculator` に `SaveOrder` や `SendEmail` を入れない)。
- 確かめる: クラス名の範囲外の仕事が混ざっていないか。

### 問題と解を同じ語彙で貫く〔2.3.6、2.7.2〕

- 定義: Name and Conquer は名前を付けて終わる技法ではない。切り出した語彙で問題を記述し、その同じ語彙のまま解を作るところまでが一続きである。工程が変わるたびに語彙を訳し直すと、訳すたびに意味がずれる。
- いつ: 要求からクラスやメソッドを起こすとき。
- する: 要求の文に登場する語(顧客、ショッピングカート、注文、在庫、出荷)をそのままコードの語彙にし、自然な動詞で表す(`cart.AddItem`、`checkout.Pay`、`inventory.Reserve`)。ユーザーの説明や既存コードで使われているドメイン用語を優先し、自分で別の言葉に言い換えない。
- 確かめる: 要求の語と、コードの型名・メソッド名が対応しているか。翻訳を挟まないと説明できない名前がないか。

## 語彙を整える〔2.4、0.5〕

- 定義: **サブルーチンは「似たような処理をまとめる」為じゃなく「名前を付ける」為にある。** 型・メソッド・変数は、プログラムを記述するための語彙である。設計で重要な行為は、この語彙を作る作業である。
- いつ: メソッドを切り出すか迷うとき。一つのメソッドに粒度の違う記述が混ざっているとき。引数が同じ組で何度も現れるとき。
- する:
  - 「どんな語彙で記述したいか」を基準に切り出す。`if (name.Length > 0)` をわざわざ `if (IsValid(name))` と書くのは、そのロジックをその抽象度で書きたいときである。
  - 抽象度は、人がそれを自然言語で「もっとも簡潔に」記述するときの粒度にする(「最寄りの空港に行く」は、鍵を閉める・信号を待つではなく、外に出る・最寄り駅まで歩く・空港駅行の電車に乗る・空港まで歩く、で書く)。
  - 一緒に現れる値の塊に型名を付け、その型に責務を持たせる(x, y の組 → `Vector2D`。距離を `Vector2D` の責務にし、3点 → `Triangle`、周の長さ → `Triangle.Perimeter`)。
- 確かめる: メソッド本体が同じ抽象度の語彙で揃い、「何をしているか」を素早く読み取れるか。
- 例外・注意: メソッド抽出の手順と注意点は refactoring.md を参照。

**ジョシュアツリー効果**: 名前を知った途端に、それまで見えていなかったものが認識できるようになる。名前を知らないものは見えないし、言語化できないものは伝えられない。コードの問題を見つけ、ユーザーに説明するときは、原則・臭い・技法の名前を使う。その語彙を持つこと自体が、問題を見抜く力になる。

## サービス指向名前付け(SON)〔2.5〕

- 定義: 名前=インターフェイス=サービス。利用する側のモジュールがクライアント、利用される側がサービス提供側であり、プログラム中の名前は、サービス提供側がクライアントに提供するインターフェイスであり、サービスの名称である。重要なのは「提供者がどう実装するか」ではなく「利用者がどう使いたいか」である。目的(顧客の問題解決)が手段(開発)を駆動する。
- いつ: 新しいクラス・メソッド・API を作るとき。名前に実装の都合が出ているとき。
- する:
  1. 呼び出し側のコードを先に書く。そこで自然に読める名前を、サービス側の名前にする。
  2. 実装の詳細(SQL、DB 製品、データ構造)を名前に出さない。クライアントがビジネス概念で操作できるようにする。
  3. 各メソッドを、クライアントが欲しいサービスとして名付ける(`EmailService.NotifyCustomer`、`AlertAdministrator`。SMTP やテンプレートは隠す)。
  4. ドメインの自然な語彙を使う(銀行なら `Deposit` / `Withdraw` / `Transfer`、EC なら `AddItem` / `Checkout`)。
- 確かめる: クライアントのコードが実装の詳細(SQL 文字列など)を書かずに済んでいるか。

```csharp
// before: 実装者視点。クライアントが SQL を書き、DB の詳細が露出する
var table = dao.ExecuteSqlQuery("SELECT * FROM Customers WHERE Id = " + customerId);
// after: クライアント視点。ビジネス概念で操作でき、実装は隠れる
var customer = repository.FindById(customerId);
```

サービス境界と契約の観点は object-design.md、ユーザーの依頼を利用者視点の語彙に言い直す手順は collaboration.md を参照。

## 命名アンチパターンの検出表〔2.6〕

名前の臭いとして、自分の生成物のセルフレビューにも使う。AI の生成コードにも現れやすい。

| アンチパターン | 検出の目印 | 問題 | 対策 |
|---|---|---|---|
| 数字を付ける | `CustomerService1/2`、`list1`、`dict1` | 違いが分からない。責務の境界が不明確で、どちらを使うべきか判断できない | 違いを名前にする(`CustomerRegistrationService` / `CustomerNotificationService`) |
| 省略する | `CustMgr`、`ProcOrd`、`custs`、`calcTot` | 読みにくく、推測が必要。解釈が分かれる | 完全な単語で書く(`ProcessOrder`、`customers`) |
| 意味不明な名前 | `Thing`、`Data`、`DoStuff`、`Items`、`object` だらけ。`tmpWork`・`flg`・`i2`(中身や何のフラグかを表さない)〔2.2.1〕 | 何をするか分からず、責務が特定できない。保守が困難 | 責務を表す名前と具体的な型にする(`OrderValidationResult`、`List<ValidationError>`) |
| 型名を含める | `CustomerList`、`OrderDictionary`、`ProductInterface`、`OrderClass` | 実装の詳細が名前に漏れる。実装変更で名前も変わる。抽象化レベルが不適切 | 概念(`Customers`)や振る舞い(`IOrderLookup`)を表す |
| 統一感がない | `Get`/`Retrieve`/`Fetch`、`Save`/`Store`/`Persist` の混在 | 学習コストが高く、予測できない。混乱が生じる | 同じ操作には同じ動詞を使う(Find/Save に揃える)。統一は同じ意味の動詞の混在(Get/Retrieve/Fetch)を禁じるもので、Find(見つからない可能性がある)と Get(必ず返す)の意味の区別とは両立する |
| 直訳で付ける | 和英辞典の訳語をそのまま使う(「大きさ」→ 常に `size`) | 日本語と英語では言葉の範囲がほとんど異なり、表したいことが訳語の範囲から外れる | ニュアンスまで考え、表したいことを意味の範囲に含む語を選ぶ |

## 名前の段階的改善〔2.7.1〕

1. **現状分析**: 名前を一つずつ読み、何を表しているかを言う。
2. **問題点の特定**: 上の検出表と次の観点で分類する。意味不明(`DataProcessor`、`DoWork`)/一般的すぎる(`Process`、`Save`、`Send`)/型情報の不足(すべて `object`)/番号付け(`list1`)/責務が不明確(何のデータを処理するのか)。
3. **段階1 意味のある名前に**: 具体的な名前と型にする(`OrderProcessor`、`List<Order> pendingOrders`、`ProcessOrder(Order)`、`ValidateOrder`、`SendConfirmation`)。
4. **段階2 責務を分離**: 名前を付けて見えてきた責務を、別の名前の単位に分ける(`IOrderValidator`、`IOrderRepository`、`ICustomerNotificationService`。全体は `OrderProcessingWorkflow.ProcessNewOrder`)。

既存コードの名前を直すときは、振る舞いを変えない変更として、段階ごとにテストを実行する。シグネチャや戻り値が変わる段階(引数の型を具体化する、結果の型を返すなど)は機能変更として手順を分け、報告でも分けて示す。

命名の相談で、一つの名前では責務を言い表せない(責務が混在している)と分かったときは、名前の案と合わせて段階2の分割を提案する。分割の実施は、依頼されたときだけにする。

**指摘・報告の書式**: 「もっと良い名前に」とは書かない。「どの名前が、どの観点(責務・抽象度・型)で不適切か」を、改善案と対にして示す。

```text
1. DataProcessor → 具体的なドメイン責務を表す(例: OrderProcessor)[責務]
2. Process       → 具体的な処理内容を表す(例: ProcessOrder)[抽象度]
3. List<object>  → 型安全な具体型を使う(例: List<Order>)[型]
4. DoWork        → 具体的な動作を表す(例: ValidateOrder)[責務]
```

## 命名パターン〔2.7.3、2.7.5〕

### 自然な英語表現

- **標準ライブラリとの一貫性で判断する**: 述語的なメソッドは、その言語の標準ライブラリに合わせる。.NET なら `Rectangle.IntersectsWith` に合わせて `IntersectsWith`・`CollidesWith`・`ConnectsTo` とする。`Intersect` や `Connect` は他動詞としても使える語で、文法的に誤りではない。判断基準は文法の正誤ではなく、標準ライブラリの命名規約との一貫性である。
- **SVO(他動詞+目的語)の語順にする**: `ProcessOrder`、`ValidateInput`、`CreateOrder`。日本語の「名詞+動詞」の語順を写さない(`OrderProcess`、`InputValidate` は ×)。
- **三人称単数の s を付ける**: `ContainsPoint`、`IntersectsWith`(`ContainPoint` は ×)。
- **メタファ**: Factory・Observer・Strategy・Pipeline・Cache のようなメタファは理解を助けるが、ドメイン上の意味を損なわないようにする。パターン名を付けるのは、そのパターンの意図と実装が一致している場合に限る。

### 変数・フィールド名

| パターン | 良い例 | 悪い例 | 理由 |
|---|---|---|---|
| 意図を表現 | `customerCount` | `count` | 何を数えるかが明確 |
| 型情報を避ける | `customers` | `customerList` | 実装詳細ではなく概念を表す |
| 略語を避ける | `calculatedTotal` | `calcTot` | 完全な単語で意図を明確に |
| 否定形を避ける | `isValid` | `isNotInvalid` | 肯定的な表現が理解しやすい |
| 文脈を活用 | `name`(Customer 内) | `customerName`(Customer 内) | クラス内では冗長な修飾は不要 |

### メソッド名

| パターン | 良い例 | 悪い例 | 理由 |
|---|---|---|---|
| 動作を表現 | `CalculateTotal()` | `GetTotal()` | 計算を行うことが明確 |
| 副作用を明示 | `UpdateAndSave()` | `Update()` | 複数の動作があることを隠さない |
| 戻り値を示唆 | `FindCustomer()` | `GetCustomer()` | 見つからない(null の)可能性を示唆 |
| 質問形を活用 | `IsEmpty()` | `CheckEmpty()` | Boolean の戻り値を自然に表す |
| 一貫した動詞 | `Create/Update/Delete` | `Create/Modify/Remove` | 操作の一貫性を保つ |

`UpdateAndSave()` は、複数の動作を名前で隠さず示す例であり、単一責務の原則を免除するものではない。まず `Update()` と `Save()` に分けられないかを検討し、それでも一つにまとめる理由があるときに限り、名前で正直に示す。

### クラス名

| パターン | 良い例 | 悪い例 | 理由 |
|---|---|---|---|
| 責務を表現 | `CustomerValidator` | `CustomerManager` | 具体的な責務が明確。Manager は責務が曖昧になりやすい |
| 役割を示す接尾辞 | `OrderRepository` | `OrderData` | データアクセスの役割を示す |
| ドメイン用語 | `ShoppingCart` | `ItemContainer` | ビジネスドメインの用語を使う |
| 実装詳細を避ける | `CustomerRepository` | `CustomerDatabase` | 実装手法ではなく役割を表す |

- 役割の接尾辞は語彙を揃える: 表示層 `~Controller`/`~ViewModel`、業務層 `~Service`/`~Engine`、データ層 `~Repository`/`~DataAccess`、生成 `~Builder`/`~Factory`/`~Generator`、変換・処理 `~Processor`/`~Transformer`/`~Handler`、検証・判定 `~Validator`/`~Checker`、結果・設定 `~Result`/`~Configuration`/`~Settings`。既存コードに接尾辞の流儀があればそれを優先する〔2.7.5〕。

## 命名の一貫性チェックリスト〔2.7.4〕

自分のコードのセルフレビューと、他人のコードのレビューの両方に使う。

- **意図の表現**: 名前を見ただけで何をするか分かるか/Why・What が表れているか/How の詳細は隠れているか
- **責務の明確性**: 単一の明確な責務を表しているか/その境界が明確か/責務外のものが含まれていないか
- **ドメイン適合性**: ドメインの専門家が使う用語と一致しているか/ビジネス概念を適切に表しているか/技術的詳細ではなくビジネス上の価値を表しているか
- **一貫性**: 同じ概念に同じ名前、異なる概念に異なる名前を使っているか/プロジェクト全体で命名ルールが統一されているか
- **発見可能性**: 他の開発者が容易に見つけられるか/推測できる名前か/略語や暗号的な表現を避けているか

## 最小の命名規約テンプレ〔2.7.4〕

リポジトリに命名規約がなく、新しく決める必要があるときは、まず次を既存コードの流儀から読み取る(読み取れないものだけユーザーに提案する)。規約は「判断基準がある/機械で強制できる(フォーマッター・リンター)/例外が少ない」形にする。

| 項目 | 決めること |
|---|---|
| Case | `PascalCase` / `camelCase` / `snake_case` の範囲。まずその言語の標準の規約に従う(例: C# はクラス・メソッド・定数が PascalCase で変数が camelCase、Java/JavaScript はメソッド・変数が camelCase、Python はメソッド・変数が snake_case、Java/JavaScript/Python の定数は UPPER_SNAKE)〔2.7.5〕 |
| Boolean | `is` / `has` / `can` などの接頭辞のルール |
| Collection | 複数形・単数形のルール |
| 単位・制約 | `ms` / `count` / `id` などを名前に含める基準 |
| 非同期・副作用 | `Async` や動詞の選び方で、呼び出し側の期待を裏切らない |

## 命名は継続的に改善する〔2.8〕

- 命名は一度決めて終わりではない。理解が深まるにつれて改善する。
- 実装の途中で、名前と実際の仕事がずれたと気づいたら、その時点で名前を直す(名前の変更の進め方は refactoring.md)。見直しで足りない名前が見つかるのは、モデルが深まったしるしである(modeling.md)。
- 曖昧な名前は、読み手に広すぎる解釈を許し、意図と境界のずれを見えにくくする。良い名前は、人にも AI にも意図と責務の境界を伝える共通の文脈であり、理解負債を増やさないための防波堤である。
