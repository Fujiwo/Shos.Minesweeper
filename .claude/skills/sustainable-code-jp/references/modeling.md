# モデリング: 意図とノイズ・分け方・ドメインとの対応

着手前に要求を捉えるとき、クラスや関数の分け方を決めるとき、ドメインの概念をコードに写すとき、コードの良し悪しを評価するときに読む。

## モデル=関心の外を取り去ってシンプルにしたもの〔3.1.1〕

- 定義: モデルとは、目的があって、その目的に沿った部分だけを抽出し、関心の外のものを取り去ってシンプルにしたものである(地図は道路・駅・目印だけを描く)。つぶさに伝えることと、適格に伝えることは違う。
- いつ: クラスの属性や引数、処理の項目を決めるとき。
- する: システムの目的とユーザーの視点から要らない属性は持たせない(社員名簿の社員クラスに「好きな食べ物」を持たせない)。
- 確かめる: 各属性・各項目について「この目的に要るか」を答えられるか。
- 例外・注意: 「社員クラスを作る」ような依頼で、エージェントは現実のもっともらしい属性(生年月日・住所・電話番号・緊急連絡先…)を一式並べやすい。要るか要らないかは、システムの目的を知る側にしか決められない。生成後に自分の出力を目的と照合し、根拠のない属性を削る。目的が分からず判断できないときは、仮定を明示するか確認する。

## 意図とノイズ〔3.1.3〕

- 定義: ソースコードが表現すべきものは意図である。意図以外の記述はモデルにとってのノイズである。**良し悪しはコードそれ自体には宿らない。意図とコードがいかに呼応しているかに宿る。** だから、コードを評価するときは先に意図を問う。
- いつ: コードを書く前、レビューやセルフレビューを始める前。
- する: まず「このコードの意図は何か」を端的に言う。次にコードと照らし、意図に含まれない記述がどれだけあるかを見る。
- 確かめる: 意図を一言で言えるか(「注文を確定する」と言えればモデルがある。「まず DB から読んでループを回して…」と手順しか出ないなら、モデルがないか、モデル通りに書かれていない)。意図が言えないなら、レビュー以前にモデルがない。
- 例外・注意: 名前も同じである。名前は意図をそのまま写すものであり、意図から離れた名前はノイズになる(命名は naming.md)。

```csharp
// 意図:「従業員リスト内のすべての従業員を画面に出力する」
for (int index = 0; index < employees.Count; index++)   // int, index, <, Count, ++, [index] は
    Output(employees[index]);                           // 意図の中にない = ノイズ
employees.ForEach(employee => employee.Output());      // ノイズが少ない
```

ただし、意図が「整数 index を 0 にし、Count 未満の間インクリメントしながら index 番目を出力する」なら、for の方がよい。`l.ForEach(x => x.Func(s))` も、意図が「l 内のすべての x を s で Func する」ならそれがよい。

## S/N比と宣言的記述〔3.1.4〕

- 定義: 意図とノイズの比を S/N比と呼ぶ。意図が信号、意図以外が雑音である。宣言型は「どうやるか」を書かないのでノイズが少ない。書き手が意図しか書かないので、読み手も意図しか読まなくてよい。
- いつ: ループ・一時変数・インデックス操作など、手続きの記述が意図の周りを埋めているとき。
- する: 意図が結果の宣言なら、宣言的に書いて手順を隠す(「10回、何かする」なら `10.Times(DoSomething)` のように書ける形を検討する)。言語や既存ライブラリにある宣言的な手段の範囲で行い、そのためだけの拡張メソッドやヘルパーは、既存の流儀にある場合を除いて新設しない。
- 確かめる: 残った記述の一つ一つが意図の中の語に対応するか。
- 例外・注意: 宣言型が常に優れているわけではない。意図がたまたま宣言だったから宣言的な記述が合っただけであり、手順そのものが意図なら命令型の方が意図に忠実である。大事なのは、意図の性質と記述の形式が一致していることである。使い分けの判断は paradigms.md を参照。

### ピュアなモデルの二条件〔3.1.4〕

- 定義: モデルがピュアであるとは、(1) 意図以外のものが書かれていないこと、(2) 意図が書き尽くされていること、の二つを満たすことである。ノイズの排除だけを追うと (1) しか見えなくなる。
- いつ: ノイズを削ったあと、汎用のつもりの処理を書いたあと。
- する: 意図の一部が固定値や特定の型に置き換わっていないかを見る。「或るコレクションを或る条件で絞り込む」が意図なのに、要素型が `int`、条件が「5の倍数」に固定されていれば、意図通りではない。型と条件を受け取り、絞り込みだけを行う形にする。
- 確かめる: 意図の文の各要素(「或るコレクション」「或る条件」「絞り込む」)が、すべてコードに現れているか。
- 例外・注意: 意図したモデルをその言語で書き尽くせるならコメントは要らない。書き尽くせない分は必要悪として書く。What と How は言語で書きやすいが、Why は書き切れないことが多い(コメントの扱いは refactoring.md)。「或る条件で」を足すのは意図に含まれるからであり、意図にない汎用化を足してよいという意味ではない(simplicity.md)。

## 分け方〔3.2.1〕

- 定義: 複雑さを解消する基本は分けることである。10000行のプログラムより、100行×100の方がシンプルだ。但し、分け方が悪ければ 100 個の部品が絡み合い、元の 10000 行より複雑になる。どう分けるともっともシンプルかが腕の見せ所である。
- いつ: 関数・クラス・モジュール・レイヤの境界を決めるとき。一つのメソッドに業務ルールの判断・文字列の分割・データベースへの保存のような、異なる抽象度・粒度の関心事が混ざっているとき。
- する: 分けたそれぞれが単一の問題を扱い、一つの問題を複数の部品に分散させず、境界がくっきりするように分ける。境界はインターフェイスでくっきりさせる(結果が低結合・高凝集)。分ける単位(関数・クラス・アスペクト・レイヤ・MVC・コンポーネント・固定部と可変部)は、分離したい関心の種類で選ぶ。
- 確かめる: 分け方を次の3観点で比べる。**分かりやすさ/変更が起こったときの複雑さ/テストしやすさ**。
- 例外・注意: 手続き型は処理単位でしか分けられない。一つのパラダイムだけでは様々な分離に対応しにくい(paradigms.md)。

### 分かる=分けられる〔3.2.1〕

- 定義: 「分かる」とは「分けられる」ということである。「これとこれは違う問題だ」と言えること、「これであるものと、ないものの境界」を知ること。分けられないものは、まだ分かっていない。
- いつ: 設計に行き詰まったとき。分け方が見つからないとき。
- する: 分け方が見つからないのは対象をまだ理解していないからかもしれない、と疑い、実装を進める前に対象の理解(要求・ドメイン・既存コード)に戻る。
- 確かめる: 対象を構成する問題を列挙し、それぞれの境界を言えるか。タスク理解の自己検証への使い方は collaboration.md を参照。

## 視点とモデル〔3.2.2〕

- 定義: 同じ対象でも、視点が変わればモデルは変わる(パラダイムの違い、高さの違い、角度の違い、問題を見る AsIs と解を見る ToBe)。ただし分析・設計・実装は別々のモデルではない。**モデルはひとつ、視点が違うだけ**である。
- いつ: 分析の語彙から設計・実装へ進むとき。一つのループに数え上げ・判定・出力が同居しているとき。
- する: 視点を変えて関心の分かれ方を比べる(一つのループ → 列挙・加工・出力を独立した部品にし、それぞれに名前を付ける)。分析で使った語彙を設計・実装にも残す。
- 確かめる: 分析モデルの名前が、設計モデルにもコードにも残っているか。
- 例外・注意: 美しいソースコードは一意ではない。しかし基準はある。分かりやすさとは、読み手が理解しているモデルと乖離していないことである。

### 独立したものは独立したまま表す〔3.2.2〕

- 定義: 疎結合=独立した事象を独立したまま表すこと。ベクトルの x 成分と y 成分は数学的に独立だから、プログラムでも疎結合であるのが自然だ。これは「プログラムのテクニックとして」疎結合にするのではない。本来独立しているものを結合させると、人の頭の中のモデルから離れて分かりにくくなる、というだけである。
- いつ: 結合を切るか迷うとき、逆に「疎結合のため」に仕組みを足そうとしているとき。
- する: 結合の有無を、対象そのものが独立しているかで決める。
- 確かめる: その結合(または分離)は、読み手のモデルと一致しているか。依存の向きの判断は object-design.md を参照。

## ドメインをコードに写す〔3.3.1〕

### BCE と変更頻度

| 役割 | 内容 | 変更頻度 |
|---|---|---|
| Boundary | システムの境界。画面や外部システムとの接点 | 多い |
| Control | 制御に関わるビジネスロジック | 中間 |
| Entity | システムの実体(永続データ)と、それに関連する振る舞い。環境とは独立した振る舞いを持つ | 少ない |

- 定義: 変更頻度の違うものを分けておけば、変更を局所化できる(画面のレイアウトは頻繁に変わるが、「残高より多くは出金できない」という業務ルールは滅多に変わらない)。
- する: Entity には、画面も DB も知らない、それ自身の振る舞いだけを持たせる(預金口座は残高を正しく増減させることだけを知る)。表示の関心とデータの関心を同じクラスに置かない。
- 確かめる: Boundary のクラスが Entity のコレクションや業務ルールを抱え込んでいないか。

### IOP(Inside-Out Principle)

- 定義: 中から外へ向かって設計せよ。モデル(Entity と Control)を先に設計し、ユーザーインターフェイスは後で設計する。画面から作り始めると、画面の都合がモデルに染み込む。
- する: 新機能は、ドメインの型と振る舞いから書き始め、UI・入出力は最後に接続する。

### 実世界をそのまま写さない

- 定義: 「実世界をそのままオブジェクトにマッピングする」を文字どおりに受け取ると失敗する。実世界をそのまま写すのではなく、システムの目的に沿って IT の概念へ抽象化する。
- いつ: 業務の説明や既存の手作業の流れから、クラスを起こすとき。
- する: 紙の実務(顧客台帳・銀行員・電卓・金銭出納帳)を写さず、システムの関心(口座の残高を正しく管理する)から見て要る概念(顧客・預金口座・取引履歴)だけを残す。銀行員も電卓も関心の外であり、電卓の計算はコンピュータにとってただの足し算である。
- 確かめる: 各クラスが、システムの目的に照らして要る概念か。

**レイヤ分割**: BCE が縦の分割なら、レイヤ分割は抽象化のレベルによる横の分割である(アプリケーション層/フレームワーク層/基盤ライブラリ層)。抽象化のレベルで分けると再利用性が変わる。

## 良いモデルの条件〔3.3.2〕

| 条件 | 判断 |
|---|---|
| Once And Only Once | 重複しないこと。一つの理由による変更が、一箇所の修正で済むこと |
| シンプル | 複雑さの度合いが人の理解できる範囲を越えないこと。自然に表現されたモデルであること |
| Ease To Understand | 分かりやすいこと。名前が的確であること |
| Ease To Change | 変更しやすく、拡張しやすいこと |
| Ease To Test | 検証しやすいこと。検証しやすいように分離されていること |

- 良いモデルとは保守性の高いモデルである。機能・使いやすさ・パフォーマンスはこの場面では関心の外で、別の視点のモデルで扱う。
- 「自然に表現されたモデル」かは、図に描いて確かめる。図とコードが同等のモデルになっているか。図に描いて説明しづらいモデルは、コードでも説明しづらい。厳密な図は要らず、スケッチで足りる。どの図を描くかを選ぶこと自体が「今、何の話をしたいのか」を決める関心の分離である。
- 「このクラスの仕事を、ひとことで言うと何か」で検査する(詳細は object-design.md)。

## Why→What→How〔3.4.1〕

- 定義: 何故作るか(Why)→ 何を作るか(What)→ どう作るか(How)の順で考える。目的が手段を駆動する。「何を作るか決めずに、とにかく適当に名前を付けて作っちゃえ」はその逆である。
- いつ: 機能を作り始めるとき、メソッドを一つ書くとき。
- する:
  - 「まずループを回して…」と How から考え始めない。求めるものを What で言い(平均は、合計を個数で割ったもの)、その What をさらに What で分解する(合計は、すべてを足したもの)。分解の中でサブルーチンが自然に現れる(コード例は refactoring.md の Average/Sum)。
  - 「つまり、結局、ここでは何をやればいいのか」と考える。What で分解すると、ネストしたループは自然に作らなくなる。
  - How の生成が速く安いからこそ、書く前に What を決め、その What が Why に照らして正しいかを一段上に戻って問う。別の手段の方が目的に合うことは珍しくない。
- 確かめる: 書いたコードの各メソッドが、What の分解の一段に対応しているか。この機能が何のために要るかを言えるか。要求どおりかは結合テストで、設計どおりかは単体テストで確かめる。
- 例外・注意: 機能レベルの What と Why は、ユーザーの問題定義に属する。エージェントは言い直して示し、勝手に確定しない(collaboration.md)。メソッド内部の What の分解(平均 → 合計 ÷ 個数)は、エージェントが自分で行う。

## 判断例: モデルの見直し〔3.4.2〕

要求「2点をマウスでクリックすると、1本の線分が追加できる」。

- **状況**: 素直に読むと「メインウィンドウが線分のコレクションを持つ」。これで動く。
- **判断**: 動いても立ち止まり「本当にこうなの?」と問う。ユーザーが描いているのはウィンドウの中身ではなく図面であり、ウィンドウはそれを描画するものにすぎない。線分は図面上の図形の一種である。→「図面」を切り出し、図面が線分を持ち、ウィンドウは図面を描画する形にする。
- **理由**: 当初のモデルは、Boundary(ウィンドウ)に Entity(線分の集まり)を抱え込ませていた。表示の関心とデータの関心を分けた。
- **名前**: 見直しは名前を増やすことで進む。図面・図形という名前が増えたことは、概念が切り出されたことである。見直しとは、多くの場合、足りなかった名前を見つけることである。
- **作らないもの**: 「図形」の抽象は、その時点で線分しかなければ設計には入れない。図形の種類が増えたときに導入する(simplicity.md)。
- **結果**: 分析の語彙(図面・図形・線分・描画する)がそのままコードの語彙になり、`drawing.Draw` は「持っている線分(図形の種類が増えた後は図形)をすべて描画する」という意図をほぼそのまま書いた一行になる。

持ち帰る点: 最初の分析モデルは仮説であり、動くからといって正しいとは限らない。見直しは名前を増やすことで進む。分析から実装まで語彙を貫く。
