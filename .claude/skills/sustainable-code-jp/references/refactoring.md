# リファクタリング(臭い・技法・カイゼン)

既存コードの構造を直すとき、コードをレビュー/セルフレビューして改善点を挙げるとき、機能追加の前に置き場所を整えるときに読む。障害の大きさ、カイゼン、臭いと技法の名前で語ることの詳細はここにある。

## 進め方の要約

1. 安全網を確かめる。テストがないときは、テスト基盤があるかどうかで分ける(SKILL.md の「変更範囲の節度」、testing.md)。
   - 基盤はあるが、対象コードにテストがない(テストプロジェクト・テストフレームワークの依存・既存テストのいずれかがある): 現状の振る舞いを押さえるテストを先に足してから進む(testing.md の「既存コードにテストを後から足す」)。
   - 基盤そのものがない: フレームワークを導入するかをユーザーに確認する(testing.md の「テスト基盤がない場合」)。確認が取れるまでは、IDE や言語ツールの自動リファクタリング(名前の変更、メソッド抽出など)で行える小さな一手だけにとどめ、構造を大きく作り変えない。自動リファクタリングを使えない環境では、手作業で構造を変えず、臭いと技法を報告するだけにする。
2. 臭いを名指しする。やみくもにコードをいじり回すことはリファクタリングではない。
3. 臭いに対応する技法を一つ選び、一手だけ適用する。
4. 関連するテストを実行し、Green を確かめる。Red なら直前の一手を戻す。完了報告の前に全テストを実行する。
5. 何を変えたかを、臭いと技法の名前で記録する。範囲外の臭いは報告だけにする。

## リファクタリングとは〔7.1〕

### 振る舞いを保ち、設計を繰り返す〔7.1.1〕
- 定義: 外部からみたときの振る舞いを保ちつつ、理解や修正が簡単になるように、ソフトウェアの内部構造を改善すること。設計の繰り返しである。
- いつ: 臭いに気づいたとき。依頼された変更を入れる前に置き場所が整っていないとき。
- する: 入力と出力の関係(利用者との契約)は一切変えず、内部の構造だけを変える。Green の状態から数分で戻れる範囲の一手を刻み、常にビルド・起動できる状態を保つ。
- 確かめる: 一手ごとに関連するテストが、完了報告の前に全テストが Green か。契約(公開された振る舞い)に変化がないか。
- 例外・注意: 定義の二語を落とさない。「振る舞いを保つ」: リファクタリングは機能追加でもバグ修正でもない。混ぜると、振る舞いが変わった原因を切り分けられない。「設計の繰り返し」: 設計は最初に一度だけ行って終わる工程ではない。コードに手を入れることは設計に手を入れることである。

### 安全網の二重構造〔7.1.1〕
- 定義: 安全網とは、テストによる検証と、バージョン管理による後戻り可能性との二重の構造である。テストは「振る舞いが壊れていないか」を検証し、壊れたと分かった後に直前の状態へ戻る手段はバージョン管理が提供する。
- いつ: リファクタリングに着手するとき。一手が大きくなりそうなとき。
- する:
  - 検証: 一手ごとに関連するテストを、完了報告の前に全テストを実行する。
  - 後戻り: コミット・ブランチの可否は SKILL.md の「変更範囲の節度」に従う。許可があれば Green の地点でこまめにコミットし、規模の大きいリファクタリングは専用のブランチで行う(うまくいかなければブランチごと破棄できる)。
- 確かめる: 次の一手で行き詰まっても直前の Green へ確実に戻れるか。安全網なしのリファクタリングは綱渡りにすぎない。

### 障害の大きさ=エラー×滞在時間〔7.1.2〕
- 定義: **障害の大きさ = エラー × エラーの滞在時間**。損害は、エラーの重大さだけでなく、エラーがコードに存在し続けた時間に比例して膨らむ。人は必ず間違う。だから勝負は「間違わないこと」ではなく、「いかに間違っている時間を短くできるか」で決まる。設計の劣化も同じである。
- いつ: 臭いや不具合に気づいたとき。「動いているうちは触らず、後でまとめて直す」と考えたとき。
- する: 臭いに気づいたその時が、最も安く直せる時である。依頼の範囲内なら、その場で一手直す。範囲外なら、その場で臭いの名前で報告する(報告が、滞在時間を縮める最も安い一手になる)。
- 確かめる: ずれを検知するまでの時間を最小化できているか(型エラー → テスト → レビューの順に、速いフィードバックで捕まえているか。testing.md)。
- 例外・注意: 手が付けられない状況への対処は、陥ってから頑張ることではなく、**そもそもそんな状況に自分を追い込まない**ことである。そもそも複雑にしない、常にレビューする(ユーザーに途中の成果を見せて方向を確かめることを含む)、常にテストする、そしてリファクタリングする、を開発の初期から小刻みに繰り返す(複雑にしない発想は simplicity.md)。

## コードの臭い〔7.2〕

### 臭いに名前があること自体の価値〔7.2.1〕
- 定義: コードの臭いの一覧は、コードの劣化を見えるようにする**語彙**である。個々の項目の暗記ではなく、名前が付いていること自体に価値がある。「なんとなく読みにくい」が「これは長すぎるメソッドだ」と名指しできれば、共有でき、対処法を選べる(語彙の価値は naming.md)。
- する: 改善点を挙げるときは、まず下表の名前で臭いを特定し、それから技法を選ぶ。表の名前に当てはまらない違和感は、症状を具体的に書く。

| 臭い | 一言でいうと |
|---|---|
| 重複したコード | 同じ処理が複数箇所に書かれている |
| 長すぎるメソッド | 一つのメソッドに複数の関心事が詰め込まれている |
| コメント | コードが語れていないことを、コメントで取り繕っている |
| スイッチ文 | 種類ごとの分岐が複数箇所に増殖している |
| 巨大なクラス | 一つのクラスに責務が詰め込まれすぎている |
| 属性、操作の横恋慕 | 自分のクラスより他のクラスのデータにばかり関心を持つ |
| 多すぎる引数 | 引数の数が多く、呼び出し側の見通しが悪い |
| 変更の発散 | 一つのクラスが、複数の異なる理由でたびたび変更される |
| 変更の分散 | 一つの変更が、複数のクラスにまたがる修正を要求する |
| データの群れ | 常に一緒に登場するデータの塊が、まとまった概念になっていない |
| 基本データ型への執着 | 概念を表すべき場面で、int や string などの基本型を使い続けている(専用型は testing.md) |
| パラレル継承 | ある階層に派生を増やすたびに、別の階層にも同じ派生が要る |
| 怠け者クラス | 存在意義が薄く、ほとんど仕事をしていないクラス |
| 疑わしき一般化 | 使われる見込みのない汎用化・抽象化が先回りで作られている |
| 一時的属性 | 特定の状況でしか使われない属性を、常にオブジェクトが持っている |
| メッセージの連鎖 | `a.b.c.d` のようにオブジェクトをたどって依頼を送っている(デメテルの法則は object-design.md) |
| 仲介人 | 委譲するだけで、自身はほとんど何もしていないクラス |
| 不適切な関係 | 互いの内部にまで踏み込んで依存し合っているクラス同士 |
| クラスのインタフェース不一致 | 似た処理をする複数のクラスで、メソッド名やシグネチャが揃っていない |
| 未熟なクラスライブラリ | 利用中のライブラリの都合に、自分のコードが振り回されている |
| データクラス | データを持つだけで、振る舞い(責務)を持たないクラス |
| 相続拒否 | 継承した機能の一部しか使わず、残りを拒否・無視している派生クラス |

### 重複は偶然ではない/症状の裏の設計を疑う〔7.2.2〕
- 定義: ソースコードが重複するのは偶然ではない。重複とは、**同じ責務を複数の部分が持っている可能性**を示すサインである。臭いは表面に現れた症状であり、改善の対象はその奥にある構造である。
- いつ: 重複に限らず、臭いを見つけたとき。
- する: 表面を消す前に「この症状の背後にある関心事は何か。それはどこが担うべき責務か」と問う。例: 重複 → 一つの関心事が複数箇所にまたがっている。長すぎるメソッド → 複数の責務が同居している。多すぎる引数 → まとまるべきデータの群れが概念として名前を持っていない。
- 確かめる: 直した後、その責務の所在が一箇所に確定したか。
- 例外・注意: 一本化の前に「同じ意図か」を判定する(SKILL.md の判断ルール6)。Once And Only Once は行数節約の規則ではなく、責務の所在を一箇所に確定させる原則である。

## 技法〔7.3〜7.7〕

### 名前の変更〔7.3〕
- 定義: **名前の変更 = モデルの変更(設計の見直し)= リファクタリング**。名前を変えるとき、変わるのは文字列だけではなく、その名前が指す概念の輪郭である。最も基本的で、最も頻繁に行うべきリファクタリングである。
- いつ: 命名のアンチパターン(数字を付ける・省略する・意味不明・型名を含める・統一感がない・直訳。naming.md)に当たる名前を見つけたとき。それが着手点である。
- する: テストの保護の下で、IDE や言語ツールの一括リネームで付け直す。例: `data2` → `validatedOrders` で「検証済みの注文の集まり」という概念が語彙に加わる。
- 確かめる: 新しい名前が責務を過不足なく語るか。すべての参照が変わり、Green か。
- 例外・注意: 名前を放置したままでは、どれだけ構造をいじってもモデルの曖昧さは残る。公開 API の名前の変更は契約の変更になるので、依頼の範囲とユーザーの了承を確かめる。

### メソッド抽出は語彙の構築〔7.4〕
- 定義: メソッド抽出とは、コードを短くする作業ではなく、**語彙を構築する作業**である。メソッドは似た処理をまとめて再利用するためではなく、名前を付けて抽象化するためにある(サブルーチンは名前を付ける為にある。naming.md)。メソッド分割は、性能や行数の問題である前に、どんな語彙で記述したいかの問題である。
- いつ: 長すぎるメソッド、深いネスト、一時変数という中途半端な形で概念が埋まっているとき。
- する: 「この塊は、つまり何をやっているのか」と問い、意味のまとまりごとに切り出して名前を付ける。粒度は、人がそれを自然言語で最も簡潔に記述するときの粒度にする。手順(まずループを回して…)ではなく、概念の側から解く。
- 確かめる: 抽出後の上位のメソッドを自然言語に訳すと、その概念の定義そのものになるか。
- 例外・注意: 20行のメソッドを機械的に4等分しても意味はない。ただ似た処理をまとめただけでは、コードはスパゲッティ化する。

```csharp
// before: 「a と b と c を足し、これを sum とする。この sum を 3 で割る」
static double Average(double a, double b, double c) {
    var sum = a + b + c;
    return sum / 3.0;
}
// after: 「a と b と c の Sum を 3 で割ったもの」= 平均の定義そのもの
static double Sum(double a, double b, double c) => a + b + c;
static double Average(double a, double b, double c) => Sum(a, b, c) / 3.0;
```

### コメントは Why だけ〔7.5〕
- 定義: コードに書けないことのみをコメントにする。何(What)はクラス名・メソッド名で、どうやって(How)はコードそのもので表す。残る、なぜ(Why)そうしたかだけがコメントに書く価値を持つ。What や How をコメントで説明しているなら、それは名前とコードで表現しきれなかった症状、つまり臭いである。
- いつ: コメントが次の行の動作や条件式の意味をなぞっているとき。
- する: そのコメントの内容を名前にして、メソッド抽出と命名で説明責任を引き取る。「なぜ5ミリ秒待つのか」のような Why は残す。
- 確かめる: コメントを消しても、呼び出し側が仕様の文のまま読めるか。
- 例外・注意: 不要なコメントは、実装とずれても黙っており、S/N比を下げて本当に読むべき Why を埋もれさせる(S/N比は modeling.md)。名前の変更・メソッド抽出・コメント整理は、同じ一手の三つの側面である。

```csharp
// before: コメントが What をなぞっている
// もし閏年 (4で割れて100で割り切れないか400で割り切れる) だったら
if (y % 4 == 0 && y % 100 != 0 || y % 400 == 0) {
    UI.ShowYear(y);   // UIにその年を表示する
}
// after: 命名が説明責任を引き取る
static bool IsDivisibleBy(this int dividend, int divisor) => dividend % divisor == 0;
static bool IsLeapYear(this int year)
    => year.IsDivisibleBy(4) && !year.IsDivisibleBy(100) || year.IsDivisibleBy(400);
if (year.IsLeapYear()) UI.ShowYear(year);
```

### 制御構造の単純化〔7.6〕
- 定義: ネストが一段深くなるごとに、読み手はその分岐の文脈を頭に積んだまま読み進める。人が同時に保持できる文脈には限界があり、限界を超えたコードは読めなくなる。深いネストにはメソッド抽出、増殖する分岐にはポリモーフィズム。
- いつ: ネストが深いとき。同じ種類による分岐が複数のメソッドに現れたとき。
- する: ネストの内側の塊を「つまり何をやっているのか」で切り出す。種類による分岐は、各種類に「自分はどうするか」を答えさせる形(ポリモーフィズム、Strategy パターン)へ移す。
- 確かめる: 種類を一つ追加するとき、直す箇所が一箇所(新しいクラス一つ)で済むか。
- 例外・注意: **switch そのものは悪ではない。** 問題は、同じ分岐が複数箇所に増殖し、種類を追加するたびに全箇所の修正を強いる構造(変更の分散)である。その解消手段が OCP とポリモーフィズムである(object-design.md)。分岐が一箇所で種類も安定しているなら、ポリモーフィズムへの置換は引き算の観点から見送る(simplicity.md)。ネスト2回・20行・引数3つの目安の扱いは SKILL.md の判断ルール10 に従う。

例の題材は、線分・矩形の追加や選択をマウス操作で切り替える簡易 CAD の Controller である(詳細は下の「準備的リファクタリング」)。

```csharp
// before: 同じ CommandKind の分岐が MouseDown と MouseUp に増殖する
void MouseUp(Point p) {
    switch (kind) { case Line: ...; case Rectangle: ...; case Select: ...; }
}
// after: 種類ごとの振る舞いをコマンド自身に答えさせる
abstract class Command { public virtual void OnDragEnd(Model m, Point p) { } }
class AddLineCommand : Command { public override void OnDragEnd(Model m, Point p) => m.Add(...); }
void MouseUp(Point p) => command.OnDragEnd(model, p);
```

### 準備的リファクタリング〔7.6.3〕
- 定義: 機能を追加する前にリファクタリングしておくこと。臭いに気づいてから直すだけでなく、次に来るとわかっている変更の**前**に、置き場所を整えておく。
- いつ: 依頼された変更を今の構造にそのまま入れると、臭い(増殖する分岐など)を育ててしまうとき。
- する: 振る舞いを変えずに構造を先に直し、Green を確かめてから機能を足す。範囲と報告の分け方は SKILL.md の「変更範囲の節度」に従う。
- 確かめる: 機能追加そのものが、小さく局所的な差分で済んだか。
- 例外・注意: 「わかっている変更」は、依頼や要求にある変更である。来るかもしれない変更への備えは疑わしき一般化になる(simplicity.md)。
- 判断例(簡易 CAD のコマンド切り替え): 線分追加だけの Controller に矩形追加と選択を足すと、`MouseDown` と `MouseUp` の二箇所に同じ種類の分岐が増殖し、一部のコマンドでしか使わない開始点が Controller 全体の属性に居座る(一時的属性)→ 機能追加を続ける前に、コマンドの種類ごとに責務を分けて Controller から switch を追放する → 開始点はそれを使うコマンドの内部へ移る → 「2点から図形を作る」共通の骨格をもう一段抽出して語彙に加える → 後から楕円の追加が来たとき、書き足すのは1クラスで済んだ。

### 責務の切り出し〔7.7〕
- 定義: 責務ごとに明確に分割し、それぞれに名前を付ける。名前で表現できるまとまりが切り出しの単位である。境界線は「外部から」「シンプルに」内と外が区別できるように引く。
- いつ: 巨大なクラス、属性・操作の横恋慕を見つけたとき。
- する: 切り出した責務のスコープを決め、できるだけ小さいスコープに置く(スコープの4段階と「ひとことで言うと何?」は object-design.md)。
- 確かめる: 次の二つの検査に通るか。
  - 説明の検査: 責務を説明したとき「○○や△△なんかをやってる」と列挙が入るなら、境界線がくっきりしていない。
  - 記述時の依存の検査: ある関数の内部ロジックを書くのに、他の関数の内部ロジックを見なければ書けないなら、結合度が高すぎる。契約だけを見て書ける状態が正常である(契約に張ったテストが、切り出し後もそれを検証する。testing.md)。
- 例外・注意: 関心の分離はきれいに保つ良い手段だが、**ゴールではない**。分割を終えた瞬間のきれいさは、次の変更が来れば崩れ始める。分割した後もリファクタリングを重ね続ける。

## カイゼン〔7.8〕

### 良いと思うことを試し続ける〔7.8〕
- 定義: カイゼンとは、「良いことを行うこと」ではなく、「**良いと思うことを試し続けること**」である。何が良いかはやってみなければ分からないことが多い。だから、良いと思うことを試し、結果から学び、行動を変える。Red→Green→Refactor は、この計画・実行・検証・改善のループをコードのレベルで高速に回したものである。
- いつ: 常に。品質は、一度の設計ではなく活動として維持するものである。
- する: コンパイラー(文法と型のずれ)・静的解析(規約や既知の危険パターンからのずれ)・単体テスト(仕様とのずれ)という**フィードバックツールの網**に、自分の生成物を毎回通す。ずれを検知した箇所を、臭いの語彙で特定して直す。ユーザーのレビューも、即座に返るフィードバックとして扱う。
- 確かめる: 変更の前後で、名指しした臭いが減ったことを報告で示せるか(品質の高さそのものより、向上していく角度が大事)。
- 例外・注意: 完全を求めない。十分であれば良い。完璧な設計に一度で到達しようとする態度は「設計の繰り返し」と正反対である。既知と思ったことも、答えをもって見ずに見つめ直す。個々の技法は手段であり、目的は変更しやすい状態を保ち続けることである(フィードバックの最大化は testing.md)。

## 精神論ではなく臭いと技法の名前で語る〔7.9〕

- 定義: 「もっと丁寧に」「品質意識を持て」は何も教えていない。「このメソッドは責務が三つ混ざっているから、まずこの塊に名前を付けて切り出す」と、臭いの名前と技法の名前で説明する。理由を言語化できることが技量である。臭いの名前と技法の名前が、そのままレビュー・改善の語彙になる。
- いつ: 自分の生成物をセルフレビューするとき。レビューで指摘するとき。リファクタリングの結果を報告するとき。
- する: 自分の生成物は、責務の混在・曖昧な名前・What をなぞるコメント・深いネストを平然と含みうる前提で点検する。指摘と報告は次の書式で書く。
  - `<場所>: <臭いの名前>(<症状の根拠>)→ <技法> → <結果と検証>`
  - 例: 「`ProcessData`: 長すぎるメソッド(検証と保存の責務が混在)→ メソッド抽出で `Validate` と `Save` に分けた → テスト12件 Green」
  - 例: 「`Controller` の switch: スイッチ文(種類の追加ごとに二箇所が増える)→ ポリモーフィズムで解消を提案(範囲外のため未実施)」
- 確かめる: 報告や指摘に「きれいにした」「整理した」「改善した」だけの文が残っていないか。各項目に臭い・技法・理由(何故そうするか)・実際の差分かテスト結果が揃っているか。
- 例外・注意: 臭いの一覧に当てはまらないときは、名前を無理に当てはめず、症状と理由を具体的に書く。

## 臭い → 技法の対応表〔7.2〜7.7〕

原典が対処まで扱うのは、重複したコード・長すぎるメソッド・コメント・スイッチ文・巨大なクラス・属性、操作の横恋慕・一時的属性(22項目の外では、不適切な名前と深いネスト)である。それ以外の行は、他章の原則(第5章など)からの適用である。

| 臭い・症状 | 技法 |
|---|---|
| 不適切な名前(命名アンチパターン) | 名前の変更 |
| 長すぎるメソッド | 意味のまとまりでのメソッド抽出 |
| コメント(What・How の説明) | 名前の変更とメソッド抽出で置き換え、Why だけ残す |
| 重複したコード | 背後の責務を特定し、名前の変更・メソッド抽出・責務の切り出しで一箇所に確定させる |
| 深いネスト | メソッド抽出 |
| スイッチ文(増殖する分岐) | ポリモーフィズムによる型の差し替え(Strategy パターン) |
| 一時的属性 | 属性を、それを必要とする側の内部へ移す |
| 巨大なクラス/属性、操作の横恋慕 | 責務の切り出し(責務の割り当て、高凝集・疎結合。object-design.md) |
| 多すぎる引数/データの群れ | データの群れに型として名前を付ける(naming.md) |
| 基本データ型への執着 | 専用型を導入する(testing.md) |
| メッセージの連鎖 | デメテルの法則に沿って、依頼先に委ねる(object-design.md) |

次の臭いには、決まった技法を示さない(名前で名指しするにとどめる)。直すかどうかと直し方は、右の原則で判断する。

| 臭い | 判断に使う原則 |
|---|---|
| 変更の発散 | 変更理由を一つにする(object-design.md) |
| 変更の分散 | ひとつの変更 → ひとつの修正。増殖する分岐なら上のスイッチ文の行(object-design.md) |
| 疑わしき一般化 | YAGNI・引き算の設計(simplicity.md) |
| 怠け者クラス/仲介人 | 「ひとことで言うと何?」テストと、委譲しても役割の所在は移らない(object-design.md)。役割を名指しできなければ、引き算の対象として報告する |
| データクラス | 情報を持つ者に判定を任せる(Expert。object-design.md) |
| パラレル継承/相続拒否 | 再利用のための継承は合成に変える、LSP(object-design.md) |
| 不適切な関係 | デメテルの法則、相手の公開サービスだけに依存する(object-design.md) |
| クラスのインタフェース不一致 | 第六箇条「ルールの統一」と、命名の「統一感がない」(naming.md) |
| 未熟なクラスライブラリ | サービス指向名前付け(SON。利用者視点の名前で、ライブラリの都合を自分のコードに漏らさない。naming.md) |
