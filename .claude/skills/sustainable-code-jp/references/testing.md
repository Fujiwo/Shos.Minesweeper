# テスト(Testable・TDD・テストケース設計)

テストを書く・足す・レビューするとき、テストしやすい構造を設計するとき、TDD で実装を進めるときに読む。フィードバックの最大化と、契約のテスト側の詳細はここにある(契約とガード節そのものは quality-gates.md)。

## Testable とフィードバックの最大化

### Testable〔1.2.7〕
- 定義: 正しい記述であることが分かるようになっていること。Testable な設計が目指すのは**フィードバックの最大化**である。フィードバックが早く、頻繁に得られるほど、品質の高いソフトウェアを効率的に開発できる。
- いつ: クラスやメソッドを新しく書くとき。テストを書こうとして準備が重いと感じたとき。
- する: 依存(リポジトリ・外部サービス・時刻・ファイルシステム)をコンストラクタなどから注入する。判定や計算は、依存を受け取らない純粋な部分に切り出す。外部 I/O は薄い層に隔離する。
- 確かめる: テストダブルを差し込むだけで、DB・ネットワーク・現在時刻なしにテストを書けるか。
- 例外・注意: 生成したコードを一行ずつ読み切ることは量的に現実的でない。速く・繰り返し・自動で確かめられる構造だけが、生成速度を品質につなげる。Testable でないコードを大量に書くことは、検証できない負債を積むことと同じである。差し替え口を作ることは YAGNI 違反ではない(SKILL.md の判断ルール3)。

```csharp
// before: DB と現在時刻に直接依存し、単独で検証できない
public void ProcessOrder(int orderId) {
    using var connection = new SqlConnection("...");
    var now = DateTime.Now;   // 検証・計算・送信も同じメソッドに集約
}
// after: repository・email・clock はコンストラクタで注入し、判定は純粋な部分に切り出す
public OrderProcessingResult ProcessOrder(int orderId) {
    var order = repository.FindById(orderId);
    return ValidateAndProcess(order, processedAt: clock.Now);   // 成功時の email 送信は省略
}
```

### フィードバックの種類〔1.2.7〕

速いものから順に使う。遅いフィードバックしかない箇所は、速いフィードバックが得られる形へ寄せる。

| 種類 | 何を検知するか | エージェントの行動 |
|---|---|---|
| コンパイル時 | 型の誤用 | 概念を表す値には専用型を使う(下記) |
| 単体テスト | 仕様とのずれ | 依存をテストダブルに差し替え、AAA で書く |
| 統合テスト | 部品をつないだワークフロー全体の不具合 | 部品をつないだワークフロー全体を確かめる。単体テストより遅いので、結合部分とワークフローの確認に絞る |
| 継続的フィードバック | 変更ごとのずれ | 変更のたびにビルド・静的解析・テストを実行する(quality-gates.md) |

### 専用型でコンパイル時にフィードバックを得る〔1.2.7〕
- 定義: 型安全性によって、誤りをコンパイル時に検出する。最も速いフィードバックである。
- いつ: ID・金額・数量などの概念を int や string のまま引数や属性にしようとしているとき。
- する: 引数に int ではなく `OrderId` のような専用型を使い、取り違えをコンパイルエラーにする。
- 確かめる: 引数の順序を取り違えたらコンパイルが通らないか。
- 例外・注意: 既存コードで同じ臭いを見つけた場合は「基本データ型への執着」として扱う(refactoring.md)。

```csharp
// before: 引数を取り違えてもコンパイルが通る
public Order(int id, int customerId) { ... }
new Order(customerId, orderId);   // 実行するまで気づけない
// after: 取り違えはコンパイルエラーになる
public Order(OrderId id, CustomerId customerId) { ... }
```

### テストの形: AAA とテストダブル〔1.2.7、6.3.2〕
- テストは準備(Arrange)・実行(Act)・検証(Assert)の3段階で並べる。題材が小さければ2行に収まってよいが、並びは同じにする。
- 差し替える依存には、テスト用に単純実装したテストダブルを使う。例: 決まったデータを返す Fake のリポジトリ、送信先を記録する Spy のメール送信、固定時刻を返す時刻プロバイダ。
- 外部 I/O(DB・API・ファイルシステム)を隔離すると、テストは高速で安定する。

## テストファースト

### テストは最初の利用者〔6.1.1〕
- 定義: テストファーストは、What(何をしたいか)を How(どう実現するか)より先に確定させる仕掛けである。命名が What を名前で表す技法なら、テストファーストは What をコードで表す技法である。テストコードは、作ろうとしているクラスの**最初の利用者**である。
- いつ: 新しいクラス・メソッド・API を作るとき。
- する: 実装より先に、それを使う側のコードを書く。その「使う側の例」にアサーションを付けて、そのまま資産にする。
- 確かめる: テストを書いた時点で、呼び出しが自然か。使いにくい API は、ここで使いにくさが露呈する。露呈したら実装前に名前と形を直す(naming.md の SON)。
- 例外・注意: テストファーストでは、テストしやすい形を先に想定して設計するのではなく、テストを先に書くことで設計がテストしやすい形に導かれる。上の「Testable」の構造(依存の注入、純粋な部分の切り出し)は、同じ形を結果の側から見たものであり、両者は矛盾しない。

### テストは動く設計書〔6.1.2〕
- 定義: テストコードは「動く設計書」である。文書の設計書は実装とずれても誰も気づかないが、テストは実装が仕様からずれた瞬間に失敗する。仕様と現状のずれ、それがバグである。
- いつ: 仕様を確定させたいとき。仕様が最初から全部は分からないとき。
- する: 「その時点のテストを通れば、その時点での仕様どおり」と考え、テストケースを一つずつ足しながら仕様を段階的に確定する。一度にすべて解こうとしない。
- 確かめる: テスト名の一覧を読むだけで仕様が分かるか。
- 例外・注意: コメントに事前条件・事後条件を書いても、実装とずれたまま黙っている。テストはずれた瞬間に赤くなる〔6.5.1〕。

### Red・Green・Refactor と帽子の切り替え〔6.1.2〕

| 拍 | すること | 帽子と関心 |
|---|---|---|
| Red | 失敗するテストを書き、失敗を確認する。失敗は「仕様と現状のずれ」の見える化 | 利用者の帽子。内部は忘れ、どう呼び出せると使いやすいかだけを考える |
| Green | テストを通す最小限の実装を書く。きれいさは問わず、最短で Green へ | 実装者の帽子 |
| Refactor | 全テストが通る状態を安全網に内部構造を改善する。テストは変えない | 実装者のまま、関心が「動くこと」から「内部の品質」へ移る |

- 一周は数分である。常に「すべて Green」の状態のそばを離れずに、コードを漸進的に育てる。
- 仕様を決める視点と、コードを作る視点を一周ごとに意識的に行き来する。

## TDD の進め方(判断例)〔6.2〕

状況: 年・月・日が日付として正しいかを答える型 `Date`(日本語識別子 `日付`・`日付として正しい` で書くと意図がさらに際立つ)を、白紙からテストファーストで作る。

1. **仕様を入力と期待値の対に翻訳する。** 「うるう年を正しく扱う」は解釈の余地を残すが、「2100/02/29 は正しくない」には残らない。表は下記「テストケースの設計」の15件。
2. **1件ずつコードにする。** 15件をいきなり全部書かない。
3. **Red を必ず見る。** 型がまだなくコンパイルが通らないのも Red であり、最速のフィードバックである。まだ実装していないのに最初から Green なら、そのテストは何も検証していない。Red を一度見ることは、テスト自体が機能していることの検証である。
4. **Fake It(仮実装)で最短の Green へ。** `IsValid => true` のように定数を返す。数秒で Green に戻れ、テストの書き方・実行環境・配線が正しいことが確定する。この嘘は次のテストが暴くので放置されない。
5. **三角測量で一般化する。** 「月が13は正しくない」を足すと定数ではいられず `Month <= 12` になる。一点なら定数でごまかせるが、二点あればごまかせない。テストを1件書くたびに、実装を最小限だけ広げる。「どうせ後で要る」と先回りした実装には、それを検証するテストがない。
6. **難所は後回しにする。** 最も複雑なうるう年は、まず「2月は28日まで」の仮実装で進む。仮実装が生き延びるのは、それを暴くテストがまだないからにすぎない。2008・2100・2000 の3件が、判定式を一段ずつ「4の倍数、但し100の倍数を除く、但し400の倍数は含む」へ追い込む。
7. **最初から通るテストも残す。** 「うるう年の2月30日は正しくない」は足しても Red にならないが、境界を守り続ける番人として価値がある(手順3の「Red を見る」は、実装で満たす前のテストに対する規則)。
8. **Refactor は一手ごとにテストを実行する。** 20行の塊を、意味のまとまりごとに名前を付けたプロパティ(`IsYearValid`・`LastDayOfMonth`・`IsLeapYear` など)へ分け、毎回 Green を確かめる。

- 理由: テストが What を先に確定するから、実装は What を語る形に整理されやすい。検証ロジックを副作用のない純粋な式で書き、外部依存を持たせなかったので、モックの準備なしにテストが軽快に回った。

## テストケースの設計〔6.3〕

### 代表値・境界値・エッジケース〔6.3.1〕

| 分類 | 考え方 | 日付の例(入力 → 期待) |
|---|---|---|
| 代表値 | 仕様の中心にある普通の値を1件 | 2007/02/14 → 正しい |
| 境界値 | 仕様の「境目」の両側を1件ずつ。`<` と `<=` の誤りは境界のちょうど両側でだけ露呈する | 年0・月0・月13・日0・日32 → 正しくない/1月31日 → 正しい/4月31日 → 正しくない/4月30日 → 正しい |
| エッジケース | 仕様の例外規定が折り重なる特殊な値。例外規定が一段あるごとに、その規定が効く値を最低1件 | 平年 2007/02/28 → 正しい、2007/02/29 → 正しくない/4の倍数 2008/02/29 → 正しい、2008/02/30 → 正しくない/100の倍数 2100/02/29 → 正しくない/400の倍数 2000/02/29 → 正しい |

- エッジケースの中にも境界値の考え方が入れ子で現れる(うるう年の2月29日と30日)。
- テストケースの設計が、そのまま実装の成長の設計になる(三段の例外規定の3件が、判定式を一段ずつ育てた)。
- 全件を最初に揃える必要はない。途中で抜けに気づいたら、その時点で表に1行足す。テストケース一覧は育てていく仕様書である。

### テスト名とアサーションで仕様を語る〔6.3.2〕
- テスト名は、**入力の状況と期待される結果を含んだ仕様の文**にする(例: `April31IsInvalid`、「400の倍数の年の2月29日は正しい」)。`Test1` や `MonthTest` では、失敗したときに何の仕様が破れたか分からない。
- 一つのテストでは一つの関心事だけを検証する。「月が13は正しくない」にうるう年の検証を混ぜない。関心を混ぜたテストは、失敗したときにどの仕様が破れたのかを語れない。
- テスト名が仕様を語り、アサーションが期待値を確定する。この二つが揃って初めて、常駐して実行され続ける仕様書になる。

## テストとリファクタリング〔6.4〕

### 安全網〔6.4.1〕
- 定義: テストがあるからリファクタリングできる。リファクタリングするからコードがきれいに保たれる。コードがきれいだからテストも書きやすい。この好循環の出発点がテストという安全網である。TDD の真の目的は、バグを見つけることではなく、**バグだらけで手が付けられない状況に自分を追い込まない**ことにある。
- いつ: 構造を変えようとするとき。テストのない「動いているが誰も触れないコード」(理解負債の典型的な発生源)に出会ったとき。
- する: 構造変更の前に、契約を押さえるテストが揃っているかを確かめる。数分ごとに Green へ戻り、ずれが小さいうちに検知して直す。
- 確かめる: 一手ごとに関連するテストが、完了報告の前に全テストが Green か。
- 例外・注意: ずれの発見が遅いほど修正は高くつく(障害の大きさ=エラー×滞在時間。refactoring.md)。テストのないコードを大きく作り変えないことは SKILL.md の「変更範囲の節度」に従う。

### 3方向のツッコミ〔6.4.2〕
- 定義: 実装は設計へのツッコミであり、テストは実装へのツッコミである。フィードバックとは、自分の作った物への的確なツッコミであり、早いほど、多いほどよい。
- テスト→実装: 実装の不足が分かる。実装→設計: API の使いにくさや名前の不適切さが分かる。テスト→設計: 設計を変えたときの安全を保証する。
- する: 最速のツッコミ役(テスト)を先に仕込む。実装中に API や名前の違和感に気づいたら、それを設計へのフィードバックとして扱い、直す。

## 良いテストコードの条件〔6.5〕

### テストは契約に張る〔6.5.1〕
- 定義: テストを契約に張り、実装の詳細に張らない。これがリファクタリングに耐えるテストの条件である。テストは契約の実行可能な記述である。良いテストスイートは、何を検証するかと同時に、**何を検証しないか**が設計されている。
- いつ: テストの対象を決めるとき。private や internal の補助メソッドを直接テストしたくなったとき。
- する: 公開された振る舞い(外部への約束)だけを検証する。内部の補助メソッドは、公開された振る舞いを通して間接的に検証する。
- 確かめる: 内部を if の塊から switch に書き換えても、テストを一行も直さずに済むか。
- 例外・注意: 内部構造に結び付いたテストは、構造を変えるたびに書き直しになり、安全網どころかリファクタリングの足かせになる。日付の例で内部の `IsLeapYear` はリファクタリングの時点まで存在しなかった。

### カバレッジとメトリクスハック〔1.2.7、6.5.2〕
- 定義: カバレッジは「テストがコードを通ったか」を測るのであって、「テストが正しさを検証したか」は測らない。アサーションをすべて削除してもカバレッジは100%のまま変わらない。数字を目標にした瞬間、数字だけが達成される(メトリクスハック)。
- いつ: 「カバレッジを上げて」と依頼されたとき。テストを大量に生成するとき。
- する: アサーションのないテストは書かない。カバレッジは、テストの届いていない場所を見つける手段として使い、低い箇所を代表値・境界値・エッジケースの分類で見直す。
- 確かめる: 各テストに期待値を確定するアサーションがあるか。実装をわざと壊したら失敗するか。
- 例外・注意: カバレッジが無意味なのではない。手段と目標を取り違えない。カバレッジ目標を依頼されたときも、数値と合わせて何を検証したかを報告する。

### 何を検証すべきかはユーザーと合意する〔6.5.2〕
- 定義: テストコードの生成は AI が得意とするが、仕様の表を作る仕事、つまり**何を検証すべきかを決める仕事は人間に残る**。検証の内容を決める力が技法の核心である。
- いつ: テストケースを設計するとき。仕様が文章でしか与えられていないとき。
- する: 境界はどこか、例外規定は何段あるか、契約として何を約束するかを、入力と期待値の表にしてユーザーに示す。解釈が割れる行(境界の含む・含まない、例外規定の扱い)は、確認してからテストにする。
- 確かめる: 表のすべての行が、ユーザーの意図した仕様に対応しているか。
- 例外・注意: ここを曖昧にしたままテストを量産すると、もっともらしい形をしたメトリクスハックになる。解釈の割れない小さな変更では確認を求めず、表を報告に含めるだけでよい(SKILL.md の行動原則3)。

## 既存コードにテストを後から足す〔6.4.1、6.5〕

- いつ: テストのないコードをリファクタリングする前(安全網を張る)。既存のクラスにテストを追加するよう頼まれたとき。
- する:
  1. 公開された振る舞い(契約)について、代表値・境界値・エッジケースの表を作り、現状の振る舞いを押さえるテストを書く。
  2. 実装は既にあるので、最初から Green になる。Red を見る代わりに、実装をわざと壊してテストが失敗することを確かめ、壊した変更は戻す。
  3. 現状の振る舞いが仕様と思えない(バグらしい)行は、テストを足す目的で扱いを分ける。
     - リファクタリングの安全網として張る場合: 振る舞いを保つことが目的なので、その行も現状のまま押さえ、「バグの疑い」として報告する。直すかどうかは、リファクタリングとは別の手順で決める。
     - 仕様を検証するためにテストを足す場合: 期待値を現状に合わせてテストにしない。その行はユーザーに報告し、仕様を確認してから扱う。
  4. テストを書くために依存の差し替え口が必要なら、それはテストのない状態での構造変更になる。差し替え口を作る前にユーザーに確認する。
- 確かめる: 足したテストが、契約の各行を押さえ、実装を壊すと失敗するか。

## テスト基盤がない場合

SKILL.md の「実行できない場合の代替手段」の詳細。

1. **テストフレームワークを勝手に導入しない。** 導入は依頼範囲外の変更であり、頼まれていない仕組みを足すことになる。導入するかを、候補(言語の標準的な選択肢、既存のビルド手順への組み込み方)とあわせてユーザーに確認する。ただし、言語標準のテスト機構(新しい依存も設定も要らないもの)を使うことは導入に当たらない。その場合も、追加したテストとその実行方法を報告する。
2. **確認するまでの間は、既存の環境で使える最小の検証手段で進める。**
   - 型: 専用型で取り違えをコンパイルエラーにする。
   - アサーション・ガード節: 前提条件を実行時に検査する(quality-gates.md)。
   - 実行による確認: 上記のテストケース表の入力を実際に流し、期待値と突き合わせる。一時的な確認用コードはリポジトリに残さない。
3. **どの検証をしたかを報告する。** 表のどの行を、どの手段で確認したか、確認できていない行はどれかを示す。
4. テストを望まない依頼でも、テストしやすい構造(依存の注入、純粋な部分の切り出し)は保つ。

## テストのセルフチェック

- [ ] テストは公開された振る舞い(契約)だけに張っているか
- [ ] 各テストにアサーションがあり、実装を壊すと失敗するか
- [ ] テスト名が入力の状況と期待結果を含む仕様の文か
