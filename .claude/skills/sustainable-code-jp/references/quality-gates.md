# 品質の関門(レビュー・規約・契約・検証・性能・負債)

実装の途中と完了前、セルフレビューやコードレビューを行うとき、引数検証や前提条件を書くとき、性能改善を頼まれたとき、変更を報告するときに読む。

## 品質管理の二つの軸〔9.導入〕

- 定義: 品質管理の柱は、問題を早く検知することと、理解しやすく変更しやすい状態を保つことにある。この持続可能な状態を維持することが目的である。
- 早期検知が効くのは、障害の大きさがエラーの滞在時間に比例するからである(式は refactoring.md)。セルフレビュー・契約・ビルドとテストは、エラーを捕まえる網の目であり、目が細かいほど滞在時間は短くなる。
- エラーを検知できても、直しにくいコードでは意味がない。だから規約と負債管理で、理解しやすさ・変更しやすさを保ち続ける。

## セルフレビュー〔9.1〕

### 一手ごとのセルフレビュー〔9.1.1〕
- 定義: レビューは、実装が終わったあとにまとめて行う一回きりの関門ではなく、常時のフィードバックである。設計や実装は常にレビューされているべきものであり、これはサイバラの原則の4本柱の一つである(simplicity.md)。
- いつ: 意味のある一手(メソッド1つの追加、名前の変更、抽出など)を終えるたび。完了報告の前。
- する: 小さな差分ごとに、下の七箇条の問いで自分の変更を見直す。まとめて最後に見直さない。
- 確かめる: 次の一手に進む前に、直前の差分を七箇条の言葉で説明できるか。

### 七箇条をレビューの観点にする〔9.1.3〕
- 定義: 七箇条は、個人の指針であると同時に、そのままレビューの共通観点として機能する。「読んで気になった」という漠然とした感想ではなく、七箇条の言葉で指摘する方が、指摘は具体的になり改善しやすい。
- する: まず、レビュー対象(PR・差分・コード)の意図を一言で言う。言えなければ、ユーザーや PR の説明で確かめる(良し悪しは意図とコードの呼応に宿る。modeling.md)。そのうえで、セルフレビューでもユーザーのコードのレビューでも、次の問いで見る。指摘は該当する箇条の名前を添え、改善案とセットにする。精神論は書かない。

| 箇条 | レビューの問い |
|---|---|
| 意図を表現 | What が How より前に出ているか。意図以外の記述(ノイズ)が意図を埋もれさせていないか |
| 単一責務 | この責務は一つに閉じているか。変更理由はいくつあるか |
| 的確な名前 | この名前は境界を過不足なく表しているか。同じものは同じ名前か |
| Once And Only Once | 同じ意図の記述が二箇所以上にないか |
| 的確なメソッド | 一つのメソッドの中で抽象度が揃っているか |
| ルールの統一 | 既存コードの流儀・規約に合っているか |
| Testable | 正しいことを確かめられる形か。前提条件が明示されているか |

- 臭いの名前で指摘できる場合は、臭いと技法の名前を使う(refactoring.md)。

### コミット前チェック(完了前チェック)

一手ごと、および完了報告の前に、この順で実行する。コミット自体はユーザーが許可または依頼した場合に限る(SKILL.md の変更範囲の節度)。

1. セルフレビュー: 上の七箇条の問いと、SKILL.md のセルフチェック(引き算を含む)
2. フォーマッター・リンター: リポジトリに設定があれば実行し、結果に従う
3. ビルド: 通ることを確認する
4. テスト: 一手ごとに関連するテストを実行し、完了報告の前に全テストを実行して Green を確認する

## コーディング規約〔9.2、10.1〕

### 規約は複雑さを抑えるためだけに使う〔9.2.1〕
- 定義: コーディング規約の目的は一つしかない。複雑さを抑えることである。プログラミングで難しいのは複雑になってしまうところであり、それこそが保守性の一番の敵である。規約はスタイルの好みを統一する道具ではなく、複雑さを増やさないための道具として使う。
- いつ: 規約を提案する、規約に従うか迷う、規約違反を指摘するとき。
- する: リポジトリに既存のフォーマッター・リンター・規約があれば、それを実行して結果に従う(優先順位は SKILL.md)。自分から規約項目を提案するときは、複雑さを抑える項目に絞る。
- 確かめる: その規約項目は、どの複雑さを抑えるのかを一言で言えるか。
- 例外・注意: 数値基準の扱いは SKILL.md の判断ルール10、型を試さずに回避しない原則は SKILL.md の優先順位に従う。

### 規約を提案するときの禁止事項〔9.2.3〕

規約が目的化すると、かえって害になる。次の形の規約・運用を提案しない。

| 提案しないもの | 理由 |
|---|---|
| 構造を固定して中身だけ書かせる(クラスは全部自動生成、クラス作成に申請が必要、全クラスを表計算で管理) | 規約を守ること自体が目的化し、複雑さを抑えるという目的を見失っている |
| 長大なメソッドを放置する運用 | 複雑さを抑えていない |
| 技量が一番下の人に合わせる規約 | 多くのコードを生産している人の足を引っ張り、全体最適にならない |
| 宣言的なコレクション操作のような、複雑さを回避する仕組みの禁止 | 保守性を下げる原因は解消されない。シンプルと簡単を混同している(simplicity.md) |
| 比較の左右の順序や、単文への波括弧の強制のような瑣末なスタイル規則 | 複雑さを抑えるという本筋から外れる。本筋は「ネストを浅く」「分岐を減らす」のような具体的な項目 |

- 規約は、複雑さを回避する仕組みを使いこなすための足場であるべきである。
- 規約は、決める(最小限の項目と例外条件)→自動化する(フォーマッター・静的解析)→観測する→更新する(形骸化した項目を見直して薄く保つ)のサイクルで回す。〔9.2.4〕

## 契約とガード節〔9.3〕

### 契約は説明責任の実行形〔9.3.1〕
- 定義: 契約プログラミングは、堅牢化のためのテクニックである以前に、説明責任の実行形である。「このメソッドは何を期待し、何を保証するか」を、コードそのものに宣言する行為である。名前と公開範囲が利用者視点で決まっているとき、オブジェクト間に契約が成立する(object-design.md)。その契約を検証するのがテストである(testing.md)。
- 3点セット〔9.3.2〕:

| 条件 | 内容 |
|---|---|
| 前提条件 | 呼び出す側が満たすべき条件。破られていれば、メソッドは処理を実行する責任を負わない |
| 事後条件 | 実行後に、呼び出し側へ保証される結果や状態 |
| 不変条件 | オブジェクトの生存期間を通じて常に成り立つべき条件 |

- する: 不変条件はコンストラクタで成立させ、状態を変えるメソッドの後も崩れないようにする。重要な状態変更の後には、事後条件をアサーションで表す〔9.3.2〕。

### ガード節〔9.3.2、9.3.3〕
- 定義: 前提条件をメソッドの先頭で明示的にチェックし、満たされなければ即座に処理を打ち切る書き方。
- いつ: 公開メソッド・コンストラクタが引数や状態に前提を持つとき。バグ修正で前提条件の破れが原因だと分かったとき。
- する: 前提条件は入口のガード節で検証し、本処理を異常系のないフラットな一本道にする。検証には、言語標準の検証 API・アサーション・型システム(null 非許容型、専用型など)を優先し、独自の検証の仕組みを作らない。
- 確かめる: 本処理に異常系の分岐が残っていないか。前提条件がコードから読み取れるか。
- ガード節の三つの効能:
  1. 異常系を入口で排除し、本処理をシンプルに保つ。複雑な問題を扱わなければならない状況に自分を持っていかない、をコードのレベルで実装する
  2. バグの早期検知。契約違反をその場で検知し、エラーの滞在時間をほぼゼロに縮める
  3. 「引数検証はガード節で先頭に置く」「前提条件が明示されているか」のように、規約項目・レビュー観点として機械的にチェックしやすい
- 例外・注意:
  - ガード節は前提条件の破れを検知するものであり、破れを起こしている呼び出し元の修正ではない(バグ修正の進め方は下の「バグ修正」)。
  - 言語標準の検証 API の例: C# の `ArgumentNullException.ThrowIfNull`、Java の `Objects.requireNonNull`、Python の `raise ValueError`。
  - リポジトリの規約が早期リターンを禁じていれば規約に従い、複雑さが増すと判断したら指摘するだけにする(SKILL.md の優先順位)。規約が return だけを禁じているなら、例外を投げるガード節は使ってよい。途中脱出全般を禁じている、または判断できないときは、検証結果を変数にまとめて末尾の単一 return にし(下の2つ目の例)、どう解釈したかを報告する。既存の契約が戻り値でエラーを返せない形(void など)なら、型を変えずにユーザーに確認する。エラーを黙って捨てない。

```csharp
public void Withdraw(decimal amount) {
    // ガード節: 前提条件を入口で検証し、満たされなければ打ち切る
    ArgumentOutOfRangeException.ThrowIfNegativeOrZero(amount);
    if (amount > balance) throw new InvalidOperationException("残高不足");
    var before = balance;
    balance -= amount;                          // 本処理はフラットな一本道
    Debug.Assert(balance == before - amount);   // 事後条件
}

// 規約で途中脱出(例外によるものも含む)が禁じられている場合: 検証結果をまとめ、末尾の単一 return にする
public Result Register(string? name, int age) {
    var error = name is null or ""      ? "名前が空です"
              : age is < 0 or > 150     ? "年齢が範囲外です"
              : null;
    Result result;
    if (error is null) result = Result.Ok(repository.Add(name!, age)); // 本処理は 1 か所
    else               result = Result.Fail(error);
    return result;
}
```

### バグ修正〔6.1、7.1、9.3〕
- 定義: バグとは仕様と現状のずれである。ずれは、見える化してから直す。
- いつ: 不具合の修正を頼まれたとき。
- する:
  1. テスト基盤があれば、不具合を再現するテストを先に書き、Red を確かめる(基盤がなければ SKILL.md の代替手段)。
     - 期待値が仕様から決まらないときは、期待値を推測で決めない。再現テストは理由を明記して保留(例: xUnit の `Skip`)で置き、再現手順と観察結果を報告して仕様を確認する。期待値が決まったら書き込み、保留を外して Red を確かめてから直す。
     - いま起きている誤り(例: NullReferenceException)を期待値としてアサートしない。最初から Green になり、バグを仕様として固定してしまう。
  2. 原因(前提条件を破っている呼び出し元、誤った境界など)を特定し、最小の変更で直して Green にする。症状を握りつぶすだけの変更(例外を捕まえて無視する、null を黙って既定値に置き換える)で終わらせない。
  3. 前提条件の破れが原因なら、入口にガード節や型で前提条件を明示する。ただしそれは再発の検知であり、原因の修正とは別に行う。
  4. 周辺の臭いは直さず、報告する(SKILL.md の変更範囲の節度)。
- 確かめる: 再現テストが Red から Green になったか。既存のテストがすべて Green か。
- 例外・注意: バグ修正とリファクタリングを混ぜない。構造の改善が必要なら、修正と手順を分ける(refactoring.md)。

## 常にビルド・実行できる状態を保つ〔9.4〕

### 変更ごとにビルド→静的解析→テスト〔9.4.1、9.4.2〕
- 定義: コンパイラー・静的コード分析・単体テストツールは、すべてフィードバック・ツールである。これらを一つの流れにつなぎ、常時走らせることで、常にビルド可能・常にテスト可能な状態を保つ。
- いつ: 一手ごと。
- する: 変更のたびにローカルでビルド→静的解析→テストを実行する。なるべく常にプログラムが起動可能な状態を保ち、インクリメンタルに機能を足す。完成に近づくまで起動できない進め方をしない。
- 確かめる: 今この時点でビルドとテストが通るか。壊れた状態で次の一手に進んでいないか。
- 例外・注意: リポジトリで利用できるツール(型チェッカー・アナライザー・テストランナー)は使う。良い開発ツールを使いこなすことも品質管理の一部である。ツールを新たに導入するのは範囲外の変更なので、ユーザーに確認する。

## 技術的負債とパフォーマンス〔9.5〕

### 負債の滞在時間を短く保つ〔9.5.1〕
- 定義: 障害の大きさの式は技術的負債にもそのまま当てはまる。返済を先延ばしにした負債は利息のように膨らむ。技術的負債の管理とは、負債の滞在時間を短く保つ活動である。
- する: 負債を放置しない。変更対象の中で見つけた負債は、その場で返す(準備的リファクタリングの条件は SKILL.md)。範囲外で気づいた負債は直さず、臭いの名前と場所を添えて報告する。範囲外の負債を報告するときは、放置すると膨らむ理由(変更の頻度・波及範囲)を一言添え、返済の優先順位を判断できるようにする〔9.5.1〕。

### パフォーマンス判断の3原則〔9.5.2〕
- 定義: パフォーマンスは勘ではなく計測して合意する判断の対象である。優先順位は相対的に低いが、無視してよいわけではない。
  1. 正しく動くコードを先に書く
  2. 計測してから最適化する
  3. 可読性を犠牲にしない最適化を選ぶ
- いつ: 「遅い」「速くして」と頼まれたとき。性能を理由に書き方を変えたくなったとき。
- する: 可読性と保守性を高めた状態を保ったまま、計測でボトルネックを特定し、その箇所だけを局所的に最適化する。解消したら、再び計測して次のボトルネックを探す。20%のコードが実行時間の80%を占める(80:20)ので、最適化はボトルネックに絞る。
- 確かめる: 最適化の前後の計測値を示せるか。最適化した箇所は計測で特定した箇所か。
- 例外・注意: 実行速度を気にしすぎると、呼び出し側がサブルーチンの内部実装に依存し、抽象化の壁が壊れる。最適化の前に、振る舞いを押さえるテストがあるかを確かめる(なければ testing.md の「既存コードにテストを後から足す」)。プロファイラーがなくても、区間の時間を測るなど、できる計測はする(一時的な計測コードは残さない)。それもできない環境では、計測の方法(計測する経路・データ量・手段)を提案する。推測だけで可読性を下げる最適化はしない。やむを得ず行うときは推測であることを明示してユーザーに確認する。

### トレードオフを記録し、ユーザーの合意を得る〔9.5.3〕
- 定義: 可読性を犠牲にする最適化をあえて選ぶときは、判断の理由をコメントに残し、合意を得る。パフォーマンスのトレードオフは Why コメントの実例である。
- する: 可読性を下げる最適化は、提案(計測値とトレードオフ)として示し、ユーザーの合意を得てから実装する。性能改善を明示的に頼まれていても、可読性を下げる箇所は報告で個別に示す(箇所・理由・計測値)。Why コメントには計測値を含める。

```csharp
// Why: 宣言的な連鎖ではこの経路で3回の走査が発生し、計測の結果、
// 本番相当データで許容時間の3倍かかっていた。可読性は下がるが、
// 単一ループへ変更してこの経路だけ高速化する。
var total = 0m;
foreach (var item in items)
    if (item.IsActive) total += item.Price * item.Quantity;
```

## 三つの負債と AI の出力〔9.6〕

### 三つの負債〔9.6.1〕
- 定義: AI がコードを高速に生成する時代には、コードそのものの負債だけでなく、人間の頭の中にも借金が積み上がる。

| 負債 | 蓄積する場所 | 内容 | エージェントの対策 |
|---|---|---|---|
| 技術負債 | コードそのもの、システムの構造 | 動作はするが一貫性がなく保守しにくいコードが、AI の速度で大量に生まれる | 一手ごとのセルフレビュー(七箇条・引き算) |
| 理解負債 | 開発者やチームの頭の中 | 生成コードを十分理解しないまま「動いたから OK」と採用し続けると、チームレベルでさらに速く積み上がる(定義は foundations.md) | 変更の What と Why を説明し、読み手が理解できる大きさに差分を保つ |
| 意図負債 | 外部化された知識(仕様や設計判断の記録) | 「なぜこの設計で書かれたか」という背景が切り落とされ、コードは読めても変更の判断ができなくなる | Why をコメントに、設計判断(選んだ案・見送った案・理由)を報告に残す |

### AI の出力を仕様と混同しない〔9.6.2〕
- 定義: コードを書く速度はボトルネックでなくなり、生成された大量のコードを理解・検証する工程が新しいボトルネックになった。AI の出力は、人間が検証してはじめてシステムに取り込まれる。
- する: 自分の出力を仕様として扱わない(SKILL.md の行動原則5)。差分の渡し方は collaboration.md の「丸投げを防ぐ」に従う。
- 確かめる: 差分は一度に読める大きさか。何を検証したか(実行したテスト・ビルド・静的解析)を示したか。

- 抽象化の経済性(書く手間が消えても読解コストは下がらない)の扱いは、SKILL.md の判断ルール2 に従う。〔9.6.4〕
