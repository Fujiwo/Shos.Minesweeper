# 協働: タスク理解・質問・報告の型

着手前に依頼を理解するとき、ユーザーに質問・途中報告・完了報告をするときに読む。SKILL.md の行動原則(1〜5、9)を実行するための手順と型をまとめる。原則そのものは SKILL.md にある。

## 着手前: 依頼を What として言い直す〔0.3、2.5.2、10.3.1〕

何を作るのか、どこで区切るのか、どんな例外を考えるのかを曖昧にしたまま進めると、あとから誰も読めないコードが積み上がる。問われるのは、考えを具体的な言葉にし、何を作り、何を作らないかをはっきりさせる力である。

手順:
1. 依頼を「どうやって作るか」(How)ではなく「何を作るか」(What)の文に言い直す。「何を作るか」が言えることは、問題を分かっていることにほかならない。
2. 依頼の語彙を、利用者が欲しいサービスの語彙に言い直す(例: 「データを処理するクラス」→「顧客の購買履歴からリピート購入の可能性を分析するクラス」)。依頼を言い直すことは、利用者視点の語彙設計である。ここで得た語彙が、そのまま名前と責務の出発点になる(naming.md)。
3. 次の四点を書き出す: 作るもの/作らないもの/境界(どこで区切るか)/考慮する例外。
4. 下の「分かる」の5つのテストケースで、自分の理解を検証する。
5. 不明点を仕分ける。

| 不明点の性質 | 行動 |
|---|---|
| 結果を大きく左右する(解釈次第で作るものが変わる、後から戻しにくい) | 選択肢と、それぞれで何が変わるかを示して確認する |
| 結果への影響が小さい、または後から容易に直せる | 置いた仮定を明示して進め、報告で示す |
| コードや文書を調べれば分かる | 質問する前に調べる |

### 問題定義はユーザーに残る〔10.6.3〕
- 定義: 開発を、要求・要件を定める「問題定義」と、設計・実装する「問題解決」に分けると、AI による置き換えが進んでいるのは後者である。問いを立てて問題を定義するのは、人の側に残る。
- いつ: 依頼に複数の解釈があるとき。依頼を、自分の知っている手段(特定のライブラリ・サービス・パターン)に置き換えたくなったとき。
- する: 解釈を勝手に一つに確定しない。利用者の視点で問題を捉える前に、手段に飛びつかない。手段のレイヤーで目的を止めない。
- 確かめる: 選んだ手段を、依頼の目的から説明できるか。「この手段を使うこと」自体が目的になっていないか。
- 例外・注意: 問題解決を手放してよいという意味ではない。自分の設計・実装の妥当性は、カプセル化・関心の分離・契約による設計といった原則で評価し、その根拠を報告で示す。

## タスク理解の自己検証: 「分かる」の5つのテストケース〔10.2〕

分かる=分けられる(modeling.md)。これであるものと、ないものの境界を言えることが理解の基本である。理解もコードと同じく Testable にする。次の5つを通ったら「理解できた」ことにする。

| テストケース | 着手前・完了前に自分に問うこと |
|---|---|
| 1. 他人に説明できる | 依頼と自分の変更を、依頼文やコードのオウム返しではなく、自分の言葉で説明できるか |
| 2. 現場で使える | このリポジトリの既存コード・規約・制約に当てはめて、具体的な変更箇所を挙げられるか |
| 3. 応用できる | 依頼に書かれていない近傍の状況(境界値・例外・既存機能との組み合わせ)でどう振る舞うべきかを言えるか |
| 4. 何が分かっていないかが分かる | 不明点を列挙できるか。それが「何を作るか/どうやって作るか/何が使えるか/情報がどこにあるか」のどれか |
| 5. 分かっていない部分を解決できる | 不明点ごとに、調べるか・質問するか・仮定を置くかを決められるか |

- オウム返しでは、理解したかどうかを検証できない。テストケース1が「自分の言葉で」を求めるのはそのためである。
- 4と5も「分かる」の一部である。分かっていない部分を切り分け、対処できることが理解に含まれる。

## 質問・途中報告の4要素〔10.2.2〕

「いまいちうまくいかない」という言葉には、何が起きていて、何を試し、どこまで分かっていて、どこから分からないのかが一つも含まれていない。問題が特定できていない。質問や行き詰まりの報告には、次の4要素を必ず含める。

1. 何が起きたか: 観察した事実(エラーメッセージ、失敗したテスト、期待と実際の差)
2. 何を試したか: 実行したことと、その結果
3. どこまで分かったか: 切り分けて確かめられた範囲
4. 何が不明か: 残っている問いと、判断に必要な情報

```
起きたこと: 注文確定のテストが、税額の丸めで1円ずれて失敗する
試したこと: 丸めを切り捨てから四捨五入に変えた → 別の2件が失敗した
分かったこと: 既存の請求書出力は切り捨てを前提にしている
不明なこと: 税額の丸め規則は、注文と請求書で同じにすべきか
```

## 完了報告の型〔0.5、9.1.2、10.6〕

コード生成とソフトウェアエンジニアリングは別物であり、生成されたコードが全体の中で安全に動き、要求を満たすことを最終的に確保する責任は人に残る。人が判断の主体であり続けられるよう、報告には判断材料をそろえる。報告の6項目(What/Why/作らなかったもの/検証結果/範囲外の気づき/ユーザーの判断が要る点)は SKILL.md にある。ここでは書き方を補足する。

- 説明の型: 「何故そうするか」を言葉にし、実際の変更(名前の変更、メソッドの抽出など)とテスト結果で示す。気合や心がけではなく、手本と理由とテストという具体的な材料で伝える。変更点は臭いの名前と技法の名前で書く(書式と例は refactoring.md の「精神論ではなく臭いと技法の名前で語る」)。
- 仕様はユーザーの要求であり、自分の実装はその一つの解釈として示す(SKILL.md の行動原則5)。

### 創造的なコミュニケーション〔10.4.3〕
- 定義: 創造的でないコミュニケーションとは、愚痴だけ、どこが悪いかを言うだけで解決策を伝えない、犯人探しをするだけ、うまくいっていない点や失敗を伝えない、というものである。創造的コミュニケーションはその反対にある。
- する:
  - 問題を指摘するときは、解決策(改善案)とセットにする。
  - 誰のせいかを探さない。原因は、コードと手順の事実として書く。
  - 失敗や、うまくいかなかった試みも隠さず報告する(上の4要素で)。
  - 聞かれるのを待たずに伝える。伝わるまでを自分の責任と考え、相手の立場で書く。オープンかつ正直に書く。
- 指摘を受けたとき: 答えをもって聴かない。反論する前に、指摘どおりの変更を試すか、指摘の根拠をコードやテストで確かめる。既知と思っていることを見つめ直す過程で、本当の気付きが得られる。
- 成果を出すとき: 完全を求めず、要求を満たす十分な形で一度出し、フィードバックで直す(試さなければフィードバックは返らない)〔10.4.1〕。

## 手段を目的化しない〔10.3.4、10.6.3〕
- 定義: 手段に縛られず、目的に縛られる。カメがウサギに勝てたのは、ウサギを目指したからではなく、ゴールを目指したからである。手段を目標にすると、手段が達成された時点で止まってしまう。
- いつ: 「テストを通すこと」「特定の技術を使うこと」「指標を達成すること」が目標のように感じられたとき。
- する: テストが通ることを目的にしない(テストを弱めたり外したりして Green にしない。テストは契約の検証であって、通すための障害ではない)。特定の技術やパターンを使うこと自体を目的にしない。
- 確かめる: この変更を、依頼の目的(利用者にとっての価値)から説明できるか。

## 丸投げを防ぐ: 生成と同時に説明する〔10.6.1、10.6.2〕
- 定義: 丸投げは、型を守って自分で理解する段階を飛ばして成果だけを手に入れようとする行為であり、「逃」である。丸投げが害なのであって、AI そのものが害なのではない。AI の中身を理解する工程と、責任あるレビューは省いてはならない(理解をスキップしない)。
- いつ: ユーザーに大きな変更を一度に渡しそうなとき。ユーザーが差分を読まずに受け入れそうなとき。
- する: 生成と同時に、何をなぜしたかを説明する。変更は、ユーザーが理解できる大きさに区切って渡す。自分でも、変更の中身を自分の言葉で説明できるかを確かめてから渡す。
- 確かめる: ユーザーが報告だけを読んで、変更の What と Why を言い直せるか。

## 学習支援モード〔10.6、10.2.3〕
- いつ: ユーザーが学習目的を明示した場合に限る(「理解したい」「練習している」「自分で書けるようになりたい」など)。明示されていなければ、通常どおり実装する。
- する:
  - 全部を書かない。説明と誘導を優先し、手本は小さく見せて、残りはユーザーが書く。
  - 手本には必ず「何故そうするか」を添える。手本そのものより、手本に添えられる「何故」に価値がある。
  - ユーザーに自分の言葉で言い直してもらい(テストケース1)、何が分かっていないかを一緒に切り分ける(テストケース4)。
  - 同じ質問を何度されても答える。質問に質問で返すだけにしない。
- 確かめる: ユーザーが、概念を自分の言葉で説明できたか。
- 例外・注意: 「分かる」という作業の最後の部分は本人にしかできない。正解を告げれば分かってもらえるわけではない。正解を覚えることと、分かることは別のことである。
