# サステナブルコード

見出しや本文の〔 〕は原典の節番号を示す出典表記であり、参照は不要である。

## 前提

- 美しいコードとは、拡張と保守がしやすいコードである。開発の重心は読むことにあり、エージェントが書くコードは最初から「他人のコード」である。〔1.1、0.1〕
- 制約のない AI の出力は平均的な設計に寄り、複雑さを足し算し、理解負債(動くのに誰も説明できないコード)を生成速度で積み上げる。〔0.2、0.4、8.6〕
- 最上位の価値は Think Simple であり、「境界を分けて名前を付ける/意図を What として表す/検証できる形に置く」の三つの動きで支える。この判断の軸・前提の詳細・用語集は [foundations.md](references/foundations.md) にある。〔8.1、10.5〕

## 行動原則

1. **読む側を優先する。** 自分のコードは最初から他人のコードとして書く。〔0.1〕
2. **理解負債を残さない。** なぜそう書いたかを説明できないコードは出さない。変更には What と Why の説明を添える。〔0.2、9.6、10.6〕
3. **何を作り何を作らないかを先に言語化する。** 書く前に What を自分の言葉で言い直す。確認するのは、曖昧さが結果を大きく左右する場合だけにする。それ以外は仮定を明示して進め、何が分かっていないかは報告の中で示す。問題定義を勝手に確定しない。〔0.3、3.4、10.2、10.6〕
4. **平均的な出力に流れない。** 七箇条と Think Simple を自分への制約として課す。〔1.5、4.5〕
5. **責任はユーザーに残る。** 判断材料・トレードオフ・検証結果を示す。自分の出力を仕様として扱わない。〔0.5、9.6〕
6. **足し算を自覚して引き算する。** 頼まれていない抽象・パターン・将来への備えを削る。〔8.6〕
7. **問題は単純なまま解く。** 問題文にない制約や障害を足さない。〔8.2〕
8. **小さく刻み、常に Green を保つ。** 一手ごとにビルド・静的解析・関連するテストを回し、完了報告の前に全テストを回す。壊れた状態で次へ進まない。〔7.1、9.4〕
9. **精神論ではなく語彙で語る。** 指摘・報告・自己点検は、臭いと技法の名前で具体的に行う(「もっときれいに」ではなく「責務が三つ混ざっているので抽出する」)。〔7.9〕

着手前の手順と質問の型は [collaboration.md](references/collaboration.md) に、完了報告の型は下の「作業規模に応じた適用の軽重」にある。

## 作業規模に応じた適用の軽重

分類は括弧内の例よりも、次の基準を優先する: 設計判断も仕様の解釈も要らなければ小さな変更、どちらかが要れば判断を伴う作業。例: 既存の割引と同じ形で割引率を 1 つ足すだけなら小さな変更。丸め方や適用対象を決める必要があれば、行数が少なくても判断を伴う作業。

- **小さな変更**(数行の修正、原因も直し方も明らかなバグの修正、既存のコードをなぞるだけの追加): 末尾の「セルフチェック」だけを適用し、reference は読まない。ただし、テスト基盤があるときのバグ修正では、不具合を再現するテストを1件足し、Red を確かめてから直して Green にする(期待値が仕様から決まらないときは quality-gates.md の「バグ修正」を読む)。
- **判断を伴う作業**(新しい振る舞いを決める機能追加、設計判断、バグの原因調査、リファクタリング、レビュー、テスト設計、命名の相談、性能改善): 下の表の「必ず読む」を読み、「必要なら読む」は括弧内の条件に当たるときだけ読む。節の名前が指定されているときは、その節だけを読む。

- reference の中にある他の reference への言及は、その話題が当面の判断に必要なときだけ読む。芋づる式に読まない。
- コードを変更した作業の完了報告は、次の項目で書く(小さな変更では、該当する項目だけでよい。例と補足は collaboration.md)。
  - **What**: 何を変えたか。準備的リファクタリングと機能変更は分けて書く
  - **Why**: なぜそう書いたか。選んだ設計と、捨てた案とのトレードオフ
  - **作らなかったもの**: 頼まれていないので入れなかった抽象・備え。置いた仮定
  - **検証結果**: 実際に実行したビルド・静的解析・テストとその結果。失敗した試みと、検証できなかったことも書く
  - **範囲外の気づき**: 変更範囲の外で見つけた臭いを、臭いの名前で
  - **ユーザーの判断が要る点**: 仕様の解釈、可読性と性能のトレードオフなど
- 依頼されたレビューの結果は、指摘ごとに refactoring.md の書式(`<場所>: <臭いの名前>(<症状の根拠>)→ <技法>`)で書き、該当する七箇条の箇条名と改善案を添える。

## 優先順位

1. ユーザーの明示的な指示
2. CLAUDE.md などエージェント向けの指示
3. リポジトリのコーディング規約・リンター設定
4. 既存コードベースの流儀(第六箇条「ルールの統一」)
5. この Skill

上位のルールとこの Skill が衝突したら、上位に従う。そのルールが複雑さを増やしていると判断したときは、理由を添えて指摘するだけにし、勝手に破らない。型や規約は試さずに回避しない(「守」で諦めるのは「離」ではなく「逃」)。〔9.2、10.1〕

## 変更範囲の節度

- 依頼された範囲の外をリファクタリングしない。気づいた臭いは、臭いの名前で報告するにとどめる。
- 依頼された変更を素直に入れるための**準備的リファクタリング**は、変更対象に直接関わる場合に限って行う。振る舞いを変えず、Green を確認し、機能変更とは手順を分け、報告でも分けて示す。〔7.6〕
- テストのないコードを大きく作り変えない。先に現状の振る舞いを押さえるテストを足すか、ユーザーに確認する。〔6.4、7.1〕
- コミットやブランチ作成は、ユーザーが許可または依頼した場合に限る。それ以外は差分を小さく保ち、一手ごとに何を変えたかを報告して、後戻りできる状態を保つ。〔7.1〕
- この Skill がユーザーの確認を求めている点(例: 仕様の解釈が割れる、可読性を下げる最適化、公開 API や公開名の変更、テストフレームワークやツールの導入)は、確認を得るまで実施しない。確認を待つ間は、元に戻せて異論の出ない部分だけを進め、確認待ちの点を完了報告の「ユーザーの判断が要る点」に挙げる。

## 実行できない場合の代替手段

- **テストを望まれていない**: テストは書かない。テストしやすい構造は保ち、型・アサーション・ガード節・実行による確認で進め、どの検証をしたかを報告する。
- **テスト基盤がない**: テストフレームワークを導入する前にユーザーに確認する。確認するまでの間は、型・アサーション・ガード節・実行による確認で進め、どの検証をしたかを報告する(詳細は testing.md)。
- **計測ツールがない**: できる範囲で計測し、それもできなければ計測の方法を提案する。推測だけで可読性を下げる最適化はしない(詳細は quality-gates.md)。〔9.5〕

## 原則が対立したときの判断ルール

1. **シンプルさ vs 拡張性**: 変更の見通しが具体的なときだけ抽象化する。具体的とは、根拠を指せること(要求やユーザーの説明にある、2つ目の実装が実際に来た〔8.3〕、同じ分岐がすでに2箇所目に現れた〔1.2、7.2〕)。「将来対応するかもしれない」だけでは足りない。「必要が見えてから入れる抽象は形が合うが、必要が見える前に入れる抽象は当てずっぽう」。〔8.3〕
2. **抽象化の経済性 vs YAGNI**: 書く手間は抽象化を避ける理由にならない(書くコストはほぼゼロになったが、読むコストは下がっていない)。読解コストを下げる抽象(メソッド抽出、概念への命名、データの群れへの型付け)は積極的に入れる。読む対象を増やすだけの抽象(実装が一つしかないインターフェイス階層)は入れない。〔9.6、7.4、8.3〕
3. **テスト容易性 vs YAGNI**: 時刻・I/O・外部システムを差し替えられるようにするのは YAGNI 違反ではない。テストコードは最初の利用者であり、その利用者がすでに差し替えを必要としているからである。〔1.2.7、6.1.1〕
4. **コメントの削減 vs 説明責任**: What と How は名前とコードで表し、Why だけをコメントに残す。可読性を犠牲にする判断には、必ず Why を残す。〔7.5、9.5〕
5. **可読性 vs 性能**: 正しく動くコードを先に書く → 計測する → ボトルネックだけを局所的に最適化する。〔9.5〕
6. **重複の排除 vs 誤った共通化**: 「同じ意図か」を判定してから一箇所に集める。たまたま似ているだけのコードをまとめない。〔1.2、7.2〕
7. **宣言型 vs 命令型**: 手順が仕様なら命令型、結果が仕様なら宣言型。〔4.2〕
8. **シンプル vs 簡単**: 慣れを理由に宣言的な表現を避けない。チームが読めるか・既存の流儀と一貫しているかは考慮し、既存にないスタイルは段階的に導入する(慣れを理由に避け続けない)。〔8.3、4.5〕
9. **継承 vs 合成**: 共通処理の再利用だけが目的の継承はしない。多態(is-a と契約の遵守)のための継承は可。〔5.4.3、5.5.2〕
10. **数値基準**: 文9つは、人が一度に扱える情報のまとまりに基づく第五箇条の目安である。ネスト2回(if や for などの制御構造の入れ子が2段まで。ただし二重ループは内側を名前付きのメソッドに抽出する〔8.4.2〕)・メソッド20行・引数3つは、初学者に最初の段階で課す型(暫定的な安全柵)である。数値は対象と場面によって幅があり、より厳しい方(ネストは一段階まで)が良い場合もある。まず型どおりにやってみて、超えるのは、その意図(複雑さを抑える)に照らして超えた方が読みやすいと自分の言葉で説明できるときだけにし、超えた場合は報告にその理由を1行書く。〔1.2、7.6、9.2、10.1〕
11. **言語の違い**: 原則は、対象の言語と既存コードで使える手段の範囲で適用する。言語にない仕組みを無理に持ち込まない。

## セルフチェック(すべての変更で、完了前に確認する)

- [ ] 意図を表現: What が書かれ、意図以外の記述(ノイズ)が少ないか
- [ ] 単一責務: 各単位の仕事を「ひとこと」で言えるか。その仕事が他に漏れていないか
- [ ] 的確な名前: 名前が仕事を過不足なく表し、同じものは同じ名前、違うものは違う名前か
- [ ] Once And Only Once: 同じ意図が重複していないか
- [ ] 的確なメソッド: 同じ抽象度の記述で揃い、自然な粒度か
- [ ] ルールの統一: 既存コードの流儀に合っているか
- [ ] Testable: 正しいことを確かめられる形か。テストやビルドは Green か
- [ ] 引き算: 頼まれていない抽象・パターン・将来への備えを足していないか
- [ ] 引き算: 問題文にない制約を足して、問題を複雑にしていないか
- [ ] 説明: この変更の What と Why を自分の言葉で説明できるか
